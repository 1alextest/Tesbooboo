## Outcome and owner map

The required result is an understandable read-only connection from an external client into one chosen Tesbo project, with truthful recovery and a later personal revoke. The relevant chain is external client/resource → active issuer/interaction → actual human session on the required host → recognizable account/project/client review → current owner policy and personal consent → callback/exchange → permitted read → truthful status/history → revoke/readback.

The amendment now assigns these joins without replacing their owners (`OAuth spec:235–263`). Its architecture alternatives remain genuine alternatives: a focused first-party login adapter or reviewed suitable same-site topology. Selecting the backend origin did not select either. Keeping OAuth off and using already permitted token clients is a valid interim result (`:249–255`). This review does not select an adapter or change ordinary frontend routing.

## Retained implementation gaps and discriminating proof

These are source observations and proposed witnesses under existing acceptance owners, **not newly demonstrated runtime failures or claims that the amended specification omitted the obligation**.

### GP-1 — The fresh signed-out join is still open; preserve recovery as well as the happy route

**Evidence:** `mcp-oauth-interaction.controller.ts:138–145` sends a signed-out HTML visitor to frontend `/login` with the interaction path. `lib/redirect.ts:85–97` then derives the interaction destination from `API_BASE`; `lib/api.ts:5,2007–2008` also uses that base for copied MCP URLs. `auth.service.ts:289–305` sets a host-only Lax session cookie. `next.config.mjs:13–22` rewrites only `/api` to the backend. These components do not prove a fresh browser can carry the session to the selected backend issuer. The amendment and guide now explicitly recognize that constraint (spec:249–255; guide:193–217).

**Concrete recovery witnesses from additional source:** the OTP page's “Use a different email” link returns to bare `/login` (`app/verify-otp/page.tsx:135–139`), and a lost session during profile completion also returns to bare `/login` (`app/complete-profile/page.tsx:36–47`). Those paths discard the continuation in the inspected frontend code. Normal OTP → profile → interaction navigation does preserve the destination (`verify-otp/page.tsx:56–65`; `complete-profile/page.tsx:74–80`). The selected adapter may change which of these paths is offered; this is not authority to remove an existing authentication option.

**Disposition / owner:** covered implementation/recovery work under spec:253 and OAUTH-15. Authentication owner must decide how an offered account-change/profile recovery safely preserves or deliberately restarts the original interaction. No additional specification blocker: the amended requirement already includes wrong account, lost session, account/profile recovery and honest restricted-pilot scope.

**Proposed proof:** start from the real external client with no session on the actual origins; observe cookie storage and delivery independently; finish login, explicit consent, exact callback, token exchange and project read. Include wrong existing account, change-email during OTP, profile lost-session, interaction expiry, blocked cookies and foreign/malformed continuation. After an expired request, an explicit restart may be correct; it must not silently authorize an old interaction or strand the person on an unrelated dashboard. A valid ordinary frontend login and existing token client must continue to work.

**Evidence limit:** `e2e/ui/oauth-login-continuation.spec.ts:15–56` substitutes signed-in state and HTML without issuing a session cookie; its URL/heading assertions (`:60–105`) can protect frontend navigation but cannot establish this browser/session join. I did not execute that suite. This is consistent with the amendment's explicit evidence limitation, not a reason to delete those useful checks.

### GP-2 — Consent must identify the human account and point to the authority the member actually has

**Evidence:** current consent HTML shows the raw `userId` for Account and has Approve/Cancel but no account-switch control (`mcp-oauth-interaction.controller.ts:156–174`). Workspace/project now have recognizable names and stable IDs (`:165–166`), which should be retained. The same HTML tells the person “You may later revoke the project grant” (`:168`). That wording conflates owner policy with a member's personal consent, whereas the personal-history panel correctly explains the distinction and offers “Revoke my consent” (`ExternalMcpAccessPanel.tsx:81–105`). An existing account lookup already provides email/name (`auth.service.ts:192–220`); a second account store is unnecessary.

**Disposition / owner:** source-confirmed copy/recognition gap to resolve at the existing interaction owner under spec:255,261 / OAUTH-15–16; no additional amended-spec blocker. Do not present a UUID as evidence that users can recognize a wrong account. Exact safe account-switch behavior depends on the selected login topology and must preserve provider-bound continuation and CSRF safeguards.

**Proposed proof:** a participant using a wrong but valid signed-in account can identify that mismatch before positive consent, choose a safe next action, return under the intended account or cancel without a grant, and locate their personal revoke afterward. Include a normal member who cannot edit project approval and an owner who can. After policy changes while the page is open, positive submit must refuse stale review while cancellation remains available. Current source retains that deliberate cancellation path before target policy re-evaluation (`controller:194–208`); preserve it.

**Accessibility limit:** source HTML has a language, title, heading, native form/buttons and viewport (`:158–174`). Those are useful existing semantics. Keyboard/focus behavior, screen-reader reading order, long identities, zoom/reflow and accessible expiry/error/restart pages remain untested. JSON/framework error source is not proof of a usable browser recovery surface.

### GP-3 — Keep truthful existing status distinctions and add only facts the evidence can support

**Evidence:** current shared panel already labels owner admission as “preapproved (not connected)” (`ExternalMcpAccessPanel.tsx:251,278–299`) and history as records rather than app-online evidence (`:78–109`). Personal history loading/error/revoke notices use status/alert semantics; failed revoke clears local rows instead of claiming definite failure (`:34–74,87–89`). Manager save ambiguity likewise forces authoritative reload (`:152–173`). These are supported no-change behaviors.

The existing bearer checker separately says its read permission/project identity were verified and writes/reporting were not (`settings/api-tokens/page.tsx:822–879`). It must remain a bounded token check. Neither that result nor project “On” nor an empty personal history can certify OAuth readiness. `lib/api.ts:1955–1968` exposes consent history states, not token expiry, client liveness or last successful OAuth use.

**Disposition / owner:** spec:259–261 and OAUTH-16 now correctly require provider / project / exact-client / personal-consent / observed-use facts independently, with unavailable/unverified states. Do not manufacture new telemetry, a readiness database or an “all ready” aggregate to fill absent data. No additional status requirement is needed within this inspected scope.

**Proposed proof:** exercise both settings entries with provider unavailable, admission missing, current consent but no observed use, permitted observed read, unavailable history and a truly empty history. A normal member must receive only permissible explanation and the next responsible actor; inability to inspect owner policy must not become “no approved client.” On lost revoke/save acknowledgement, allow authoritative inspection of the original outcome before another mutation. Preserve project-switch fencing (`panel:14–15,34–51,132–150`). Same-project account-switch isolation is a **hypothesis to inspect**, because these effects are keyed by project/permission/refresh rather than account identity; I did not inspect enough upstream session/layout remount behavior to assert a leakage defect. Hold an old response, switch account with equal project role, and verify old data/actions cannot appear under the new account before closing that obligation.

### GP-4 — Explain breadth and project-wide reconsent before policy saves; retain conservative enforcement

**Evidence:** the OAuth form writes `allowedTools:null` (`ExternalMcpAccessPanel.tsx:210–216`) while the shared predicate treats null as no tool-name restriction (`mcp-access.ts:136–144`). Existing approval supports a non-empty tool list (`:90–103`), so reuse that policy structure if an explicit pilot restriction is chosen. The form currently has no OAuth-specific tool selector. The manager UI save actions show local add/revoke/enable notices (`panel:190,215–216,237–256`), while the actual writer advances the revision and tombstones prior OAuth families throughout the project (`mcp.service.ts:503–510`). Thus an unrelated API-client edit can require OAuth reconsent. This is intentional policy, not evidence of an incorrect revocation mechanism.

**Disposition / owner:** spec:263 / OAUTH-18 already names both consequences and the unresolved owner-selected pilot tool/data and offline lifetime boundary. Preserve conservative invalidation; explain before consequential saves that existing OAuth users in this project must consent again. Do not show an affected-person count without authorized current evidence, silently narrow existing grants, or treat read-only as data minimization. Current consent's offline “until revoked” wording (`controller:167`) must also be reconciled with the finally selected expiry/recovery policy; no exact lifetime is selected here.

**Proposed proof:** show the approved all-read choice including its future-read-tool implication, versus a selected explicit restriction; verify displayed effective tools match permitted discovery. Save an unrelated token-client change, keep another project's client as an unaffected control, and verify the old project OAuth family remains denied after same-ID reapproval until new explicit consent. Ask an uncoached participant to predict that consequence before save. Keep source/database enforcement proof separate from participant comprehension.
