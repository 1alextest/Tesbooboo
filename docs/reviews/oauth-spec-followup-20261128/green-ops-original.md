## Source-contract details for the next handoff

### GOPS-01 — pre-registration and CIMD are not interchangeable client contracts

**Observation/classification:** confirmed source contract mismatch for a **conditional, unselected input**, not a demonstrated target-client failure, security bypass or unconditional doc blocker. The operator's `configuredClients` accepts any nonempty bounded string as a static `client_id`, and constructs public clients with `token_endpoint_auth_method: "none"` (`src/auth/mcp-oauth-server.ts:76–106`). Project policy independently requires a canonical HTTPS URL as `oauthClientId` (`src/mcp/mcp-access.ts:61–74`); the UI also requires this shape (`ExternalMcpAccessPanel.tsx:195–214`). Thus an opaque statically registered ID can pass provider configuration but cannot receive the project approval required for a usable grant. A canonical HTTPS statically registered ID remains a valid existing path; CIMD has a separate ChatGPT-URL predicate (`mcp-oauth-server.ts:20–27,208–219`).

**Consequence:** guide `:222–224` offers reviewed pre-registration or CIMD, while the old decision register retains actual-client registration selection (spec `:196–203`). The next handoff must give the actual selected client ID shape, callback and authentication mode to **both** operator configuration and project policy. A configured provider and an authentic client do not alone make that identity admissible. Do not promise opaque pre-registered clients, silently substitute a static client for the target's CIMD identity, or force a signing-key client to `none`.

**Disposition:** resolve independently from the actual client evidence and existing bounded policy before that path is advertised; if broader ID/authentication support is needed, it is a deliberate extension at the existing registration/policy/UI owners. Preserve current fail-closed rejection and the working HTTPS/public-client alternative. Discriminating proof: selected legitimate registration reaches policy/consent/exchange/read; an opaque ID is truthfully refused or explicitly supported under a separately reviewed extension; wrong client/callback/auth method remains denied. No live client identity was obtained or modified here. Existing D2/OAUTH-05/12/17 are the destination, not a new workstream.

### GOPS-02 — carry an explicit credential × endpoint × protocol matrix into client acceptance

**Observation/classification:** confirmed source asymmetry; existing D6/OAUTH-10/12/20 qualification, not proof of protocol nonconformance. Product `src/mcp/mcp.controller.ts:65–94,147–189,192–225` sends a verified OAuth principal on the project endpoint through the modern codec, keeps the shared endpoint on the API-token path, and preserves legacy token routing. `src/mcp/mcp-oauth-modern.ts:4,38–103,106–129` accepts only `2026-07-28` metadata/headers and the named modern methods, including successful `server/discover`, without initialize/session fallback. `src/mcp/mcp.types.ts:22–29` advertises the legacy initialize versions for the API-token surface.

**Consequence:** the current continuation correctly says “replicas/client protocol” and preserves old clients, but implementation/client handoff should state this concrete existing matrix. Earlier spec `:9–13` is explicitly a limited safety increment; it must not be read as a complete current inventory. A future API-token legacy success cannot certify OAuth protocol behavior; a client's successful OAuth exchange cannot certify its subsequent MCP request era. API-token clients and OAuth clients cannot be treated as one homogeneous compatibility population.

**Disposition:** retain current source behavior pending actual target-client evidence and D6 authority. Qualify the exact project OAuth path and actual client era first, plus legacy API-token project/shared positive controls, wrong-era/header/body refusal and stale-grant denial. If the target client uses another era, surface the blocked compatibility choice rather than silently converting transport or weakening version checks. No actual-client incompatibility was observed, and source presence does not certify modern standards conformance.
