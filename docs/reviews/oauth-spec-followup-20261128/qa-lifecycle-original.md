## Existing evidence boundaries — retain, do not inflate

1. **Browser navigation fixture.** `e2e/ui/oauth-login-continuation.spec.ts:11–57` starts without stored browser state, but its route handler answers `auth/me`, password/OTP verification, profile completion and final consent HTML. Password/OTP success is an in-memory boolean (`:34–50`); the final document is fulfilled locally (`:20–22`). Cases at `:65–105` can discriminate frontend continuation/navigation regressions. They do not exercise the actual session `Set-Cookie`, browser storage/SameSite decision, backend session resolution, provider callback or actual project read. This is a useful scoped fixture, not a defective test merely because OAUTH-15 needs more.

2. **Real issuer plus saved-session continuation.** `Tesbo-Backend-Nest/scripts/ci/oauth-interaction-redirect.cjs:155–167` follows the authorization interaction and checks its sign-in return path, then directly creates a session and installs it in a `CookieJar`. The following forms, exchange and tool read are stronger joined downstream checks (`:169–197`), but installation bypasses actual frontend login and browser cookie delivery. The test deliberately disables session caching (`:110`). It cannot certify cache-enabled recovery behavior. The ordinary HTTP consent suite also substitutes provider/session outcomes (`src/mcp/mcp-oauth-interaction.http.integration.spec.ts:25–26,40–85,95–115`). Its actual Nest HTTP boundary should retain credit within that scope.

3. **Persistence lifecycle/reinstatement.** `src/auth/mcp-oauth-grant-binding.db.spec.ts:216–264` uses the actual owner settings writer to revoke/reapprove and rejects the old Grant/RefreshToken. Its `:312–373` variant preserves four old model artifacts across direct membership delete/reinsert, checks changed membership identity, refuses stale binding, and checks a fresh family. These are meaningful persistence oracles. The deletion is intentionally direct SQL (`:288–292`); neither the real membership mutation/invitation path nor pinned-provider HTTP refresh concurrency is established. The earlier `:298–303` cleanup destroys its family before restoration and therefore, alone, would not prove non-resurrection. The later preserved-artifact variant supplies the stronger source-defined scenario; no execution is inferred.

4. **Atomic consume versus HTTP races.** `src/auth/mcp-oauth-postgres.adapter.db.spec.ts:93–119` checks concurrent adapter consume/replay-marker operations. `scripts/ci/embedded-oauth-state-spike.cjs:267–274` overlaps credential **lookups**, then `:279–289` exchanges a new code, refreshes once and rejects code replay. It does not submit two competing refresh redemptions or replay the old refresh token. Atomic adapter SQL is present at `src/auth/mcp-oauth-postgres.adapter.ts:160–170`; this cannot by itself prove the provider's complete rotating-family HTTP behavior. Spec `:273,285` correctly retains that distinction.

5. **Consent UI versus durable revocation.** `e2e/ui/projects.spec.ts:560–606` mocks both history and DELETE responses. It proves selected-record UI semantics and that history is not labelled live. The separate DB scenario (`src/auth/mcp-oauth-grant-binding.db.spec.ts:125–147`) asserts other-user isolation, durable self-revoke and exactly one audit after a repeat. Preserve both narrower observations; they do not jointly become proof that an actual client stopped using its existing token after an actual browser revoke.

### QA-L3 — refresh/code redemption, withdrawal and uncertain response (OAUTH-09/19)

**Actual join:** provider credential load → consume/rotation → persistence → HTTP response → subsequent resource authorization. That separation makes ordering a test target, not evidence of an exploited race.

**Required witness:** with an independently verified usable family, submit competing real HTTP redemptions through the pinned provider using independent requests/replicas. Cover code reuse, old-refresh replay, withdrawal before load, withdrawal while a request is held after load, same-ID client reapproval and membership removal/rejoin. Observe every response and family identity, then attempt protected reads with every resulting candidate credential. No family predating withdrawal may regain effective access after reapproval/rejoin; a new explicit consent must work. An already admitted response must be classified using the decided in-flight policy rather than being retroactively described as never authorized. OAUTH's existing `:49` requires that policy to be explicit.

Drop a response after rotation has durably committed and distinguish unknown delivery from unsuccessful rotation. Recovery and replay/family-invalidation expectations require D5's actual lifetime/reuse policy (`spec:127,185,200,263,273`); do not invent a universal number of winning refresh responses or silently retry a token whose outcome is unknown. Include a normal no-withdrawal refresh, expired input, different family/project, and API-token use as controls. A no-response timeout is neither defect-detection evidence nor successful revocation proof.

## Source hypotheses — coupled only when the selected path depends on them

### H1 — competing OTP verification may reuse one code

`src/auth/otp.service.ts:48–59` selects an unused code, then `:130–131` updates it by ID without an unused-state predicate/returned consume winner. Two requests reaching the SELECT before either update are a plausible route to two successful verifications; session creation follows successful verification (`:37–45`). **Source-supported concurrency hypothesis, not an executed product failure.** The amendment already calls it a hypothesis requiring controlled proof (`spec:273`).

If OTP is offered, verify authoritative valid/unexpired/unused preconditions and hold two distinct requests at the exact consume phase. Observe code-consume outcomes and every resulting session for that account. A single-use contract needs one successful consuming authentication and no second session from the same consumed code, with wrong/expired/already-used codes refused. A fresh different code and unrelated account must still work. Use real DB/middleware with isolated users; a mocked false verify or an earlier rate-limit rejection does not test atomic consumption. If confirmed and coupled, repair the shared OTP owner; do not create an OAuth-only verifier. A deliberate password-only pilot may defer this path only under the existing explicit pilot decision.

### H2 — session revocation can interact with positive-cache refill/failure

`src/auth/otp.service.ts:101–114` returns cached identity before DB read and can refill after reading the row. Session removal precedes cache invalidation (`:117–127`). Cache positive TTL is 60 seconds (`src/cache/session-cache.service.ts:8`), while invalidation errors are swallowed (`:84–109`). A held resolver could refill after deletion/invalidation; a cache deletion failure could leave a positive entry. **Source-supported stale-authority hypotheses, not proof of their runtime reach or actual deployment settings.** The amendment correctly keeps this open (`spec:273`).

If the chosen login/consent solution relies on these sessions, test the configured cache-enabled path, not only the provider fixture that turns it off. Establish a real positive cached session, hold a resolver between authoritative read and cache population, perform logout/password reset/change, release it and attempt protected consent/session use. Separately inject cache invalidation failure with storage deletion verified. The refused result must be attributable to current session authority, not foreign-origin/CSRF failure. Include cached valid login, cache unavailable/miss fallback, unrelated account/session and permitted fresh login. The expected effect of browser logout/password events on **existing offline OAuth families** is a separate product policy decision: current browser-session invalidation code does not establish that policy (`auth.service.ts:160–188`; spec `:263`). Do not silently equate the two credential lifecycles.
