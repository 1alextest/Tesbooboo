## Review result

**Disposition: CHANGES REQUIRED; NOT implementation-ready.** The feature direction (add inbound OAuth to the existing MCP authorization owner, preserve API tokens) is sound, but the current spec permits several divergent interpretations with security and interoperability consequences. The following findings convert those ambiguities into specific owner decisions, enforcement points, exact tests and acceptance evidence.

## Cross-lens questions that the original review must not silently decide

1. **Security/authority:** Is Tesbo acting as a compliant AS itself, or will an existing supported external AS issue resource-bound tokens? Confirm which service owns keys, token family, client registration, user login and audit.
2. **Project authority:** Does an owner preapprove named OAuth clients before end-user consent? Can a member initiate read-only only? What does “write” allow for non-owner members? Existing project roles and machine-publication restrictions must be preserved.
3. **Discovery/client trust:** Will the server advertise CIMD support, DCR or pre-registration? Which clients/redirects are accepted? Provide real ChatGPT metadata/redirect observed in connection flow.
4. **Grant lifecycle:** May a user consent once for multiple projects? Default **no** pending explicit approval. Define expiry/reconnect/revocation semantics and semantics when grants reach the configured count limit.
5. **Transport:** Does ChatGPT actually accept Tesbo's current HTTP success codes, content type and JSON-RPC session behavior? Measure rather than assume.
6. **Operability:** What happens on authorization-server outage? Existing API-token clients must remain unaffected; new OAuth grant/refresh should fail closed and expose useful, safe diagnostics.

## Completeness adjudication (White lens; analytical only)

- **Covered but unresolved:** identity boundary, AS choice, registration model, project consent, credential lifecycle, transport compatibility, ChatGPT product capability, regression reuse.
- **Newly surfaced as explicit obligations:** metadata fetch SSRF/DNS rebinding and localhost-client impersonation; client identity vs consent trust; middleware-level OAuth challenge; project-count and concurrent grant edits; token-family state and recovery; transactional revocation race; outcome-truth UX states; consequence-aware grant graph; observability SLOs; existing MCP HTTP 201 behavior.
- **Still external / blocked:** actual IdP inventory, middleware call-graph for every deployment path, current ChatGPT handshake with deployed Tesbo, human owner decisions, individual Independent/White delegates, native test-case creation, actual test execution and release approval.
- **No claimed signoff:** this review is evidence-grounded lens analysis, not multiple independently executed agents. Human product authority and truly independent reviews are required before design freeze.

**Review exit:** the source specification must explicitly contain OA-01–OA-16 as testable obligations or tracked decisions, with owners and verified closure. A later code PR should not declare acceptance from this review alone.
