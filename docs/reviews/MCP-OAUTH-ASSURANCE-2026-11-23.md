## Current-version addendum: MCP 2026-07-28 (standards review)

**Important later finding OA-17, P0 interoperability/Green:** The [MCP 2026-07-28 release](https://blog.modelcontextprotocol.io/posts/2026-07-28/) explicitly replaces handshake sessions with a stateless core: `initialize`/`initialized` and `Mcp-Session-Id` are retired for that revision; client/version/capabilities are supplied per request, with optional `server/discover` and `Mcp-Method`/`Mcp-Name` headers. DCR is deprecated in favor of CIMD but remains for backward compatibility. Credential isolation to the issuer and authorization `iss`/scope-step-up requirements are strengthened. Tesbo's inspected `mcp.controller.ts` still implements the earlier handshake path and rejects GET/DELETE. This is **not evidence the old implementation is invalid for older clients**; it is a version-compatibility obligation. The [MCP TypeScript SDK migration notes](https://ts.sdk.modelcontextprotocol.io/v2/migration/support-2026-07-28) specifically distinguish per-era wire codecs and OAuth opt-ins.

**Required revision:** select a supported-version matrix, protocol detector and minimum ChatGPT-required era using a real handshake. Either retain older clients and add separately tested stateless 2026 support or explicitly defer 2026 with demonstrated target-client compatibility; do not claim 2026 conformance from OAuth discovery or 2025 tests. Define 2026 per-request authorization, header/body consistency, caching/expiry versus grant revocation, issuer-bound credentials and no accidental downgrade. Prefer modern spec conformance for new integrations when target-client support is evidenced; preserve existing working clients.

**Additional regression OA-T15:** exercise old and modern client wire requests, including unsupported/mixed/missing `MCP-Protocol-Version`, forged `Mcp-Method`/`Mcp-Name` relative to body, replayed 2025 sessions, stateless read/call after grant revocation, cache TTL during tool permission changes, auth issuer switch, and false-downgrade attempts. Oracle: no cross-protocol tool/permission ambiguity, denied writes stay unchanged, explicit supported version, old client success and real ChatGPT compatibility.

## Review result

**Disposition: CHANGES REQUIRED; NOT implementation-ready.** The feature direction (add inbound OAuth to the existing MCP authorization owner, preserve API tokens) is sound, but the current spec permits several divergent interpretations with security and interoperability consequences. ## Downstream producer provenance finding OA-18 (P0; additional Green/Security/Blue challenge)

Two actual MCP staging tool handlers in `Tesbo-Backend-Nest/src/mcp/mcp.tools.ts` (current `development` around lines 1947–1961 and 2013–2017) require `ctx.tokenId` and pass `{kind: "api_token", transport: "mcp", tokenId: ctx.tokenId, actorId?}` to the existing testcase/requirement proposal staging owners. The tool context is defined in `mcp.types.ts` and populated by `McpService.callTool`. This proves that a mere controller/token principal adaptation is **insufficient for OAuth writes**. Those proposal owners may have additional receipt and idempotency assumptions; trace before changing them.

**Contract:** preserve existing API-token producer receipts verbatim; introduce an authorized credential-kind-aware staging producer representation carrying stable OAuth grant/client identity, verified subject/issuer/project binding and existing agent actor provenance, **without a fake `api_token` ID**, without allowing caller-supplied `kind`, and without changing human-only apply/review. Exact existing proposal hash/receipt version and replay behavior must be inspected before migration. No duplicate task/case owner.

**Added OA-T16:** real read-scoped OAuth discovery; legitimate OAuth write stages a native testcase/requirement proposal with accurate machine provenance; forged credential identity/kind, revoked grant, mismatched tenant, duplicate request, lost response and stale role fail closed with no official writes; unchanged API-token staging receipt and replay still pass; human apply remains separately authorized. Persist official cases/runs in TESBOPROJECT only after authorized review. **Not run**.

## Cross-lens questions that the original review must not silently decide

1. **Security/authority:** Is Tesbo acting as a compliant AS itself, or will an existing supported external AS issue resource-bound tokens? Confirm which service owns keys, token family, client registration, user login and audit.
2. **Project authority:** Does an owner preapprove named OAuth clients before end-user consent? Can a member initiate read-only only? What does “write” allow for non-owner members? Existing project roles and machine-publication restrictions must be preserved.
3. **Discovery/client trust:** Will the server advertise CIMD support, DCR or pre-registration? Which clients/redirects are accepted? Provide real ChatGPT metadata/redirect observed in connection flow.
4. **Grant lifecycle:** May a user consent once for multiple projects? Default **no** pending explicit approval. Define expiry/reconnect/revocation semantics and semantics when grants reach the configured count limit.
5. **Transport:** Does ChatGPT actually accept Tesbo's current HTTP success codes, content type and JSON-RPC session behavior? Measure rather than assume.
6. **Operability:** What happens on authorization-server outage? Existing API-token clients must remain unaffected; new OAuth grant/refresh should fail closed and expose useful, safe diagnostics.
