## 1. Product purpose, corrected positioning and differentiation decision
**Owner clarification (2026-11-18):** Tesbo is NOT intended to be another coding agent or IDE, nor merely an AGENTS.md reminder or a collection of MCP endpoints. Its existing project, test-case, run, bug, Knowledge Base, Zyra and graph foundations serve multiple functions; **cross-role BA/PM/policy workflows and end-to-end release controls are part of the intended platform and are not yet verified as fully implemented**. This is a product-vision correction, not a release claim. Proposed new capabilities must **extend this shared product** rather than invent the collaboration premise from scratch.

**North-star product thesis:** **Tesbo is a collaborative software engineering assurance and delivery platform for software built by humans and agents.** It gives people a comprehensible, accountable account of an application: what it should do, what agents changed and attempted, what actually works, what remains uncertain, who owns decisions, and whether a known build is ready for a controlled release. It is where fast agent-assisted/vibe coding meets evidence-backed engineering discipline. It should help teams reach production sooner *and* lower avoidable failure/rework risk.

**Differentiation to prove, not merely assert:** Human visibility, cross-role coordination and release confidence over autonomous/agent-assisted work **without prescribing a coding agent or replacing its IDE**. An individual vibe coder can operate a lightweight path; an organization can use role-based QA/BA/PM/policy/security approvals and audited history; both share one Tesbo control plane. The proposed Skills module governs how each domain's agent authors its material; it is not a stand-in for the application's accepted requirements or for human judgement.

**Core product questions:**
1. **What should happen?** Approved requirement, business rule/policy, scope, affected journey and independent acceptance oracle.
2. **What is happening?** Human/agent activity, tool calls *actually observed by Tesbo or authenticated integrations*, in-flight work, stalled/deferred tasks, who owns the next decision.
3. **What changed and why?** Pinned source change, requirements/case/manual/policy/task/evidence deltas, causal provenance and impact on downstream behavior.
4. **What was proved?** Exact cases, run selection, results, evidence integrity, environment and deployed version; do not mistake agent explanation, static CI or green check for target acceptance.
5. **What remains risky?** Coverage gaps, policy conflicts, unknown deployment state, missing evidence, rejected drafts, known defects and accepted residual risks.
6. **Can we release?** A computed, explainable release-readiness report and authorized human decision, with rollback/monitoring plan and deployment verification.

**Existing owner reuse:** Testcases/Plans/Runs/Bugs, Requirements external-cache, Knowledge Base, Zyra Copilot/tasks, MCP, graph history/notifications, releases and existing QA UI stay native owners. A Change Workspace is a **connected role-sensitive projection and review workflow** over these, not a new independent requirement/test/wiki/issue database.

**Market interpretation correction:** A broad product feature overlap does not make a product a direct competitor. Kiro, Claude Code, OpenCode, Codex and Spec Kit are primarily **complements, integrations or interoperable process tools**: their agents can work through Tesbo MCP. Qase, TestRail and other test-management tools are direct competitive baselines. Full ALM products (Polarion, Codebeamer, IBM ELM) and DevOps platforms (GitLab, Atlassian) are adjacent/partially overlapping and valuable design references, not necessarily one-to-one substitutes.

**Assurance truth:** "Guaranteed stable application" must NOT be promised as defect-free software. Tesbo should provide *reproducible evidence, bounded risk, policy-conformant decisions and faster detection/recovery*, letting organizations trust agents based on observed outcomes, not model confidence. Measure improvement rather than claiming certainty.

## 3. Standards and architecture candidates (not automatic dependencies)
- **Agent Skills open standard:** `SKILL.md` + optional `scripts/`, `references/`, `assets/`. Official specification: https://github.com/agentskills/agentskills . Our ASER Skills document currently specifies KB-backed text but never mentions `SKILL.md` or standard import/export, script handling, manifest/package digests, supported agent/engine constraints or compatibility. **New material design gap**: choose a portable package contract; default to skills being instructional text only until sandboxed executable payload rules are authorized.
- **Google Agent Registry / Tessl**: independent immutable versions, runtime default assignment, scanning and evaluation provide source patterns. Reuse ideas; compare with Tesbo's existing Knowledge Base and governed-asset design first.
- **MCP Authorization and OWASP MCP Security:** audience-bound tokens, least privilege and tool schema integrity beyond prompts; protect against token pass-through, prompt/tool-description injection, unauthorized delegation and hidden alternate API paths. https://github.com/modelcontextprotocol/modelcontextprotocol/blob/main/docs/specification/2026-07-28/basic/authorization/security-considerations.mdx ; https://cheatsheetseries.owasp.org/cheatsheets/MCP_Security_Cheat_Sheet.html
- **OSLC + ReqIF:** optional interoperability vocabulary for external requirements, test artifacts and change records; do not mandate industry-standard import in MVP but preserve IDs/schema/source/version boundaries to support it. https://open-services.net/specifications/ ; https://www.omg.org/spec/ReqIF
- **OpenTelemetry GenAI semantics:** tool spans, skill-load spans, agent invocation, latency/exception observability; status of conventions is Development, so adopt selectively and avoid inventing mandatory stable schema. https://github.com/open-telemetry/semantic-conventions-genai
- **SLSA/in-toto-style provenance:** evaluate signing/artifact attestation for executable skill packages, source commits and CI receipts where the trust model requires it; don't treat unsigned model narration as an attestation. https://slsa.dev/

## 4A. The shared human-and-agent operational experience (product-level integration)
**One product, multiple role-specific views—not separate departments building their own copies of application truth.** The existing Tesbo project is the primary navigation context; Zyra remains its native assistant, with external agents accessing the same services via MCP. Use a **Change Workspace / Release Readiness** projection on the existing work and graph, not a seventh duplicate record store.

### Target end-to-end user journey
1. **Begin anywhere:** vibe coder starts an unplanned feature in Kiro/Claude/OpenCode, BA creates requirement, QA finds a defect, PM opens task, or policy authority changes a rule. Tesbo accepts any starting point; no mandatory formal spec before coding, but later normative decisions require evidence/approval.
2. **Bind actor and source:** link project, source repo/ref/commit, work goal and exact authenticated agent/capability; preserve user identity vs agent identity, live tool access vs reported claims.
3. **Discover intended behavior:** read existing applicable policies, authoritative requirement versions, cases/models, documented user journeys, previous findings, skills and active tasks. A discovered implementation behavior is an observation, not automatically the accepted oracle.
4. **Execute engineering:** coding agent implements or changes code and tests. It may delegate QA/BA/documentation/policy/task drafting, but all share one change identity, explicit scopes and bounded authority. Collect agent progress/events if actually received.
5. **Synchronize relevant artifacts:** create/update draft requirement, cases, internal/external manuals, policies, tasks, files and evidence under their module skills; record justified unchanged/N/A/blocked, proposed revision and links. Never fabricate an update to fulfill a checklist.
6. **Make status intelligible to humans:** show one timeline: who initiated, what changed, what agent commands/actions Tesbo witnessed, PR/commit, affected behavior/people, tasks/results, untrusted inferences, decisions, changed and missing records.
7. **Challenge and verify:** independent approved requirement oracle, negative paths and regression tests, browser/API/device checks, execution evidence and skill provenance; a model assertion or "I ran tests" message without observed receipt is not proof.
8. **Collaborate and approve:** BA reviews expected behavior, QA reviews cases/results, policy/security reviews controls, PM owns delivery/risks, technical reviewer approves implementation. Exact revision and authority gates apply, separately; no agent impersonation of a privileged human.
9. **Decide readiness:** a user-facing release panel displays change scope, known deployed/tested builds, verified vs unverified coverage, blocking defects, policy conflicts, pending approvals, rollout/rollback plan and residual risks. Readiness computation is explained; authorized human makes release decision.
10. **Observe actual release:** capture deployed build and post-deploy smoke/monitoring, incidents and regressions; link outcomes to the change, update living documentation, reopen failed work and measure speed/quality effects. The cycle is not finished simply because code merged.

### Role-specific questions: same underlying facts
| Role | Must be able to answer in Tesbo |
|---|---|
| **Solo/vibe coder** | What do I need to check before shipping? What did my agent change? What remains unverified? What's the shortest safe next action? |
| **Developer/tech lead** | Which code paths and behavior changed? Which model/agent/tool produced it? Which tests and regressions establish correctness? |
| **QA** | Which approved requirement or oracle was checked? Which cases are drafted vs approved, actually executed against what build, and still missing? |
| **BA/product owner** | Does built behavior satisfy the *approved* user need? Did the agent invent a requirement to explain code? Which decisions are pending? |
| **PM/delivery** | Which changes are in progress, blocked, late, at risk, release candidates, and dependent on which owner? |
| **Policy/compliance/security** | What policy version governs this feature? Who authorized it? Which controls/tests enforce it, and what evidence supports compliance claims? |
| **Executive/business sponsor** | What changed for users, can we release, what's the evidence and accepted risk, and are delivery speed and reliability improving? |
| **Operations/support** | Which build was deployed, how do we monitor and recover, what changed in troubleshooting guidance, and who owns incidents? |

### Data/visibility and assurance constraints
- **Agent activity visibility:** Tesbo can truthfully show Tesbo MCP calls and authenticated integrations. Without a client callback or execution transcript integration, Tesbo **cannot claim to observe every local tool call, file edit or hidden agent decision**. Show observed, externally reported, inferred and unknown as distinct evidence tiers.
- **Risk-based friction:** Solo low-risk project gets simple defaults and role sharing as applicable; organization/regulatory work activates stronger policies. Do not bypass original P-07 protected publication. Avoid needless approval for nonauthoritative drafts or N/A entries.
- **Progress without false confidence:** "No known failure" is not "tested"; "No discovered requirement" is not "no requirements"; code merged is not production deployment; skill configured is not agent-used; a linked case is not executed coverage.
- **Cross-role updates:** Requirement changes notify QA of possible stale cases, manual owners of content drift, policy reviewers of possible control impacts, PM of schedule risk; each gets a concrete **review candidate** with source and consequence, not automatic mass rewriting.
- **Accessibility and usability:** project-specific yet connected dashboards, clear actionable statuses and low-noise notifications. A reviewer can drill from summary to exact source/test evidence; do not need raw logs to understand a release decision.

## 5. Risk and decision register (new findings against *inspected ASER*, not duplicated as confirmed implementation bugs)
| ID | Severity | Scenario demonstrating the gap | Required contract / testable exit |
|---|---|---|---|
| ARC-01 | CRITICAL | Agent infers "requirement" from changed code while existing approved policy requires opposite behavior. An after-the-fact requirement becomes a false independent oracle. | Separate `user_intent`, `approved_expectation`, `source_observation`, `agent_inference`, `verified_runtime`; only authorized source decides normative requirement; show conflict, never auto-ratify implementation. |
| ARC-02 | HIGH | Skill v2 is created in KB as text, but Claude/Kiro/GitLab expect a `SKILL.md` package with references; an uploaded shell script executes via client unexpectedly. | Define Agent Skills import/export, portable manifest, nonexecutable default, allowlisted script types, sandbox, trust/permission boundary, digest+scan/approval; content and referenced assets included in version hash. |
| ARC-03 | CRITICAL | Native Zyra/Copilot uses an admin browser session to approve/activate skill even though the same action is forbidden to the MCP token; effective role does not prove human assent. | Action-bound explicit interactive human confirmation with exact version/hash/assignment, CSRF/replay protection and no AI impersonation; deny all alternate writers. |
| ARC-04 | HIGH | P-18 says project MCP off but a preexisting token can still resolve active Skills or submit candidate; revocation only checked when token minted. | Server verifies project enablement, current membership, current consent and token scope at **every** read/write; deny stale client sessions. |
| ARC-05 | HIGH | Agent creates policy, requirements, manual and cases sequentially; network fails after 2/4 writes, and retry duplicates the first two. | Durable per-change journal/idempotency, staged rows with per-item state, conflict/partial receipts, replay-safe reconciliation, no false all-or-nothing across external sources. |
| ARC-06 | HIGH | Two agents author against different skill assignment heads and requirement revisions; one creates stale cases after approval of the other's policy change. | Exact current-head preconditions, deterministic conflict/compatibility, affected-edge invalidation, review rebase and attribution. |
| ARC-07 | HIGH | Source changes in a PR but agent does not invoke AGENTS.md and no source capture occurs. Tesbo appears synchronized because its last graph receipt was green. | Define event ingestion with source/PR/deploy identity, ordered/fenced captures, delayed/out-of-order handling and a detectable 'sync not observed' state; local hook is advisory not sole mechanism. |

## 6. Minimal build sequence and conditions for an architecture freeze
**Gate 0 — Repair source authority:** obtain actual latest eight canonical Tesbo specs; reconcile P-07, P-14, P-17, P-18 and all ASER R-ASE IDs. Confirm ownership of Skills/KB, requirements, graph and Zyra in deployed source. Decide human-only skill approval and regular case approval independently.

**Gate 1 — Commit to portable skill format:** adopt the Agent Skills `SKILL.md` package as the interchange format or document a concrete reason to limit MVP to equivalent text-only export. Preserve versioned bundle digests, references, validation, workspace/project active bindings and trust; no arbitrary scripts in first slice.

**Gate 2 — Prove the end-to-end change identity:** one authenticated coding agent (code-first feature or bugfix) uses real MCP to propose a native requirement + linked testcase while pinning authoritative source, exact active skill versions, code commit and change packet. Include an independent reference requirement that disagrees with code to prove the agent doesn't canonize wrong behavior.

**Gate 3 — Prove authorization and partial recovery:** deny machine or Copilot-based skill activation/approval through all entrances; enforce project MCP OFF-by-default; stop on concurrent skill/requirement changes, tolerate mid-batch failure, retry without duplicates, and keep original history.

**Gate 4 — Extend one domain at a time:** internal/external manuals and policies, tasks/issues, evidence/files must share traceability primitives but retain separate authority, privacy, publication, review and external ownership. Do not force all modules to update every change.

**Gate 5 — Operability and assurance:** migration/backward compatibility, real incident/runbook, observability, cost/latency budgets, backup restore, source/deployment fingerprints, checked graph/evidence truth. Run genuinely independent Blue/Red/Green/White/QA/Grey/Security/Purple/Graph/Elephant-Gold teams and Simulation on the **specification**, then execute live disposable-project negative tests. An author's charter-guided desk check is NOT an independent team run.


## 6A. Revised delivery priority: prove the whole human-facing loop, not isolated module completion
**This corrects the previous instinct to finish a full Skills Library first.** A standalone module can be perfectly implemented while the human still cannot tell what the agent did or whether the build is safe to release. The first product milestone should be the **end-to-end working journey** over native Tesbo building blocks, with minimum necessary governance from the start. Build domain completeness incrementally *inside that journey*.

|---|---|---|

**Important dependency distinction:** Human-only skill assignment, protected case publication, tenant isolation and trusted oracles are *minimum controls from slice 1 onward*. The remainder of Skills Library UX/evaluation can be built later. A lightweight path is not a permission bypass, and a governance feature is not proved until the coding-agent-to-human journey works.

### Release readiness is an explainable decision, not an AI certification
The engine produces per-release facts and explicit unknowns: source and deployed target identity, approved requirements, changed behavior and impact, candidate/approved cases, chosen execution scope, observed results, unresolved defect severity, policy applicability/decisions, evidence integrity, known risks and release/rollback owners. It may compute **blocked**, **insufficient evidence**, **ready for authorized decision** and **released with known risks**; a model opinion cannot set "safe" and missing data never counts as a pass. Human authorization is bound to exact release candidate version and current receipts.

### Benchmark the question-answering experience against Qase, not only MCP endpoints
Use the same sample feature/bug change and compare (a) creating and reviewing linked QA cases, (b) identifying changed requirement/manual/policy impact, (c) locating accurate test/run/evidence, (d) understanding who did what, and (e) making a release decision. Measure elapsed workflow time, human corrections, omissions, fabricated claims, cross-role rework and production instability.

**Direct competitor cross-check:** TestRail also supports AI-generated test cases, project/role permission gating, field-mapped templates, human review and audit logging; these are **QA category baseline features**, not differentiators by themselves. References: [TestRail AI generation](https://support.testrail.com/hc/en-us/articles/37119835854484-Quick-Start-Generate-Test-Cases-with-AI) and [AI-assisted automation/traceability](https://support.testrail.com/hc/en-us/articles/43587086897428-Getting-started-with-Automate-Test-Cases-with-AI).

**Measurement correction:** DORA's current five delivery metrics distinguish throughput (change lead time, deployment frequency, failed-deployment recovery time) from instability (change fail rate, deployment rework rate), rather than assuming faster deployment alone means better outcomes. [Official DORA metric history, January 2026](https://dora.dev/insights/dora-metrics-history/).

## 7. Decisions for owner; not safely derivable from competitor docs
1. **System of record per project:** native requirements/docs/policies in Tesbo vs externally authoritative Jira/Confluence/Git/ALM, with bidirectional links but no silent ownership swap.
2. **Standard skill payload:** full open Agent Skills package versus text-only first release, and whether executable resources are ever allowed. Human-only promotion and assignment remain separate.
3. **Publish modes:** exact human approval of official cases (binding P-07) versus any revised bounded auto-publication; preserve current approved policy until explicitly changed.
4. **Quality and completion gate:** what must be complete for code merge versus record review, when offline Tesbo is blocked/degraded and which exceptions require a human.
5. **Cross-project and multi-repo scope:** global skill catalog reuse vs isolated policy/data and source-of-truth, with portable export/import.
6. **Where to compete:** focus on independent agents working on existing apps rather than copying Kiro IDE, GitLab full DevOps suite or Polarion heavy ALM. Pilot must validate measurable benefit against Qase MCP + Spec Kit + Git/Confluence/Jira workflows.

**Final assurance verdict:** SOURCE-REVIEWED, ARCHITECTURE NOT FROZEN. The corrected primary purpose is cross-role human understanding, governed agent visibility, safe and fast release—not a coding agent competitor or a collection of standalone MCP functions. New research establishes real direct-versus-complementary distinctions and material open contracts; it does not prove every other area is absent, nor that independently executed assurance teams have run.
