# Versioned collaboration through Tesbo MCP

**Proposed extension to PR #264.** A tester should be able to answer five questions. Which version did I start from? What did I change? What did my colleague change? What would applying mine do now? Who approved the result? The same answers must be available from Tasks, Zyra, an authorized MCP client and the native artifact history. This contract uses the existing FR-027–037 proposal, selection and publication owners, FR-048 corrections, T-422 Skills, and the FR-115/T-455 Change Packet. MCP is a transport to these owners. A project can use this workflow without a Git repository or a provider PR.

## Translate Git operations into user actions

| Git concept | Tesbo action and observable result |
| --- | --- |
| Fetch a known revision | Open an authorized artifact or shared task checkpoint. Receive the stable object ID and exact starting revision, including the dependency and method basis needed for this action. When offline or reconnecting, expose freshness and any unexamined updates. A lost cursor resynchronizes from an authorized snapshot, with no hidden-record counts or silent skips. A paged read identifies its snapshot or reports that it must be refreshed. Fetching has no publication effect. |
| Work on a branch | A person or agent prepares an isolated proposal for one change. Several people can contribute, and one person can have multiple proposals. A branch name, client session or person alone never identifies the unit of work. Unsaved private content stays with the client unless the member expressly contributes it. |
| Stage and commit | Save a typed change as an immutable candidate revision, with a reason, its parent or originating revision, stable logical operation IDs and contributor receipts. Staging a selection records the proposed operations and their dependencies. A checkpoint may be incomplete. The review view distinguishes incomplete checkpoints, validated submissions and applied official revisions. |
| Push for review | A permitted contributor submits the exact candidate to the existing proposal owner. The native service checks authority and the approved Skill and returns a durable receipt. A lost response can be reconciled by its authorized originator. The official case stays at its existing revision. |
| Fetch changes, compare and rebase | On a stale base, show **Base**, **Current** and **Proposed** for the same authorized object and identify affected fields, steps, decisions and dependencies. Preserve the original submission. A reconciled candidate records the new official base and the earlier proposals whose work it uses. |
| Review and merge | The eligible human selects the exact operations and the native writer commits a dependency-closed set against the expected current revision. Show the effective saved values and destination. Creating a new native case yields a Draft. Formal case approval and run admission have separate native checks. |
| Log, inspect or revert | Show the permitted history of an operation, including transitions, reviewers, conflicts and resulting native revisions. To reverse a published change, propose a compensating change on the current head, review its actual impact, then append the outcome. Earlier evidence and decisions retain their original revision. A recording, observation, delivered comment or production release has its own correction or follow-up process. |

Git's three-way comparison, conditional reference update and compensating commit are the relevant precedents. Tesbo supplies object permissions, native data types, business expectations and human approval. For the first implementation, use existing proposal/task identities and their revision streams. It needs no repository per project, branch per employee, full client clone, Git shell, user-accessible force push, or new public MCP command family. [Git merge](https://git-scm.com/docs/git-merge) · [Conditional reference update](https://git-scm.com/docs/git-update-ref) · [Git revert](https://git-scm.com/docs/git-revert)

### The MCP conversation

Discover supported capabilities for the current grant and project before offering an action. Canonical 04 already proposes `list_case_versions` / `get_case_version` for history, `create_change_proposal` and `add_proposal_operations` for draft work, `submit_change_proposal` for review, `get_proposal_review` for comparison and `revise_change_proposal` for a successor. Use T-422's proposed `get_effective_testing_method` for the approved method. These are design-level names. The source's preview-only `stage_testcase_changes` has a distinct current contract. A client must use the advertised version and supported operations. Unavailable personal staging leaves eligible native human authoring available with its own attribution. For example, the client submitting Bob's S2 edit supplies its authenticated request plus a command key, target/project, stable operation and step IDs, original base, expected proposal revision, typed before/after intent and Skill-delivery reference. The server derives the principal from the verified session or delegated grant, checks the target and returns the proposal/operation IDs, stored revision, disposition and permitted next action. A stale request receives a conflict and an authorized route to compare. The client fetches Current, prepares a successor, and resubmits against that basis only after explicit resolution. After a transport timeout, first check the original command's authorized receipt. For a multi-item command, expose the native atomicity rule and per-item outcome. A client can display “submitted for review” only after the native receipt exists and “saved” only for an observed commitment. Human review/apply continues through the protected native owner.

## What the server must know

These are semantic obligations on existing readers and writers. A concrete wire change requires versioned discovery and compatibility evidence from the actual adapter.

| Fact | Binding and behavior |
| --- | --- |
| Target and versions | Distinguish project, native artifact ID, native revision or non-repeating generation, content digest, proposal ID and immutable proposal revision. Bind the relevant dependencies and exact normalized output profile as well. A new target starts with a stable logical create ID and an expected-absent precondition. Capture its mapping to the native UUID on first apply. A rename retains identity. Reusing a title or external key after archive never selects an old target implicitly. |
| Operations | Give each edit a stable logical identity and typed intent, such as changing step S2's expected result, replacing a whole step list, moving a case to another suite, or linking a criterion revision. A step position is a display property. If legacy steps cannot be matched reliably, show a full exact comparison and require an explicit reviewed replacement or fresh proposal. Reordering or deletion must never switch the target of an edit. |
| Ancestry and attribution | Distinguish the version edited, the source proposal(s), and the current official version on which a successor would apply. Preserve original contributor and authenticated delegate, later editor/resolver, current submitter, reviewer, native writer and any external delivery actor. Copying, combining or reapplying work preserves material contributor lineage per selected operation. Applicable self-review restrictions follow that lineage. The client name, Git author/email, commit signature or hash cannot establish Tesbo membership, role or delegation by itself. |
| Preconditions and recovery | Test expected proposal revision, expected official revision, dependencies, rights, Skill and approval basis at the authoritative affected writer. Never use a content hash or last-seen timestamp alone as the concurrency check. A denied or stale operation leaves official state and downstream effects untouched. After a lost response, recover the authorized original receipt before retry. A new request with equivalent intent may be a no-op or duplicate candidate. It never creates a second commitment for the same logical operation. |
| Visibility | A member needs current permission for each exposed object, comparison input, attachment, thread and destination. Opening a successor cannot grant access to its private parent. Filter history, diffs, notifications and exports before disclosure. A permitted cross-project copy requires explicit destination authority, a new local target/base and the receiving project's applicable Skill. Where the origin cannot be disclosed, expose only the authorized transferred content and permitted provenance. If safe disclosure or a trusted base cannot be established, use a scoped fresh proposal or decline. |

The case history trigger stores the **old snapshot** alongside the **new row’s updated_by value**. A dependency change can advance a case revision while leaving the previous editor in that field. For example, Alice edits a case, then Bob changes a tag definition. The drawer must establish Bob’s action from a correlated authenticated transition event before naming him, and must not blame Alice from a carried-over value. If the evidence establishes only that the case’s dependency changed, show exactly that. Field authorship requires separate contribution evidence. The proposal trigger advances a generation and protects producer identity and committed receipts. Current ordinary edits overwrite the draft payload; a counter and activity title cannot reconstruct the prior candidate. For new work, the native proposal owner must persist the base and each immutable candidate snapshot or sufficient typed deltas and contributor evidence to reconstruct it, atomically with its generation, before the first apply. Test two unpublished edits, close the client, reopen each revision, and compare exactly. For legacy or expired history, mark the missing basis. The reviewed case snapshot includes custom fields and tags as dependencies. Reuse those mechanisms and verify the revision exposed by each adapter. ## One case, two agents, one reviewer

1. Alice and Bob use the same approved MCP client with separate member grants. They fetch case C at revision 12 under Skill S4 and the same approved requirement. Both receive the required instructions. Each opens a distinct proposal. Identical fixed inputs and scenario intent must produce the same governed fields under S4. Contributors can propose different intentional changes.
2. Alice improves the preconditions. Bob corrects the expected observation for stable step S2. Both submit against 12. Cara selects Alice's candidate and the native case becomes revision 13. Bob's proposal, field changes and original base remain available to an eligible reviewer.
3. Bob opens his proposal and sees 12 as the original base, 13 as current and his exact proposed change. A preview may combine independent changes. The service validates the **combined** setup, ordered actions and expected results against the approved requirement, relevant policy and current Skill. It presents a new candidate against 13, with the original contributors and the person or service that reconciled them. An ambiguous oracle stays unresolved for the responsible human.
4. Cara reviews and applies that specific candidate. If the case, Skill, relevant dependencies, selected operations or authorized suite override changes again, the writer refuses the stale decision and preserves the work. A successful apply returns the native revision and the selected-operation receipts. Reopening the case shows Alice's precondition, Bob's expected result, the resolver and Cara's decision. The run screen separately reports the formal approval and evidence applicable to this exact case revision.
5. If Bob was offline, his local edit may be preserved privately until reconnect. He fetches current authority and the authorized basis for reconciliation. A shared credential cannot resume Alice's named authorship. Repo or project removal during that interval blocks subsequent protected reads and writes. Revocation cannot recall bytes previously delivered to a client. A member can explicitly hand off the permitted checkpoint, with its visibility and scope, without transferring a private sibling thread.

### When changes do and do not combine

| Observed difference | Resolution |
| --- | --- |
| One side changed a field, or both made the same typed change | A preview may suggest the changed value once. Attribute both independently submitted contributions where supported. Re-evaluate the full resulting case. An equivalent value alone cannot prove a repeated submission is the same event. |
| Different fields changed | Check semantic dependencies. In the test fixture an editor may publish and a viewer may view. Changing editor to viewer on one side and view to publish on the other can merge as text while producing the wrong expected result. Hold the candidate for correction or an authorized product decision. |
| Both changed one expected result differently, or one deleted a step the other edited | Display the permitted original, current and proposed values. A permitted resolver can keep current, use the proposal or enter a reviewed alternative with rationale. Persist the resolution as a successor. Declining preserves the official head and leaves an explicit disposition on the work. |
| Step order, array replacement, suite, required link, custom field, audience or Skill changed | Treat identity, ordering, reference and governance changes as typed operations. Re-evaluate related actions and expected results, destination permissions and normative sources. Ambiguous order or missing dependency returns a conflict. A requirement bundle’s atomic requirement/case/link contract still applies. |
| Several target records selected | Present their exact dependency closure and effects. Apply atomically only where the native owner supports the declared unit. Independent owners record separately recoverable decisions with explicit partial or pending state. A committed operation cannot replay through another proposal. |
| Revert or copy | Calculate the effect against the current target, preserve intervening edits unless expressly reviewed, and check current method and permissions. Reverting C from A to B to A produces a new revision even if its governed bytes match the first A. Do not resurrect its old approval or represent an earlier run as current. Trace any proposed withdrawal/correction of an external communication separately. |

Start with an explicit compare, a deliberate successor proposal and one human decision per native publish unit. Automated combination, if introduced, may prepare a preview only. Reconciliation needs a known authorized common base. If multiple possible bases, incomplete history, retention or permissions prevent a reliable comparison, surface the limitation and permit a new scoped proposal. Individually validated components, matching schemas and clean textual merges can still yield the wrong business outcome.

## Carry the earlier findings through this model

| Previous concern | What the collaboration workflow must preserve |
| --- | --- |
| Skills are consistent across team members | Resolve the applicable Skill at the start, bind delivery to each authorized contributor, validate at submission and re-evaluate the materialized revision at apply. A changed assignment requires an explicit successor or disposition. External submissions can demonstrate delivery before acceptance; only an observed generation path can prove sequence before drafting. A fetched method cannot certify a business oracle. |
| Identity, permissions and contribution history | One member can use multiple clients. Multiple members can use the same app. A service or shared key is labeled accordingly. Queue recovery keeps the originating subject separate from the operator who resumes work. Changing a task assignee, rebasing or copying a proposal cannot confer another person's authority. |
| Two-member edit race | Use stable draft/step IDs and the expected candidate generation on every edit, delete and bulk operation. A stale edit must not hit the new occupant of an array index. Reopen, compare then retry intentionally. |
| New task, Zyra generation, selected review and native approval | Keep the existing Tasks, Changes and Requirements entry points. An analytical task can finish without a native case save. Review shows the complete atomic effects or explicit selected items. The merge receipt, formal native case approval and release decision keep separate authority. Manual/source-free work requires no provider PR or model allocation. |
| Independent Zyra review and the read-only pilot | Seal the authorized independent input set before comparing contributor proposals. Bound author-authored expectations embedded in the diff. Apply FR-124 using the same frozen inputs and budget for both groups. A real reviewer must correctly choose the next action, including hold or no change, against an independent oracle. Record costs, critical misses and uncertain cases. |
| CI, external delivery and exact evidence | PR status refers to its provider/basis. It gives no automatic Tesbo approval. Writing a proposal, resolving a draft, rejecting it or reading its history posts no external comment. Only the configured native save can schedule the qualified delivery. Recover missing initial claims and ambiguous acknowledgements separately, under current send/destination authority. Historical execution evidence stays attached to the actually executed revision and build. |

### Read-only pilot and writable proof

For the one-binding FR-124 shadow evaluation, pin an authorized repository snapshot, its approved expectations, the exact agent report where available, model/Skill versions and input/egress permissions. Seed a valid change, an omitted negative path, a clean textual merge with a wrong business expectation, a stale criterion mapping, and a genuinely undecided outcome. Give both arms the same comparator output and time budget. Only the treatment arm receives Zyra's reconciliation. Have a separate reviewer grade the correct next human decision while blinded to the arm. Before unblinding, the accountable QA owner sets the allowed false flags, time and cost thresholds and critical-miss veto. Report blocked/unavailable inputs separately. Preserve independent results; a draft comparison has zero native writes and zero provider comments.

For writable acceptance on a pinned build, collect both personal connection identities and authorization decisions, delivered method content/version under approved retention, the original, current and proposed case snapshots, three member-attributed receipts (two contributors and the reviewer), formal approval where required and independently reopened case history. Repeat with a refused stale mutation and a valid fresh mutation. Under a policy requiring human-approved cases, attempt run admission immediately after applying a new Draft and verify refusal. Have a separately eligible human formally approve that exact snapshot. Admit it and record one manual attempt with step observations, environment and build evidence. Make a material edit or compensating revision, observe current admission refusal again, and reopen the earlier attempt on its original snapshot. A case save eligible for optional provider delivery has its own receipt; neither proposal submission nor a prior approval authorizes a second external report. If production-like execution or an authorized external test destination is absent, keep that claim open. This forms one end-to-end acceptance record across Tasks, Zyra, MCP, native review and the downstream consumer.

## Acceptance and rollout

Each exercise is an extension of the indicated existing owner. Use separately authenticated people and a controlled test project for claims about Tesbo. Read the candidate, official case, decision receipts, run eligibility, and applicable delivery state after the action. Preserve a negative or unknown observation with its actual evidence level.

| --- | --- | --- |
| Competing heads | Alice and Bob start at 12, then apply in both orders. Exactly one conditional write from 12 can win. The other sees a conflict and can reconcile against 13 without losing either contribution. Check identical request replay and a separately authored equivalent change. | FR-030/032/034, TEAM-05/06, PRR-19/37 |
| Different edits, wrong joint meaning | Compare independent fields that retain the approved expectation with the viewer/publish fixture above. The first may yield a reviewable candidate. The second cannot be labeled valid on a clean text merge. | PRR-24/34, T-422 |

| Equivalent contents across distinct revisions | Save A, change to B, deliberately restore A, then submit a write and an approval against the first A. Reading, declining or reverting a draft sends nothing. | PRR-19/28/32/38 |

For a first writable slice, the proof boundary is one project, one case, two independently authenticated authors, one eligible reviewer, one supported client plus native review, stable step/operation identities and versioned readback. Until the mounted deployment advertises the required delegated stage and validation capabilities, an authorized native human can perform a separately attributed manual proposal; the deployment cannot claim delegated MCP authorship. Introduce changes to the native readers and writer together or return a discoverable unsupported result. Verify older clients keep their documented read behavior, drafts survive conflict, and rollback disables the new write path while historical receipts remain readable. That slice establishes two members on one adapter. For a cross-client consistency claim, repeat with two distinct write-capable clients, separate member grants, the same approved requirement, Skill and frozen three-step input. Compare each member’s independent canonical outputs, then perform the S2-only update and read back all action/expected-result pairs. A read-only client is the refusal control; it does not qualify as the second writing client. A second domain, distributed offline synchronization or multi-repository enforcement requires its own evidence.
