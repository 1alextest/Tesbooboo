# Multi-member MCP authoring and change attribution

**Proposed acceptance contract, 25 November 2026.** This specification covers the question a reviewer must be able to answer when several people use the same assistant or MCP server. Who authorized the work? Which person or process changed this exact revision, which permissions and Skills applied, and who personally reviewed it? The Tasks board, Zyra, external clients and CI must use the evidence owned by the native record they display. The existing authorization model and audit owners remain authoritative. The effective-method and output-conformance contract is defined in [Skills governance](skills-governance.md). Connected delivery, protected submission, activity and execution decisions are defined in [the design](design.md).

## Shared credential lifecycle — staged enhancement (25 November 2026; candidate)

**Purpose:** enable a member to connect their own AI/client using individually accountable authority, and eventually allow an independently authorized project workload, without replacing Tesbo's native identity, roles, project policy, governance or records. This extends the existing enrollment/attribution contract and [OAuth D5/OA-T18R](../mcp-oauth-chatgpt-connection.md). Existing actors, membership/RBAC, ApiTokenService, REST/MCP authorization, revisioned externalMcpAccess and publication owners remain authoritative. OAuth remains read-only/default OFF; no new service account, token broker, generic RBAC system or OAuth write expansion in this slice.

**Research:** [GitHub personal tokens](https://docs.github.com/en/authentication/keeping-your-account-and-data-secure/managing-your-personal-access-tokens) follow user access; [GitHub Apps](https://docs.github.com/en/apps/creating-github-apps/about-creating-github-apps/deciding-when-to-build-a-github-app) separate installation authority from installer identity. [GitLab project access tokens](https://docs.gitlab.com/user/project/settings/project_access_tokens/) use a project bot and support expiry, rotation and inactive history. [Atlassian service accounts](https://support.atlassian.com/user-management/docs/manage-api-tokens-for-service-accounts/) separate service identity and scopes; [Google Cloud workload identity](https://docs.cloud.google.com/iam/docs/workload-identities) illustrates short-lived federation. [RFC 7009](https://www.rfc-editor.org/rfc/rfc7009), [RFC 9700](https://www.rfc-editor.org/rfc/rfc9700) and [MCP authorization](https://modelcontextprotocol.io/specification/2026-07-28/basic/authorization) guide OAuth revocation and resource-bound access, not a universal API-token schema. [OpenAI MCP authentication](https://developers.openai.com/plugins/build/auth) motivates retaining OAuth for clients unable to supply custom API keys; confirm actual client capability. Copy the useful outcome, not the vendor architecture.

**Current evidence:** ApiTokenService generates 192-bit random secrets, hashes them, stores user/project/scopes, records last use and deletes on explicit revoke. REST checks membership and rejects machine control-plane/human-only actions; MCP additionally rechecks the token and intersects the approved client/tool scope. Current API & MCP UI restricts create/revoke to owner/manager, whereas the earlier pinned legacy issuance contract above says members can issue read-only keys: reconcile actual route/controller/service and UI by role before claiming either universally or changing policy. Reviewed V5/service lack intrinsic expiry and rotation; inspect later migrations/consumers. MCP grant expiry is not REST credential expiry. #246's [failed-first job](https://github.com/1alextest/Tesbooboo/actions/runs/45615177204/job/139208593719) reproduced OAuth model resurrection after project/org rejoin; [corrected job](https://github.com/1alextest/Tesbooboo/actions/runs/45624191255/job/139239966529) passed five persisted model cases at bac0089 using existing membership row IDs. At reviewed f17d8e44, stale-review-to-binding probes remain a separate seam; #269 must classify history using that same authority. PAT resurrection is a hypothesis, not an executed finding. Full membership writer inventory and actual deployed acceptance unavailable.

| Principal / relationship | Source of authority | Lifecycle |
| --- | --- | --- |
| Human session | Existing account/session and native roles | Only eligible interactive human can perform protected decisions |
| Personal delegated credential (PAT or OAuth) | Accountable member, current membership generation, resource and credential restrictions; additional MCP grant where applicable | Committed removal terminates old delegated authority; rejoin requires fresh authorized credential/consent; eligible role changes reevaluate capability |
| Independently authorized project workload (future) | Explicit project-owned workload actor and policy, not creator's personal role | Installer departure alone does not terminate independent authority; explicit owner/maintainer/revoke controls |
| Legacy unknown/shared bearer | Possession and known issuer only, not verified operator | Preserve history; never silently upgrade into an individually attributed or project-owned identity |

A label identifies a management entry, not a verified app or operator. A member with two tokens is one accountable member, not independent reviewers. Record distinct actor, issuer/authorizer, client/credential, native writer, reviewer and executor as appropriate; no copied userId, label, email, assignee or shared secret proves human authorship.

### Credential invariants

- **CL-I01:** Keep credential-specific authentication adapters but converge on existing native operation/role/publication decisions. Enforce credential-specific resource/scope restrictions. Do not silently apply MCP-only grants to REST or fall back to cookies after invalid bearer.
- **CL-I02:** Bind delegated credentials to existing project/org membership row identities only after proving their non-reuse across actual writers, cascades and reinstatement. Reuse #246's generation mechanism; no parallel membership store. A stale issuance or consent review cannot be rebound to a new generation. If a writer reuses IDs, repair generation ownership at membership boundary.
- **CL-I03:** Explicit credential revocation is terminal. Role/scope changes reevaluate at use and completion; distinguish temporary pause from terminated authority. Preserve current project-wide OAuth owner revision policy. Decide PAT MCP grant remove/reapprove separately from underlying REST token validity.
- **CL-I04:** Intrinsic expiration must apply to all credential consumers using server time. Decide finite default/max TTL and rotation overlap/cutover/retry before implementation. A replacement has new secret/identity; old credentials cannot regain access or historical authorship. One-time secret delivery; ambiguous response requires secure recovery/revoke and reissue, not secret replay.
- **CL-I05:** Preserve event-time issuer, actor, credential ID, project, authorized operation and revision/evidence after rename, revoke, rotation and membership changes. Separate history, current validity, last use, verified live connection, and actual human work. Never expose secret/digest in history. Review privacy, retention and hard-delete cascades; no inference of historical role from current role.
- **CL-I06:** Recheck at native commit/worker start and completion fence; queued work cannot rely on admission alone. Already transmitted bytes cannot be recalled; define in-flight semantics; no new admission after committed withdrawal. Prove project/membership/credential/binding/audit lock ordering, rollback and outage handling; no duplicate logical effects.
- **CL-I07:** Inventory existing credentials and consumers before migration. Missing issuance-generation evidence cannot be backfilled from current membership by assumption. Explicitly authorize compatibility window or revoke/reissue with user communication; no silent widening or unapproved mass disconnect. Preserve evidence and rollback safety.

### Personal token management (CL-T18/19 implementation candidate)

Current backend permits project members to issue read-only credentials, their issuers to revoke their own credentials, and owners/managers to issue write credentials and revoke project credentials. The interface must expose these existing capabilities without changing server-side authority. Return only an advisory caller-specific `canRevoke` flag from the token list, derived from the same policy as the revoke operation; do not disclose issuer identifiers, infer ownership from token names, or use the flag as authorization. Keep write issuance and external MCP grant approval separate. On project/account change remount the credential interface, including its one-time reveal; ignore superseded list responses. Reload before retry after ambiguous revoke. Acceptance: same-label own/other/unknown issuer, current roles, QA read creation and self-revoke, foreign-token refusal, management projection versus actual API, no secret in list or client config, and no scope expansion. The native lifecycle race and legacy-token transition remain separately governed by #292/#298. This candidate's tests are not evidence of actual client execution.

## Enrollment, identity and authority

1. **Member connection.** A signed-in member selects an eligible workspace and project and authorizes a registered application for listed purposes. Show the account, project, app, requested operations and expiry before consent. Bind the verified issuer and subject (or Tesbo's authenticated member identity) to the stable Tesbo member ID through the trusted identity owner. Account linking across issuers or clients requires a verified link. A matching email, user-entered name, host workspace seat or request argument cannot link accounts. In an application with multiple signed-in seats, establish the delegation for the acting seat on each call. If the host cannot provide a verified per-member binding, classify its work as shared.
2. **Roles at decision time.** Intersect current organization and project membership, operation-specific native capability, grant scopes/tool allowlist, project settings and plan restrictions, and any object/transition rules. Bind the exact resource and tenant before reading Skills, issuing a receipt or disclosing a target. Record the authorized operation and effective role(s) in its receipt. Keep QA lead, BA, developer, project owner, task assignee and content reviewer distinct where they refer to a persona, membership role, assignment or actual decision. A role requested in a prompt has no authority. No new workspace RBAC taxonomy is required to represent stakeholder views.
3. **Member-delegated machine.** A personal delegate can submit an unpublished candidate under the member's current stage permission when supported. A receipt says “Client C submitted revision R under Alice’s grant.” That establishes delegated authority and the authenticated client or credential. An unattended agent using that grant does not prove Alice was present, typed the text or reviewed the result. One member using two clients retains one accountable member ID and two grant/client histories. Two members using the same client retain two member IDs and independently revocable grants.
4. **Shared integration and service workloads.** A shared secret establishes possession and the issuer recorded at issuance. It may serve approved read or preview use. A named-attribution-required write must stop before staging unless the request has independently verified member delegation. A project may explicitly authorize an identified service workload to stage as a service where that workflow accepts service provenance. Give the workload its own stable actor, project grant, purpose and limited actions. CI may supply a provider-verified run or trigger ID. A service maintainer, commit author and build trigger each receive their own label and confidence level. A schedule may legitimately have no human initiator. Updating a maintainer never reassigns historical work.
5. **Human decisions.** A trusted interactive session must bind a decision to the exact object, target revision, selections and approval capability. If an existing transition requires independent review, compare the verified reviewer to accountable contributors on that revision, including delegated contributors and subsequent editors. Multiple tokens or clients belonging to one person do not satisfy independent review. Unknown contribution must not satisfy a policy requiring proven independence. Where self-review is permitted, record it truthfully. Applying a selected proposal into Draft and approving the official artifact remain separate native operations.
6. **Gateway and queue boundaries.** If a client, gateway or worker forwards work, propagate a server-issued reference bound to purpose, project, source member or workload and attempt. A gateway's service credential, another user's bearer, user ID in a job body, MCP session ID or client-supplied agent name cannot confer delegated membership. Recheck current authority after queue waits and at the native write transaction, including scope reductions, membership removal, grant revocation, project archival and job cancellation. Preserve the historical requester if the active executor changes. If no trusted propagation is available, report the workload and the missing attribution.
7. **Least-privilege fallback.** While personal delegated stage is unavailable, an eligible member can read authorized context with their own approved read credential and use a supported signed-in native authoring path for a new human-submitted revision. Preserve any known external source as reported provenance and apply the same native Skill and review gates for governed work. If that surface cannot enforce the required policy, keep it an unpublished draft or return the explicit unavailable state. No role promotion or copied manager credential is needed.

The project-owned client allowlist and individual consents serve different cardinalities and administrative purposes. Keep the existing limit on named legacy credential entries until capacity policy is deliberately changed. For delegated mode, model one approved client with many independently indexed member/project grants. Use cursor pagination with stable ordering for authoritative history and consent lists. Surface filters, truncation, revocation/expiry state and last observed activity time with correct scope. Never infer active sessions from grants, or physical presence from last use.

## What to record and what people see

The native domain transaction writes its revision and mandatory activity or receipt together. Append corrections to an original event, link the superseded revision and preserve the evidence retained under project policy. Reuse case versions, Tasks activities, native save events, approval records, execution evidence, project audit and available outbox projections. A new global “author” column or a parallel approval database cannot represent the relationships below.

| Fact | Minimum durable reference or evidence | Presentation and handling |
| --- | --- | --- |
| Who authorized and produced | Internal tenant/project IDs, origin kind, verified accountable member or service if available, actual tool/client/workload, non-secret grant reference and authority revision or equivalent. Separate issuer, delegated subject and verified human initiator where those differ. ## Retries, contention, revocation and privacy

- **Recovery.** Preserve existing producer-scoped keys for legacy history. A retry by the same authorized producer of the same request and digest recovers the existing receipt. Changed content under that key conflicts. A second member or a rotated credential cannot implicitly inherit another producer's receipt. Carry explicit task/proposal and stable logical operation IDs for a deliberate continuation. Reauthorize target access and handoff permission, compare the exact prior revision and record the new actor/attempt. If a lost response cannot be recovered under current authority, return an authorized recovery path or deny without revealing the original. A duplicate-content warning is advisory and cannot merge independently intended cases.
- **Offboarding and races.** Revoke only the selected member's grant where policy permits. Disabling the project client takes effect across its grants. Stale sessions, cached tool catalogs and queued jobs cannot retain write authority. Recheck after obtaining the domain lock so a revocation that committed first wins. A successful write that committed first keeps its receipt even if future reads are denied. Existing drafts remain accessible to eligible project reviewers for explicit reassignment. Never silently continue as the owner, service or next assignee.
- **Retention and observability.** Store the smallest necessary trusted references. Exclude bearer values, refresh secrets, raw external subjects where an internal mapping suffices, prompts, raw headers and full artifact copies from ordinary audit or analytics. Restrict account mappings and sensitive before/after data to their native owners. Apply project retention, export, deletion and legal-hold controls through the responsible data owner. For role/retention changes, preserve permitted decision and correlation evidence or display explicit expiry/redaction. An audit lookup, export or analytics aggregation must enforce its own project/object access. Do not use connection history to publish a project-wide roster or per-member presence telemetry by default.
- **Durability.** Attribution-required mutation and its domain receipt must commit together. A projection outage can delay activity/search/report visibility only if the durable source survives and projection replay deduplicates. On audit/receipt failure, roll back the protected change. A denied attempt can emit a separate minimized security event under project policy. It creates no domain success receipt. Metrics distinguish denied staging, stale review, unknown/shared producers and delayed projections without collecting member identities as metric labels.

### Following one contribution across revisions

The [versioned collaboration contract](mcp-change-workflow.md) defines the base, current and proposed values, stable operation/step identity, contributor lineage across reconciliations, protected review, and compensating revisions. Attribute a previous case snapshot only to the degree its evidence permits. The migration stores the old snapshot and the new row’s updated_by, which may carry over on dependency invalidation. Naming the person responsible for a transition requires a correlated authenticated event. Naming an earlier field author requires its own contribution evidence.
