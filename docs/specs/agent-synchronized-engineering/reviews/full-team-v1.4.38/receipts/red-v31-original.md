## 2. Reconstructed problem and premise challenge

A useful Tesbo result is a trustworthy decision that a person can act on: understand what is expected, know what was actually observed, identify a relevant gap, prepare a useful native case or other record, preserve human judgment and recover safely when work changes or fails. The required reality has several independent dimensions: expectation authority, observed source, inferred relationship, authored case, accepted mapping, exact attempted execution, evidence availability and current applicability. One status, graph edge, model confidence or green indicator cannot carry all of them.

I tested the premise by removing each product label. Without “AI graph,” the remaining job is permissioned explanation and comparison over existing source, expectation, case and evidence owners. Without “Skills Library,” it is durable reusable guidance plus controlled version/assignment decisions. Without “Change Packet,” it is a navigable projection of the native changeset, operations, impacts and attempts. Without “learning,” it is attributed correction history and a separately evaluated change proposal. None of those names by itself requires another product authority.

The proposal survives this challenge because it explicitly permits ordinary manual work, deterministic checks, existing methods, no change and unresolved outcomes. A source-free manual QA task is a legitimate first-class sibling of a repository-driven analysis. The specification must preserve that sibling through implementation: repository connection, AI provider credit, formal model authoring and automation are not prerequisites to writing a defensible manual case or retaining an authorized observation. R-ASE-40/41/47/48, ASER-C01–06 and the existing I3-Q exit provide this contract; an attractive source-to-graph demo cannot satisfy it alone.

The largest remaining sufficiency uncertainty is empirical: will bounded reasoning identify consequential missing tests with stronger oracles and acceptable human effort across differing applications? The pack contains methods and planned comparisons, not measured Tesbo effectiveness. The candidate's held-out evaluation, legitimate no-change outcomes, separation of method/model/tool effects and non-compensating authority constraints are appropriate obligations. They are not results. A lower test count or repeated fluent explanation cannot close that uncertainty.

## 4. Additional findings from the cold source pass

### TESBO-GS-R01 — Generated-case origin is reused as current model applicability after semantic mutation

**Severity:** Major. **Category:** Invariant / Spec-Code-Drift. **Status:** Open. **Evidence level:** directly inspected source mechanism and conceptual trace; not runtime-reproduced. **Scope:** source419 Model Studio integration, not a claim that the candidate lacks the governing requirement.

**Finding.** The generation path records model revision, path digest, case ID and element IDs, but no relied-on case semantic revision in `mbt_generated_cases`. Dispatch builds eligibility from generated records and explicit links. Only explicit links enter the `mappings` collection checked against the current case edit revision. Generated-only cases have an empty collection. Once a materially edited case is approved again, it can pass that check while retaining the old generated path and element IDs. A new explicit link also adds to the generated element set; it does not by itself retire the old generated attribution.

**Source support.** In [model-studio-repository.ts](sandbox:/workspace/scratch/40f0abd3bdbc/source419/Tesbo-Backend-Nest/src/behavior-graph/model-studio-repository.ts), `createCasesFromPathsForUser` inserts generated provenance around lines 421–428; dispatch reads and unions it around 617–667; current-case checks and `changedMappings` occur around 688–726; the run manifest retains the union around 762–780; `observedByElementFor` groups native results by those manifest elements around 907–935. V153/V154 retain generated provenance without a case-revision field. [model-studio-runs.spec.ts](sandbox:/workspace/scratch/40f0abd3bdbc/source419/Tesbo-Backend-Nest/src/behavior-graph/model-studio-runs.spec.ts) explicitly sets `generated = false` in its changed-mapping test. [model-studio-runs.db.spec.ts](sandbox:/workspace/scratch/40f0abd3bdbc/source419/Tesbo-Backend-Nest/src/behavior-graph/model-studio-runs.db.spec.ts) tests changed explicit mappings after reapproval. These tests are source evidence, not executed receipts or an exhaustive assertion of absent coverage.

**Counterexample.** Generate case C from accepted model r1's transfer-success path. Edit C's actions and expected results into a different denial/recovery scenario and approve that new case definition through the legitimate native case workflow. Leave C without an explicit model-case link. Dispatch r1 using C. The inspected mechanism checks current case approval but has no original generated-case revision to compare; it carries the original generated element set into the new manifest. An explicitly reviewed replacement relation to different elements can coexist with, rather than replace, that old origin attribution.

**Impact.** Case lineage is true historical evidence, but it is insufficient evidence that the current assertion still tests those model elements. A graph reasoner or reviewer can receive a fresh native run and exact occurrence together with stale element applicability. Exact occurrence capture solves which run result was observed; it does not solve whether the case still belongs to the original behavior mapping. The source correctly says `coverageAssertion: none` and that rollups are not model conformance. I therefore do **not** report an executed false conformance pass. The integration risk is accepting origin as current semantic membership when the proposed graph/coverage consumers need a reviewed relation.

**Recommendation.** Extend the existing relationship/model owner to distinguish immutable generated-from lineage from currently accepted applicability. Pin or independently accept the relevant case semantic basis before relying on it; an edit should stale the affected relation without erasing origin or historical runs. A valid alternative is to retain origin strictly as provenance and require a separate current accepted mapping for model-governed selection. Ordinary native case/run work can remain available according to its own policy. Do not rewrite older attempts or create a second mapping store.

**Falsifiable closure.** Extend the existing MBT-AC-34/35 and ASE-INT-11 allocation and native tests with the generated-only mutation/reapproval path, plus generated-and-explicit mixed lineage. Before a fresh accepted relation, the model-governed operation must refuse or expose unresolved applicability according to its declared contract, with no false current attribution. After an authorized fresh relation, only the appropriate current elements inform current reliance; original lineage and old run manifests remain unchanged. Include an unchanged generated case that remains valid, so the fix does not reject legitimate reuse indiscriminately.

### TESBO-GS-R02 — Mapping mutations can outlive the authority check made before a serialization wait

**Severity:** Major. **Category:** Boundary / Invariant. **Status:** Open. **Evidence level:** directly inspected source mechanism and conceptual concurrency schedule; not runtime-reproduced. **Scope:** current link/unlink paths; broader sibling sweep remains required.

**Finding.** `linkCaseForUser` and `unlinkCaseForUser` call `access()` before entering their transaction. Inside, they can wait on model and/or case locks and then insert/delete mapping rows without calling the existing final transactional authority check. This differs materially from model approval and case generation, which call `requireCurrentProjectAuthority` after their domain serialization waits. The access check is request-memoized and does not hold membership/workspace authority through commit.

**Source support.** The same repository's link/unlink methods are around lines 470–550; protected sibling calls are around 309 and 397. [legacy.service.ts](sandbox:/workspace/scratch/40f0abd3bdbc/source419/Tesbo-Backend-Nest/src/legacy/legacy.service.ts), `requireProjectAccess` around 4010–4032, uses request-scoped cached access; `requireCurrentProjectAuthority` around 4035–4046 explicitly bypasses that cache and locks the relevant project, membership, organization and active-workspace rows through commit. The model controller delegates directly to these repository methods. The global [API token guard](sandbox:/workspace/scratch/40f0abd3bdbc/source419/Tesbo-Backend-Nest/src/auth/api-token-rest.guard.ts) checks before handler execution, and [project write-lock guard](sandbox:/workspace/scratch/40f0abd3bdbc/source419/Tesbo-Backend-Nest/src/plan-limits/project-write-lock.guard.ts) supplies a plan check, not transactional membership retention. [DatabaseService](sandbox:/workspace/scratch/40f0abd3bdbc/source419/Tesbo-Backend-Nest/src/database/database.service.ts) wraps the provided function in BEGIN/COMMIT; it does not add authority validation. Inspected link/unlink DB tests cover archive ordering, not the same membership-revocation schedule.

**Counterexample.** An authorized user starts linking a case while another transaction holds the relevant model or case row. The outer access check succeeds; the operation waits. An authorized administrator removes that user's project membership, or the applicable workspace authority changes, and commits. Release the domain lock. The inspected link path has no post-wait membership check before INSERT. The unlink counterpart can likewise proceed after its earlier authority becomes invalid. This schedule is a source-derived hypothesis to reproduce in a disposable database, not an allegation of observed exploitation.

**Impact.** A revoked participant can still affect the trace relationship after current authority has ended. Even where links are proposals rather than approvals, unauthorized mutation violates the stated native-owner boundary and changes information later consumed by selection or review. Prefixing the route with the right project or using one transaction does not make a stale pre-transaction check current.

**Recommendation.** Reuse the shared native authority check at the authoritative mutation boundary after waits and preserve the required locks through commit; retain feature-specific capabilities at their native owner. Include all applicable entrances, not only the UI route. Sweep save/archive and other sibling mutations for the same pattern rather than assuming they are covered by approval's correction. This recommendation is an extension of the current authorization owner, not a new policy engine or a newly invented human role.

**Falsifiable closure.** In the existing Model Studio DB/API suite, hold the domain lock, let access succeed, revoke membership or change applicable workspace authority, release the lock and assert refusal with unchanged mappings and no unauthorized native effect. An authorized concurrent case must still succeed. Also test the opposite ordering: when the writer legitimately holds authority through commit, revocation must serialize rather than retroactively rewrite history. Canonical MBT backend rules, R-ASE-18 and ASER-C03 already require current transactional authorization; allocate this witness to existing owner work.
