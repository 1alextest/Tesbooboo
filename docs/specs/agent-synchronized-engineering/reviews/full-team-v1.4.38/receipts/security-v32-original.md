## 1. Threat-model delta

This proposal connects project source observations, native QA records, external agents and imported testing methods through typed graph relationships and an explicitly governed instruction resolver. The valuable assets are private source/evidence, truthful original reports and actual performer identity, exact human publication decisions, and the distinction between readable content and effective governing instruction. The new risk is that a legitimate read, delegated credential, historical approval or inferred graph link acquires authority it did not receive; the proposal generally states the correct boundaries, while the present implementation still has admission gaps at source entitlement, machine-result provenance, final revocation and legacy AI-context composition.

### Scope and alternatives considered

The desired outcome is useful, explainable QA work from existing native records and source evidence, including human manual work and an external agent's own driver, with exact original reports and selective human decisions. It does not require a second authorization service, a new graph database, a new testing platform or unrestricted autonomous execution. A bounded deterministic graph reader plus human-selected method is a valid initial implementation; adding an agent must demonstrate benefit without weakening that baseline. Keeping the current workflow unchanged avoids new activation machinery but does not satisfy the proposed immutable provenance and governed-method guarantees. An intentionally shared source registry is a valid alternative to per-project source grants only when its policy, contents and positive/negative tests demonstrate that every eligible destination may read those sources; this review does not assume such a policy exists. See `C/03_TECHNICAL_DESIGN.md:1384,1579–1661` and `C/06_IMPLEMENTATION_AGENT_BRIEF.md:550–602`.

Security-1 is conditional because a deliberately shared source catalog may be entirely legitimate; there was no inspection of production registry contents. `implementation-source-verifier.ts` returns source inventory with content hashes and proposed concepts, so this receipt does not inflate the inspected output into confirmed arbitrary file-content exfiltration. The global checkout map and path/pin checks are useful integrity controls, but answer a different question from source entitlement.

Security-2 is a concrete compatibility problem for the new trust claim. The legacy handler explicitly documents attribution to the token owner; `updateExecution` writes that user into `executed_by` when status changes. Its users-FK constraint explains the implementation choice but does not establish the actual performer. The ordinary activity counter likewise intentionally counts a delegated mutation as user engagement (`B/src/auth/activity.middleware.ts:12–26`); that metric must not be promoted to human-assent or execution evidence. I found no justification for rewriting old records as known human or machine history.

Security-3 is deliberately narrow. Proposal staging **does** revalidate the current token and MCP grant inside its transaction (`B/src/legacy/legacy.service.ts:15603–15614`) and preserves producer provenance. Source capture checks current membership, current binding and pin stability, but accepts only `userId` downstream; none of those checks can determine whether a particular token or named MCP grant still exists. No race was run, and no claim is made that revocation can retroactively undo a permitted external action already completed before its fence.

Security-4 does not assume that putting data in a system message guarantees model obedience, nor that every retrieved document is malicious. The issue is that the legacy DTO/composition does not itself preserve the new distinction between authorized reference content and assigned governing instruction. AI-memory-specific reviewed-content filtering is a useful narrower defense, not proof for the full proposed Skills lifecycle and all ordinary reference readers.

## 4. Attack chains

The following are **reasoned chains, not executed exploits**. Their severities describe the end state, not a maximum copied from individual links.

1. **Conditional HIGH — private source metadata disclosure:** eligible destination owner learns an allowlisted key/repository → binding accepts global registry membership as sufficient → source scanner validates and hashes those bytes → graph history faithfully stores the result in the attacker's permitted destination. Correct pin verification strengthens evidence authenticity but does not supply missing source entitlement. This chain disappears if explicit global sharing covers the source and destination.
2. **HIGH within the delegated project — evidence laundering:** permitted reference content influences an agent's conclusion → a write-authorized agent records `Passed` through a legacy execution tool → native result stores issuer as performer without the proposed independent original/attempt provenance on this path → downstream readers may rely on it as stronger evidence than the submission warrants. The dangerous composition is provenance loss and later reliance, not proof that this review induced an actual model or UI to misbehave.
3. **HIGH within the formerly authorized scope — post-revocation completion:** capture passes entry grant → operator revokes the credential/grant during source work → downstream capture still has issuer membership and unchanged source binding → history commit/response proceeds without the credential being available to recheck. A regression must distinguish revocation before the final fence from a completed earlier action.

No independently supported chain to cross-organization takeover, arbitrary host command execution or unauthenticated bulk exfiltration was found in the inspected paths. That is a coverage statement, not proof such vulnerabilities are absent elsewhere.

## 6. Residual risk

Even after the above tests pass, a permitted actor can submit false observations; immutable provenance establishes who asserted what, not that a target was truly exercised. Human manual observation remains legitimate without a machine receipt. A genuine source pin proves selected bytes, not expected behavior, complete coverage or release fitness. Approved guidance can still be poor or conflicting, so independent evaluation, rollback generations and human assignment remain necessary. The candidate explicitly preserves these distinctions (`C/03_TECHNICAL_DESIGN.md:1603–1661`).

**S5 secret and credential accounting:** inspected API tokens are randomly generated, stored hashed and exposed raw on creation; their inspected lifecycle is revocation/deletion rather than a built-in expiry, while named MCP grants can have expiry (`B/src/auth/api-token.service.ts:91–177`; `B/src/mcp/mcp-access.ts:25–63`). This is not a claim that every deployment must impose the same lifetime. Issuer membership, token scope and grant scope must remain separate; browser session lifetime, actual production secret storage/rotation, provider credentials and backup access were not audited. Project/project-token confinement was inspected, not all connector-specific delegation.

**S12 privacy and provider risk:** Langfuse is disabled without its required configuration and cloud use requires explicit opt-in. Its inspected masking covers particular key/Bearer patterns in input/output, not every secret or metadata field (`B/src/observability/langfuse.ts:32–89`). Provider request assembly still needs the candidate's purpose, recipient, minimization, retention and revoked-access controls demonstrated on actual payloads. No outbound traffic, real secret or production data was used here.

**S8 abuse and resource risk:** repeated legitimate captures, large graph fan-out, expensive provider/evaluator loops and repeated denied capability probes can consume resources without crossing a tenant boundary. The source scanner has concrete file/tree/byte/concept bounds; these do not establish queue fairness, aggregate per-tenant budget, cancellation behavior or backpressure (`B/src/behavior-graph/implementation-source-verifier.ts:30–34`; `C/05_IMPLEMENTATION_BACKLOG_AND_TEST_PLAN.md:1533`). Named measured limits, retention/erasure policy, root recovery authority and delivery ownership remain deployment gates, not assumptions that there are no users. No marketplace/payment fraud or CVE/dependency audit was performed.

All-reader revocation, cached derived metadata, source-sharing exceptions, upload/artifact storage, full UI rendering, network egress, script sandboxing, recovery after partial failure and actual deployed DB immutability still require integrated evidence. This receipt does not certify those surfaces based on specifications or isolated helpers. A preserved historical record may remain legally/operationally retained while read access is revoked; retention and current accessibility must not be conflated.
