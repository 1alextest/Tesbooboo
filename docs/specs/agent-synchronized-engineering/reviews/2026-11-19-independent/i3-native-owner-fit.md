## 3. The complete reachable native journey

This is the intended producer chain to implement after the relevant admissions. Names such as `create_test_task` and `submit_test_report` are canonical **proposed contracts**, not a claim that this source exposes them. They should extend the existing MCP/controller/Legacy owner seams, with one implementation per action shared by transport. [C04 §§3–5; S01,S02,S06]

1. **Create the task without a case or AI key.** ChatGPT or the native composer supplies authorized project, exact user objective, typed target/environment, permitted actions and success/blocker criteria. Persist the task intent and prompt revision. Optional cases, changeset, provider requirements and source/build references are typed links, not required parents. Creation must not call `aiGenerate`, allocate a model key, launch generation, open a Run, or produce native Draft cases. Assignment remains manual pickup as already chosen. [C01 FR-001–009; C02 §§2–5; C06 original demonstration]
2. **Assign a specific installation and claim a frozen revision.** An authorized human/work coordinator explicitly selects one registered executor installation. The installation uses its own current project credential and claims that assignment with compare-and-set. Claim returns the exact prompt revision plus one attempt/fence. A second installation with the same vendor/model label cannot claim it. Driver capability and actual target access are checked independently of Tesbo authorization. [C01 FR-010–017; C04 task contracts]
3. **Execute externally with truthful visibility.** The executor uses its own Chrome/Playwright/Appium/CLI and network access. Carry settled PD-02 into the exact prompt/claim scope: web HTTPS origin/path/action allowlists and read-only/non-destructive defaults; separate explicit per-task authorization for login/IdP redirects, tabs, downloads, outbound transfers and target mutations; typed safe policies for non-web adapters. Reject unapproved redirects and request clarification. Actual target/role/account and credential-delivery access comes from its authorized target/security owner; credentials do not go in prompts. Tesbo records authenticated messages, receipts and evidence it actually receives; it does not claim to observe every local tool action. Heartbeats renew only a valid current lease; progress validates the current attempt/fence and never resumes expired work. Lease expiry/cancel revokes later server writes, but cannot prove an external browser or device stopped. Unknown completion stays unknown until evidence/reconciliation. [C00 P-06/P-15, PD-02; C04 task tools/ASER-C01; C07 ASER-UX01]
4. **Reserve, upload, finalize and read the original.** Reserve a report for the exact task/prompt/attempt; upload original bytes and evidence to current storage under a pending binding; verify actual byte digests, completeness and policy; atomically finalize the immutable manifest with current authority/fence and audit. Reservation or upload is not `REPORTED`. A truthful blocker report can finalize without a fabricated execution. Repeated finalize reads its receipt; it cannot replace the primary with a new idempotency key. [C01 FR-018–025; C02 lifecycle; C04 report contract]
5. **Independent analysis reads originals.** A separate permitted analyst, including ChatGPT without a Tesbo AI key, fetches the entire original report and relevant evidence through the authorized byte reader. It records exactly which reports/artifacts/revisions were read, which failed or were inaccessible, and the difference between observations and inference. Each persisted analysis revision is immutable; report bytes remain unchanged. The analyst may stage proposals but acquires no result-reporter, reviewer or apply authority by reading. [C01 FR-026–037; AC-014; C03 report/analysis contracts]
6. **Clarify or request a NEW retest.** A clarification appends a question/answer and explicitly resumes under current authority; material instruction change creates a prompt revision and a newly fenced attempt. A retest creates a new linked task, prompt, assignment/attempt and primary report. It references prior report/finding/proposal revisions, preserves earlier evidence and states what is being rechecked. It does not reopen or overwrite the original task/report. [C01 FR-009; C02 retest/clarification; C04 `create_followup_task`; C05 QA-135–138]
7. **Review exact operations in the native surface.** The analyst or human synthesis creates source-neutral shared staging with stable logical operation IDs, immutable submitted revisions, exact native targets/base revisions/postimages/dependencies and evidence/Skill context. Humans edit, reject, request changes, accept copy-only work or approve selected native writes. A material edit invalidates the affected prior decision. Decision and application are separate facts. [C01 FR-027–037; C04 ASER-C02/C03/C05]
8. **Apply only the selected dependency-closed native set.** Current authorized human intent is bound to the exact selected manifest. A single native transaction writes accepted cases/results/Bugs or other supported native domains, mandatory audit and receipt. Readback navigates to exact native IDs/revisions and still shows unselected/rejected/pending work. An external tracker copy remains copy-only unless separately authorized provider action exists. Publication does not imply semantic case approval, actual execution, task closure or release. [C01 AC-005/015/018/019; C04 ASER-C03; W-P]

### Alternate and recovery branches that are part of the same journey

| State/event | Required server/UI consequence | Forbidden inference/effect |
|---|---|---|
| Manual primary for DRAFT/READY/ASSIGNED; no active lease | Human import provenance; exact task-version CAS and explicit manual adoption; close unclaimed assignment as manually fulfilled; preserve claimed author separately from authenticated submitter. | Fabricated executor/attempt, implicit cancellation or pretending Tesbo observed the external actions. |
| Manual evidence while an executor is active | Authorized supplemental/historical evidence linked to its true source; preserve active authority. | Completing or replacing that executor's primary report. |
| Lease expires, actor revoked, task canceled, final response lost | Current authority is invalid for further primary effects; retain historical state; read authoritative receipt after lost ACK; explicit reassign/resume creates valid new authority. | “Local tool stopped,” auto-resurrection, old fence reuse, or blind retry that starts another action. |
| Bytes incomplete, digest mismatch, scan unavailable/quarantined | Keep pending/quarantined with recoverable reason and owned cleanup; task does not advance to reported. | Passing length-only verification as integrity, silently dropping evidence, or rendering quarantined active content. |
| New report conflicts with prior analysis/decision | Preserve both originals; append analysis/correction and identify affected exact decisions/obligations as stale or requiring new review. | Editing the earlier receipt or automatically rewriting approved requirements to match the observation. |
| Mandatory domain adapter/authority is unavailable | Stage/read what is permitted, show the actual blocked selected effect and owner. Reject an unsupported atomic selected set before writes. | Silent partial native apply or marking all seven domains complete. |

The manual and lifecycle rules above come from C02/C04; they do not reopen PD-01/02/05. Different transport does not change actor truth.

A surviving E/X/C is a reason to reject a separate platform, not proof that an arbitrary new child table is already approved. [R-Red §5; W §5]

### 5.1 Task representation A versus B — decision ready for W-OWN

**A: typed extension at the current `ai_generation_requests` root.** A genuine discriminator would separate legacy generation, source-neutral proposal and external work meanings. External work must have its own state and parent/child relations; it must not overload `provider`, `agent_name`, `generated_payload` or `task_status` to pretend it is a generation. Its creation bypasses AI allocation and `processZyraTask`. External work and its many proposal batches must have distinct logical IDs even if a shared physical root eventually represents them. Required evidence before admission: all listed readers/writers below filter by supported kind; legacy routes reject incompatible kinds before side effects; generation counters/history, archive sweep, chat/pending pointers, feedback and close/save cannot act on external work; requester/project retention rules are explicit. Benefits: least disruption to existing task links/navigation/authorization placement. Cost: expanding a heavily generation-specific aggregate and auditing every consumer. **Do not implement this as `provider='external_task'` plus fake zero drafts.** [S01,S02; V8/V35/V107/V157; §8]

**B: extract a common native work identity/envelope, retaining generation and shared proposal owners as typed dependents.** This can separate incompatible state/custody cleanly while preserving one native Tasks responsibility. It requires an admitted canonical ID/compatibility mapping, no duplicate writable work rows, all legacy links/resolvers migrated or adapted, and explicit lifecycle/deletion ownership. Benefits: fewer generation predicates leaking into new external work. Cost: broader migration, more relations/joins and a dangerous opportunity for two competing task truths. It is not a new top-level task product or an assumed `TasksService`. Physical record shape and whether an additional root relation is justified are unresolved W-OWN choices, not authorized by the conceptual wording in C03 §18.1.

**Recommendation for admission:** compare A first against the complete consumer census because it preserves the current root and entry placement. Reject A if its typed constraints cannot prevent accidental worker/review/counter/deletion coupling without broad fragile predicates; then assess B against explicit old-ID compatibility and unique ownership. Select neither before Blue/Red review and White's concrete W-OWN decision. The unique semantic owner is the existing native work responsibility; unknown consequential behavior in either option blocks allocation. The alternative “one external task equals one current proposal row” is rejected because multiple report/analysis/proposal rounds and independent completion cannot be expressed truthfully. [W-OWN; R-Blue/R-Red]

### 5.2 Evidence representation: precise extension choices

**Preferred candidate to review:** task-owned immutable report envelope/manifest composed with existing attachments and StorageService. The manifest records exact original report blob and evidence references, not a second blob store. Compare (a) typed immutable child facts at work owner referencing attachment IDs, and (b) an admitted immutable-envelope extraction reused from governed snapshots plus attachment refs. An ordinary KB document fails because autosave, draft permissions, indexing and AI-memory review have different consequences. A native execution report fails case-free intake. A bare attachment fails report primary uniqueness, attempt/fence attribution and manifest finalization. An untyped `activity_log`/`context` JSON append fails unless the actual DB/API guards can independently enforce identity, immutability, cardinality, access and cleanup. No table-per-noun conclusion follows. [S07–S09,S12; C03 report design; W-E]

The required state is `pending → finalized` or policy-defined quarantine/rejection/expiry, with immutable finalization. The byte uploader is not an alternate report authorizer. `StorageService.put` can overwrite a key, `verify` checks length, and `getBuffer` reads actual bytes. Therefore reuse requires server-assigned object identity, actual server digest verification, and a write-once/finalization boundary that prevents object replacement after verification. Candidate mechanisms include immutable/versioned objects or storage-level conditional creation plus application guards; actual local and S3 guarantees must be proven before choosing one. A client hash is an input to compare, not evidence that bytes arrived. [S08]

Avoid holding a native transaction across slow upload/scan. Reserve and upload first; verify the exact immutable object identity, then commit the manifest/authority transition/audit. The selected mechanism must close the verify-to-finalize replacement race and the cleanup-to-finalize race. Retry finalization compares the exact manifest and reads its receipt. Pending quota reservations and cleanup are owned obligations; finalized or held evidence must not be deleted by the existing attachment deletion path. Private reads recheck current parent/project permission and quarantine state, including previews/downloads/range responses. Reusing a presigned URL alone does not prove immediate reauthorization. Inline markdown remains original bytes plus a separate safe rendering, with no newline normalization of the original. The actual MCP/client capability must support complete text and the authorized binary retrieval path; a metadata-only response or a client unable to retrieve the binary is explicitly unverified, never a successful evidence read. [C03 evidence lifecycle; C04 artifact reader; S08,V115]

### 5.3 Proposal representation: extend the current safety core

Keep the current source-neutral staging location and native case writer. Add logical operation identity and immutable submitted revisions at that owner, with exact per-operation native base and dependency references. Preserve V157's snapshot-after-lock check, idempotency provenance and append-only save-receipt protection. Extend receipt/commitment uniqueness so a committed logical operation cannot replay under another proposal revision or key. Aggregate progress derives from decisions and commitments; no new mutable completion authority is needed. A current `proposal_revision` counter/digest and mutable remaining array alone do not preserve all prior submitted revisions. Any new persistent representation requires W-OWN review of those exact gaps. [S02,S03,V157; C04 ASER-C03/C05]

## 6. Seven domains in the same native loop

Every change/task context records **requirements, test cases, manuals, policies, tasks/issues, files/evidence and Skills** applicability with reason/source. ## 7. Exact selected native publication protocol

This is a concrete extension of the current case-save path, not a replacement engine. The existing positive controls in `zyraSaveAttempt` are mandatory starting properties. [S03; W-P]

1. Read the exact submitted proposal revision and selected stable operation revisions. The UI shows native before/postimage, field intent (absent/clear/set), evidence, current guidance, target identity and dependencies. Resolve suite/parent/tag/custom-field and candidate-created target references **before** decision; no ambiguous name lookup can expand the reviewed effect at apply.
2. Capture the configured current human decision for that manifest. PD-01 owner/delegated active reviewer is settled; no universal two-person rule is introduced. Trusted `human_session` is already checked at narrow current boundaries, but native Copilot/delegated browser execution must not manufacture interactive human assent. W-A must prove the action-bound mapping before affected enablement.
3. Build a deterministic dependency-closed plan. A selected operation may reference an existing exact native revision or the declared output of another selected operation. Missing prerequisite, unsupported adapter, conflicting writes to one semantic target, undeclared reordering or mandatory blocked authority rejects the set before native writes. An explicit reviewed ordered chain may be supported only if the native planner/manifest defines its intermediate postimages.
4. Start one database transaction. Recheck current membership/capability/consent and relied-on guidance after lock waits. Lock the proposal and target/dependency rows in a defined deterministic order; preserve existing suite-tree serialization and fresh snapshot checks. Current machine grants never stand in for human decision authority.
5. Look up logical operation commitments first. An exact committed retry returns the existing receipt. Different manifest/actor/decision reuse conflicts. If nothing committed, validate expected proposal, targets, dependency revisions, selected decisions and approved native definitions where results are proposed.
6. Invoke **same-client native adapters**, not existing public methods that open their own transaction or call remote providers. Cases can reuse/extract the current with-client writers. Bugs need the current `createBug` transaction body extracted and audit included. KB versions/updates and result correction need their own equivalent proof. Keep each native owner's validation, ID allocation, revision and semantic rules.
7. Persist exact native IDs/revisions, stable operation commitments, mandatory audit and apply receipt in that same transaction. Audit/receipt failure rolls everything back. Retain original report/attempt and all prior decisions. No case, execution or Bug effect escapes on a failed selected set.
8. After commit, derived caches/search/embeddings and permitted notifications are invalidated/dispatched from recoverable obligations. The current `zyraSave` calls cache/index/comment/notify helpers after commit; that source fact is not evidence of general exactly-once delivery. For new operations enumerate which post-commit effects are necessary and reconcile lost dispatch/ACK without reapplying native mutations.
9. Read back the receipt and exact native records through current authorization. A timeout before response is “outcome unknown; read receipt,” not “failed; rerun.” Status derives from terminal operation dispositions: all applied → MERGED; all rejected → REJECTED; all withdrawn → WITHDRAWN; mixed/copy-only terminal → COMPLETED; any unresolved operation keeps the proposal pending. Work/evidence/release truth remains independent. [C02 proposal lifecycle; C04 ASER-C03/C05]

**Important existing side effect:** `queueZyraTicketComments` uses project auto-comment settings and connected-provider checks, inserts a deduplicated integration comment record and starts delivery after case save. Preserve that historical behavior for its authorized legacy path. Do not automatically inherit it for raw reports, staging, retest, copy-only issues or new native operations. The new operation manifest and existing provider policy must make any intended external effect reviewable; no external send occurs in this design task. [S03 `queueZyraTicketComments`:1983; C00 AD-08]

**Partial staging is different from atomic apply.** Composite staging can record committed/failed/not-attempted/uncertain items in its existing-owner request journal. Exact replay reads known outcomes; explicit resume uses the original manifest, expected journal revision, current grants/guidance and a new resume attempt, only for eligible unresolved items. Changed intent requires new proposal revision. This does not permit partial selected native publication or retrying a committed logical operation under another key. [C04 ASER-C05]
