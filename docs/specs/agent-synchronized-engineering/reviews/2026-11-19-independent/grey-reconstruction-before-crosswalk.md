This checkpoint was written after reading the unchanged Grey charter/orchestration/portability/evidence policies, Tesbo AGENTS/CLAUDE, the original v1.4.28 workflow and requirements (FR-001–070 and R-ASE-01–48), original API/technical integration contracts, implementation gates and historical fieldwork. ## User outcome and stage model

A person wants an accountable answer to “what did we change, what was actually tested, what should become our maintained truth, and who still owes a decision?” They may start with a problem and no case, with a regression definition, with a spontaneous code edit, with a policy or documentation correction, or with an incident. Their job is not to complete every module or make every badge green.

The original QA path must remain independently usable: human/analysis client agrees bounded scope → persists an exact task prompt → an explicitly assigned external principal claims a fresh attempt → that principal uses its own authorized driver/target access → original report and actual evidence bytes are admitted → an analyst distinguishes observation from explanation → missing proof causes a linked new retest and a separate report → a human reviews exact operation versions → separately selected native publication changes only the intended official records. Nothing about code synchronization, a native Copilot, a skill resolver, or an optional model replaces this path.

Stages that cannot collapse: intended scope / authorized dispatch / lease / target action / receipt / independent interpretation / candidate / human decision / selected apply / current run eligibility / observed attempt / release decision / deployment observation / post-deploy verification. A useful user explanation is attached to each boundary, not just an internal enum.

## Six executable personas

| Persona | Goal and starting state | Knows / does not know | Constraint and decision criterion | Success / abandonment |
|---|---|---|---|---|
| P1 — solo QA lead | Investigate a new feature; project exists, no official case or Tesbo model key | Knows feature and target; does not know internal graph/model/token vocabulary | Wants an explicit bounded assignment and a reviewable report without buying/configuring an unrelated runtime | Can retrieve originals, request a retest and publish only selected reviewed outcomes; abandons if task creation requires inventing a case or reported success is only generation |
| P2 — returning analysis client | Continue someone else's incomplete report in a fresh ChatGPT/native session | Knows permitted task question; lacks private prior transcript and restricted documents | Task-limited grant; must not infer inaccessible evidence or repair missing records by duplication | Finds exact reports, sources, comments and pending decisions; uncertainty remains explicit; abandons if pasted IDs/private memory are prerequisites |
| P3 — external executor | Complete one explicitly assigned web/API/mobile test from its own accessible environment | Knows exact authorized prompt and its real local capabilities; cannot know server-private ownership or assume cancellation stopped an in-flight action | Intermittent connectivity, expiring lease, existing Chrome/Playwright/Appium driver, no shared machine secrets | Exact claim/report attribution, truthful blocker or observed outcome, recoverable upload; fails if stale attempt continues authoritatively or unsupported driver is labelled tested |
| P4 — bounded human reviewer | Accept one correction and reject another while preserving historical truth | Understands expected behavior and visible diffs; cannot infer hidden side effects of Bug links or “Approved” | May be QA, BA or policy reviewer with different capabilities; uses keyboard and narrow viewport | Sees complete effect/dependencies and exact originals; edit/retest/reject/selected apply work; fails if one action silently changes other result/authority |
| P5 — developer/coding agent | Fix behavior first, then synchronize applicable maintained records | Knows repository diff; must discover independent accepted expectations and correct project | May have no hook, stale catalog, partial sync or no formal model; has propose/read rather than human governance | Reuses existing identities, records seven applicability decisions, proposes justified changes with exact versions; fails if source becomes its own oracle or all modules must mutate |
| P6 — governance/operations reviewer | Restore blocked work, decide a release, and understand a later incident | Knows own authority and visible summary; does not have all evidence payloads or hidden agent actions | Independent skill/policy/release capabilities; provider may be unavailable | Resolves only authorized gates, sees missing proof and surviving work, distinguishes prior candidate success from incident/retest; fails if summary access leaks evidence or “settled” means deployed |

Job labels do not create permissions. The same human can hold several capabilities; a token owned by that human is still a machine credential.

## Initial negative-space questions, before source diagnosis

1. Where does a low-knowledge user find a stalled external task/report in a fresh session if neither client is running? A schema or latest-50 list is insufficient.
2. Can someone accept a valid core result while withholding an unrelated policy/manual operation, without hiding a genuinely required dependency? The selected set and its closure must be visible, not guessed.
3. Can an executor truthfully return failure evidence after its authoring guidance changed, and can a human import it without impersonating the executor? Raw intake and authored inference have different prerequisites.
4. What does Cancel mean when the local browser/device is unreachable? “Authority ended; external action status unknown” is an acceptable boundary; pretending rollback is not.
5. Does the exact set selected for testing survive skip/filter/retry and remain distinguishable from actual attempts? A status/count/linked case is not the user outcome.
6. Can a restricted reviewer understand the next responsible action without discovering private evidence identity/counts? Unknown must stay permission-safe.
7. Which legitimate outcomes are not creation/publication: no change, rejected, copy-only, postponed with authorized owner, unsupported target, blocked evidence, and source-free change? None should need fake records.

## Scope and epistemic boundary

This run can execute G0 artifact simulation and G1 source tracing. It cannot claim browser/UI observation, external client-driver execution, database/queue atomicity, evidence byte transfer or deployed verification. Source-stage proof of a missing reachable method is stronger than a guessed runtime behavior but still not an executed user failure. Existing source mechanisms are diagnosed only after defining each user's expected and forbidden outcome. Formal independent review of Major findings and White gate disposition remain pending.
