## 4. Representation B and the remaining consequential allocations

### B: common native work identity extraction

B is a valid comparison candidate only if it extracts one canonical work identity and leaves typed generation/proposal responsibilities as dependents or compatible views. A new physical relation is not automatically duplicate authority; two independent writable records for the same work truth would be. Conversely, an existing table name does not prevent duplicate completion semantics.

The memo currently names the needed proof rather than supplying the selected mapping. Before allocation, B must show:

1. For every old generation/proposal UUID and TASK reference, the one canonical identity, resolver, project scope and retained history; whether the compatibility path is read-only/adapted and which command owns future mutation.
2. Which existing fields remain generation-specific, which fact moves to common work, and which fact is merely projected. No dual-writable `done`, current prompt, requester or completion authority may be left to eventual synchronization.
3. All affected FKs, trigger invariants, chat/message pending pointers, V157 receipts, integration comments, dashboard/notification routes and row-lock ordering. V135 identity/sequence behavior and old direct routes are material, not a cosmetic migration detail.
4. The old/new mixed-version and rollback behavior after new work exists: stop producers without erasing new reports or turning them into generation, keep old URLs readable, and refuse incompatible writes instead of guessing type or provenance.
5. A bounded extraction reason tied to current invariants. Generic future work, cleaner naming or the bare existence of two use cases does not justify a universal workflow engine.

A valid alternative to a broad extraction may remain a narrow typed extension plus immutable child facts. A valid extraction may be better if it prevents demonstrable semantic entanglement without duplicating work truth. This White review ranks neither; the source-backed Blue/Red delta must challenge both. [M1/M2; C03 §§2–3/18.1; D §5.1]

### Evidence and report allocation — W-OWN-E

The logical report/custody need is established, and reusing StorageService is appropriate. Allocation proof remains incomplete because the actual immutable-object identity and finalize/cleanup coordination are not selected. `put` performs an ordinary S3 PutObject or local `open(..., "w")`; `verify` checks presence/size; `getBuffer` reads bytes; `getAccessUrl` returns an expiring signed URL after the caller's check; `delete` deletes the object. These useful existing operations do not themselves supply write-once identity, digest binding, current-read revocation or report-aware retention. [S5]

The next packet must bind a specific candidate mechanism to both supported storage drivers, or explicitly narrow supported capability before enabling it. It must show: exact immutable object/version identity verified and finalized; reservation/primary uniqueness independent of request key; same-length replacement and old-upload refusal; finalize/cleanup race ordering; current authorization on raw/preview/range/export paths; byte sharing without permission widening; quota consumption/release; and the deletion path for pending versus finalized/held objects. A manifest with a hash field is not proof of those effects. The reader and cleanup owner must be named before report finalization is accepted. Q4–Q7 provide suitable oracles; they still need the candidate-specific mechanism. This is engineering proof work, not permission to invent a storage service, scanner, retention schedule or production policy. [C01 FR-018–025; C04 §§4.3/12; D §§5.2,8,10]

### Installation/authority allocation — W-OWN-I

V58's agents/actors and V65's shared MCP actor are real roots for reuse. They do not yet distinguish two installations of one runtime. The packet must select the native installation/credential binding grain, historical versus current relationships and command ownership, while retaining current project membership/consent. Token issuer, agent label, activity author and assignee cannot be substituted for one another. Bind claim, renew, progress, reserve/finalize, resume/cancel, manual import and historical supplement to their correct authority. Concrete policy evaluation must keep bound project separate from the issuer's UI workspace and preserve genuine revocation denial. Existing root/Skills/human assent policy questions stay at their affected action; raw observation is not automatically governed publication. [C01 FR-010–017; C00 PD-01/02/04/05; S8; D §§3–4,8]

### Proposal/decision/commitment allocation — W-OWN-P

The shared proposal extension is a grounded direction. The packet must choose how stable operation identity, immutable submitted revisions and once-only logical commitments compose with existing V157 receipts. A task must be able to produce several proposal batches without becoming each batch. New decisions must not be backfilled from legacy `done` or saved-count values. Existing exact snapshot/replay is a positive control, not an allegation to erase.

Same-client adapter feasibility must be shown for the selected native set. I independently checked `createBug`: its transaction returns before `logProjectActivity` and notification. MCP `create_bug/update_bug` pass `ctx.userId`, and their native signatures do not receive the new exact human decision. The design correctly includes those aliases in its future governed-publication sweep. The next packet must map both allowed legacy/native reporter behavior and denied analyst publication, preserve result association independence, and make mandatory audit/receipt part of the selected transaction. An unsupported adapter must reject a mixed set before native writes. Tracker-comment and notification behavior needs its own after-commit disposition; copy-only approval cannot inherit delivery. [S6/S7; C01 FR-027–040/049; C04 ASER-C03/05; D §§5.3,7–8]
