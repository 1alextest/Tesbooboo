## 1. Decision and review binding

The intended user outcome is coherent: give an external executor a real QA task, preserve what that executor actually reported, investigate or retest it without overwriting the original, and publish only the native changes a currently authorized human reviewed. The canonical requirements represent that outcome and the broader requirement/case/manual/policy/work synchronization. They explicitly distinguish observation, proposal, accepted expectation, native publication, executed result, and release decision. I did not find a reason to replace the native owners with another agent platform, proposal repository, document repository, execution engine, or release-status store.

**Recommended architecture direction: EXTEND EXISTING SUBSTRATE + COMPOSE.** A few additional identities are justified by invariants that the present owners cannot represent: a case-independent assigned execution attempt with fencing; an immutable original report/receipt; stable logical proposal-operation commitment across revisions; and stable source-binding configuration history. These belong at the named native seams, not in a parallel product. The proposed Change Packet is a projection over the canonical changeset and obligations, not an additional mutable completion owner.

**Readiness:** enough evidence exists to define and implement a bounded, complete original QA round-trip milestone after its explicit authority and migration gates are resolved. There is not enough evidence to freeze the whole integrated architecture, enable every governed writer, call the original loop implemented, or approve UI parity. Most gaps below are confirmed implementation-admission constraints already anticipated by the requirements, rather than newly discovered missing product concepts. A further broad rewrite of the eight files is not the justified next deliverable.

## 2. Independent problem model and journey denominator

The tester has several distinct problems, even when the UI puts them in one task. They must describe a permitted target and the question to investigate; know which actual runtime accepted responsibility; distinguish expectations from observations; recover a trustworthy original report after interruptions; ask a narrower followup or a fresh retest; decide whether an observation should change a reusable expectation, an executed result, a defect or supporting documentation; and see the exact accepted native changes and unresolved work afterward. A useful system also preserves the ordinary human/manual path when no external connection or model key is available.

Changes in source, requirements, documents, assignments, capabilities or evidence can invalidate a decision without changing a convenient `status` field. Accordingly, identity and provenance are part of the user outcome: project, actor, installation, task revision, attempt, source binding/build, definition/criterion revision, evidence bytes, operation revision and human decision cannot be collapsed into task ID plus a report string. Native publication is not proof of an execution; a Bug association is not proof that a case failed; a captured source graph is not an approved expectation; a completed generation job is not completed general work. [C/01 FR-001–048, FR-071–087, R-ASE-01–48; C/04 ASER-C01–06]

## 9. Findings and precise acceptance consequences

These findings identify gates for the proposed implementation. They do not assert that a gated preview is currently exposed in production. “Must-Fix” is scoped to the affected architecture freeze or exposure; it does not mean every row needs a new requirement or a new repository.

### TESBO-QA-B01 — Reconcile the current source delta before freezing the migration plan

- **Severity:** Must-Fix. **Category:** Implementation-Grounding. **Status:** Open for the consolidated handoff; the concrete delta is recorded in this receipt.
- **Finding:** C/03 §18.2 deliberately describes an earlier pinned source: absent P-18 enforcement, status-based new-run admission, insufficient case dependency receipt, and ordinary KB-only history. - **Impact:** Planning from the older account duplicates guards/migrations, weakens the newer semantic receipt path, or counts the newer partial preview as full FR-027–037 completion. Either mistakes actual native owners and rollout risk.
- **Recommendation:** Attach a current-pin delta and reachable writer/reader inventory to the existing backlog, preserving the older pins. ### TESBO-QA-B02 — Stable operation commitment needs a concrete migration from the existing preview

- **Severity:** Must-Fix. **Category:** Implementation-Grounding. **Status:** Open.
- **Finding:** The required stable logical operation identity and immutable proposal revisions are clear (FR-028/030/035; ASER-C02–04). The current V157/E2 implementation mutates `generated_payload`, identifies selected work by array index, removes saved entries, and binds Save to a digest plus selected indexes and suite parameters. Its exact decision replay protection is valuable but does not represent one logical operation committed once across later revisions/fresh keys. Its external stage is restricted to case create/update/archive; suite resolution can still use project-wide lowercased name at Save. The existing row/receipt migration contract is not yet concretely frozen for the complete target.
- **Impact:** Retrofitting a new operation list without preserving old identity can reapply an already accepted change, misidentify remaining proposals, misstate old review provenance, or direct a reviewed item to a different hierarchical destination. It also makes partial-selection retry and corrective work ambiguous.
- **Recommendation:** Extend the existing proposal owner with stable operation IDs and immutable iteration/base/dependency records; bind exact destination/new-target logical references before review; commit a dependency-closed selection with one durable logical commitment and native-ID mapping. Define treatment of existing in-review payloads, prior `save_events`, producer identity and unknown legacy data before migration. Do not backfill invented historical approval/identity.
- **Valid alternative:** Preserve the current preview as a legacy read-only history/explicitly drained pilot and admit new governed proposals only under the new contract. Or adopt old items only through a fresh human-reviewed revision with explicit legacy provenance. Neither requires a second proposal system.
- **Closure oracle:** Original commit → lost response → exact retry gives the same receipt; copying the operation into another revision/fresh request cannot republish; explicit compensation can. Reordered/deleted drafts, same-target conflicts, suite rename/move, already committed dependencies and stale context produce deterministic allowed/rejected effects with no partial native write.

### TESBO-QA-B03 — The existing machine authority path cannot be reused unchanged

- **Severity:** Must-Fix. **Category:** Implementation-Grounding. **Status:** Open.
- **Finding:** MCP `authorizeRequest` and the token REST guard call `requireProjectAccess(token.userId, token.projectId)`. That method derives the issuer's current workspace and requires the project's organization to equal it. API tokens carry issuer/project/read-write scopes, and the MCP actor remains the shared seeded identity; these do not establish the distinct executor installation/fenced-attempt contract. Missing scopes currently default to `read`, whereas FR-017 specifies failure. This is a concrete gap against FR-010–017 despite meaningful P-18 improvements. [E1/E2/E11]
- **Impact:** Switching a human UI workspace can affect an otherwise bound machine task; installation ownership, current delegation, revocation and actual attribution cannot be inferred reliably from a token issuer. Omitted scope handling differs between the intended contract and current issuance.
- **Recommendation:** Reuse token hashing, project membership and P-18 checks while introducing an explicit machine principal bound to the project/installation and current delegated ceiling. Resolve organization from the bound project for machine requests; keep the browser's workspace semantics for human navigation. Add server-validated fencing and actual actor attribution to task/report writes, with legacy-token migration and explicit scope parsing.
- **Valid alternative:** A deliberately named single-installation pilot can narrow capability and adapter support, but it still needs a distinct identity and must pass workspace-switch, revocation and stale-attempt oracles. A descriptive token name is not a substitute.
- **Closure oracle:** Two installations in one project cannot submit each other's attempts; issuer workspace change does not change machine target; issuer/delegation/instance revocation denies the next protected operation and evidence read; stale fencing cannot finalize; omitted/empty/unknown scopes fail without granting access. Exercise both MCP aliases and permitted REST paths.

### TESBO-QA-B04 — Result and historical truth require explicit native semantic changes

- **Severity:** Must-Fix. **Category:** Consistency / Implementation-Grounding. **Status:** Open; automatic Bug-link status mutation is a confirmed source defect against binding canonical human policy, not an undecided product behavior.
- **Finding:** `failLinkedExecutions` changes any eligible non-Failed execution to Failed and sets execution time/actor after a Bug association; sealed automated runs have a narrower exception. Current case update and proposal Save also update `cycle_items.snapshot_external_id` for that case. The target instead requires side/direct/unknown findings, original tested provenance, independent retests and separately reviewed correction. Existing case/history/import consumers cannot inherit those side effects unchanged. Canonical README lines 301/303 define the adopted direct-versus-side and historical-integrity policy; line 329 explicitly requires removal of the automatic status mutation. A direct failed expectation needs its actual applicable condition/step and evidence, not association alone. No newer attributable user decision overriding that policy was provided to this review. [E4; C/00 lines 301–339; FR-048/071–087; C/03 §18.2]
- **Impact:** Human-selected defect association can fabricate result evidence; current case edits can alter historic identity; a fresh retest can appear to have repaired an old execution instead of creating a new observation. Audit/summary consumers can then report misleading quality or actor history.
- **Recommendation:** Keep native Bugs, Runs and case versions, but split association from an explicit authorized result correction and introduce attempt/condition occurrence identity. Preserve frozen tested fields and append correction/supersession provenance. Make relevant mixed case/Bug/result operations use the shared selected transaction and mandatory audit; distinguish later external notifications/attachments from native commit.
- **Valid alternative:** For a first external report with no applicable approved case, retain an observed finding/report and stage a native Bug without creating any executed-case result. It must remain unadjudicated where no justified assertion exists.
- **Closure oracle:** Linking a side Bug leaves status/time/actor unchanged; direct finding still needs the relevant assertion and evidence; a retest creates new immutable provenance; editing current case identity or importing history cannot rewrite accepted tested snapshots; rejected/unselected operations and failed audit leave no native selected-apply effects.

### TESBO-QA-B05 — Accountable authority and recovery policy must be decided before affected governed writers

- **Recommendation:** Record narrow accountable decisions for the first enabled artifact types and scopes before implementing/exposing their governed promotion. Bind exact action/revision/target/dependency/policy evidence with replay/expiry controls; keep raw intake separate from authoring/promotion. Preserve the approved native permission hierarchy and fail closed where a mapping remains undecided.
- **Valid alternative:** A closed pilot can use an explicitly ratified narrow human authority and one approved method assignment while broader policy/release promotion remains disabled.
