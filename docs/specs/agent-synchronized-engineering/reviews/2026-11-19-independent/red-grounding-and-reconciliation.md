## Grounding member: premise, coupling and wrong-owner attacks

The user job survives removal of the proposed platform: ask a specific external tester to perform
bounded work with its own driver, retain the exact original observations, analyze them, request a
linked new retest and accept only selected native changes. An existing case or hosted model key
cannot be a prerequisite for every such job. Baseline `aiGenerate` explicitly refuses a missing
project model allocation and generates cases; it cannot serve unchanged as the external task
creator. The default-off `stageTestcaseChanges` supports externally prepared case proposals but
does not establish an executor claim, attempt, original report or retest chain.

Conversely, the job does not require another case, run, Bug, file, KB, review or source repository.
Native Test Cases own definitions, native Runs/executions own accepted result projections, Bugs own
defects, storage owns bytes, and current generation/task/proposal owners already supply useful
navigation and selected native application. A cleaner external API cannot justify copying those
facts. The source graph can be linked to a task; it cannot be the mandatory parent of source-free
mobile investigation. Model Studio remains a model owner, not the universal QA work owner.

The main cross-consumer coupling risk is treating one current mutable projection as the historical
fact another decision consumed. Examples include a testcase label rewritten into an old run,
an edited report presented as the original, an ordinary KB approval treated as Skill activation,
or a task's generation-complete status presented as successful testing. The repair direction must
retain separate requested, observed, interpreted, accepted and released facts while composing their
views through the existing native shell.

## Grounding member: failure boundaries and implementation reality

`StorageService.verify` at the baseline checks availability and length; `getBuffer` can retrieve
the bytes. The first is a valid generic helper but is not a digest proof. The design should extend
the existing receipt/attachment boundary with actual-byte verification rather than falsely claiming
the current helper already implements the report contract or replacing the whole storage service.

Native selected proposal apply already uses exact current review data, native writers, a transaction
and mandatory audit. These are positive controls. They do not prove cross-revision logical operation
identity, exact destination selected before apply or a dependency-closed conflict-free plan.
Atomicity can commit an incorrectly interpreted plan; it does not validate that interpretation.

The baseline Bug side effect is a confirmed canonical contradiction. Root previously accepted an
implementation note as if it established a newer human policy; that was not supported and is
withdrawn. Both direct source inspection and the canonical README support removal of automatic
result mutation. The separate current repair preserves native relationship validation and explicit
result writing. It does not implement all finding classifications or historical correction policy.

The same distinction applies to ordinary case-ID rename: the current repair removes automatic
updates to earlier run snapshots from native/proposal edits. Privileged history import and full
attempt/correction retention remain open. Later repairs cannot close a baseline finding without a
new exact-pin disposition, and source changes cannot establish deployment.

Existing human-session checks are a meaningful narrow boundary. They are not the complete proposed
action-bound authority, role, root recovery, exception and capability contract. Future executor and
analyst grants cannot simply inherit every existing machine write permission. Legitimately
authorized reporter compatibility must be preserved explicitly, not globally prohibited to make
the new boundary look complete.
