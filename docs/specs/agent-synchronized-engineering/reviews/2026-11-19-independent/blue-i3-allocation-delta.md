### 4.3 Transition and race protocol

Lock the canonical task before its current assignment/attempt and receipt; use a fixed order everywhere. Re-read current grant/credential/installation/issuer-delegation and project writability after waits, through a bound-project resolver. Keep the human UI active-workspace check for human navigation; machine access uses its bound project's current membership/consent, not the issuer's last selected workspace. Current MS:178–208 and L:4010–4054 show why these checks must be distinguished, and why the existing request-time consent/credential checks must survive.

Claim is an atomic transition from an eligible unclaimed/expired authorization. The winner allocates a new generation and attempt, the loser receives conflict. A heartbeat renews only the exact active attempt before its authoritative expiry; elapsed time alone never grants another worker authority without an atomic claim. Reassignment/cancel/clarification invalidates the prior generation; even if a slow process continues externally, its next progress/finalize is denied. Resume creates a new fenced attempt; a material scope change also needs a new prompt/assignment.

Manual primary finalize takes the same task lock, checks expected work_revision and no active executor, and closes an unclaimed assignment explicitly as manually fulfilled. A racing claim either wins first, making manual import evidence-only/refused as primary, or loses after manual fulfillment. With an active executor, a permitted manual receipt is historical/evidence-only and cannot cancel, claim or finish it. Finalizing a supplemental receipt never rewinds UNDER_ANALYSIS/CLOSED/CANCELLED. Primary task fulfillment is checked independently of every reserve/finalize key. [C02 §4.1–4.2; C04 §4.3]

## 7. Report bytes, finalization and retention — E1

**Chosen ownership:** task_reports owns the pending/final receipt; attachments remains the single file metadata owner; StorageService gains a narrow **immutable-report object mode**. An attachment uses entity_type=task_report and a checked report FK as in §4.2. The immutable report manifest binds attachment UUID, same project/report, full byte count, detected/accepted type, SHA-256 and immutable object generation. It never binds only a URL, display filename, length or client-supplied digest.

**Driver support is explicit.** Current local open("w") and S3 PutObject overwrite; current verify uses stat/HEAD length; getBuffer can retrieve actual bytes; getAccessUrl may issue a direct expiring S3 URL. None is sufficient unchanged. The selected local adapter uses exclusive create at a server-generated unique key and closes the write handle before verifying the complete bytes. The selected S3-compatible adapter requires demonstrated create-if-absent and immutable generation identity (conditional create and, where available, returned version identity bound on reads). The installed SDK/configured endpoint's support is **not demonstrated by this source review**. Until its isolated capability probe passes, that driver's new immutable-report capability is disabled with a truthful error; existing ordinary storage remains supported. This is the explicit capability narrowing White permits, not a claim that all S3-compatible providers implement a new promise.

The design must not accept weak fallback to ordinary overwrite if the conditional request/version contract is unsupported. No new cloud/storage service, public bucket, scanner or provider is selected. Local exclusive create is also not a claim of protection from a privileged out-of-band filesystem administrator; accountable operational controls remain W-E/W-M.

### Selected reserve/upload/finalize protocol

1. **Reserve in a short database transaction.** Authorize task/report mode and current assignment/fence or explicit manual/historical authority; lock task, then assignment/attempt, then report. Allocate report ID, primary slot, expected manifest/reservation and server-owned artifact IDs before bytes exist. Unique primary slot is independent of request key. Quota is reserved at the native storage-plan owner, not inferred from a successful precheck.
2. **Upload outside the transaction.** Claim one upload generation by CAS. Key includes project/report/artifact/generation plus server entropy; client cannot choose it. A retry after an uncertain upload creates a new object generation or reads the existing receipt; it never overwrites a verified key. Only the claimed generation may become READY. A stale uploader cannot attach bytes to a new attempt or generation.
3. **Verify actual completed content.** Close upload; read/hash full stored bytes, compare server size/hash/type to the declared contract, store immutable generation and result. Size-only verify is not promoted. A missing required artifact blocks availability; optional omissions remain explicit. No analysis/public preview of pending bytes.
4. **Finalize atomically.** Take the same lock order and current authorization again; compare task version, assignment, fence and all READY artifact generations. Persist complete raw narrative, manifest/digest, submitter/source, exact prompt and report receipt plus mandatory audit in one transaction. Primary advances work to REPORTED once; supplemental/manual evidence-only does not. A lost response is recovered by receipt lookup/replay.
5. **Cleanup has a fenced state.** Under the report/reservation lock, cleanup can claim only expired/abandoned unfinalized objects under approved policy. Finalize and cleanup cannot both win. Delete outside the transaction using the exact claimed object generation; mark storage/quota release only after verified cleanup outcome. A stale upload completion cannot change an abandoned reservation to READY. Late/uncertain abandoned bytes remain tracked for retry, not falsely declared deleted.
6. **Read through current authorization.** New raw, Markdown, image preview, range, export and MCP evidence reads resolve task/report/attachment ownership and current grant each time. Use server-mediated bytes; do not expose a legacy presigned direct URL for this protected report namespace. All read modes honor the same scope and do not allow a preview/export/public-trace alias to bypass revocation. A range response is not proof that the client consumed the full image.
7. **Protect the storage namespace.** Generic put/delete/getAccessUrl cannot operate on finalized report keys; they reject or dispatch through the report owner. Attachment metadata/manifest immutability is enforced in the database. Finalized/held evidence cannot enter ordinary Bug attachment or abandoned-upload deletion. A lawful erasure/redaction action, once explicitly configured, creates an attributable custody disposition; it does not rewrite the original receipt to claim missing bytes remain available.

**Quota caveat discovered in source:** PlanLimitsService:198 counts nondeleted attachments plus KB files, so the new type can participate without a new accounting catalog. But checkStorageAvailable:301–336 is a read/compare, not a concurrency reservation. Relevant writers are Bug-comment preparation L:8997, Bug upload9532, execution upload9645, KB upload12964 and Automation's nonthrowing storage check/evidence upload. A shared short reservation/charge protocol at this existing owner must cover competing writers before claiming a hard concurrent quota guarantee; locking only new report uploads is insufficient. Preserve Automation's documented behavior: evidence quota refusal must not discard an otherwise legitimate native test result. Reserved bytes convert to charged bytes once, and are released only for confirmed abandoned cleanup, not receipt replay.

**Decisive remaining evidence:** actual conditional-create/immutable-read behavior of the configured S3-compatible endpoint, full client-authorized screenshot consumption (including ChatGPT), and isolated real-db finalize/cleanup/primary-race tests. These are specific W-E/W-Q admission oracles, not reasons to keep A/B unselected. No digest field, code inspection or successful metadata HEAD closes them.
