## 2. Independent problem reconstruction

The job is to let a QA tester delegate real investigative work and reliably decide what to retain. The user's intention, the executor's actions, the executor's observations, an analyst's explanation, a reviewer's decision, and the native repository's current state are different truths. They differ in authorship, timing, trust, and mutability even when a single screen displays them together.

A useful system must work when no cases, native model, AI key, or source repository exist; when an executor can reach a private application that Tesbo cannot; when a human supplies a report manually; when two instances race or a lease expires; when an upload succeeds but acknowledgement is lost; when a report contradicts the next retest; when a side finding accompanies a passing test; when the target case changes during review; and when an approving human changes their mind after an operation has already committed. Recovery must preserve what actually happened rather than rewriting history to fit the current task state.

The value boundary is narrower than a new automation platform. Tesbo coordinates work and preserves traceability. The external executor remains responsible for its driver, application reachability, device/browser credentials, and actual observations. Native Tesbo remains responsible for authorization, reliable receipts, immutable relied-on evidence, selected publication, and meaningful downstream projections. The native engineering loop adds upstream change and requirement context; it cannot make cases or Model Studio a prerequisite for exploratory QA. [C1 FR001–048, FR071–081; C2 core workflow; C3 original architecture and §18; C5 I3-Q]

### Historical truth, migration constraints and dormant machinery

1. **Cases:** V155 explicitly separates content from bookkeeping and captures custom field/tag dependencies. Approval cannot be reconstructed from an old `Approved` label. Historical cycle snapshot fields may be null; preserve them as unverified history rather than attach today's receipt. Existing runs and new admission are different cases. [E4]
2. **Knowledge Base:** V156 preserves ordinary autosave behavior while making submitted/approved/rejected governed snapshots immutable. Existing approved documents without a reviewed version remain unverified; content/source metadata changes invalidate current review. Do not backfill human approval or Skills use. Ordinary autosave coalescing must not be generalized to immutable evidence. [E5,E6]
3. **Proposal history:** V157 supplies revision counters and append-only applied save receipts, not immutable history of all uncommitted proposal revisions or stable cross-revision operations. Migration must retain legacy selected indexes/receipt snapshots honestly and introduce new stable identities without pretending old arrays had them. Existing shared task/chat associations and subsequent soft-delete restrictions must remain intact; early migration defaults alone do not describe current deletion behavior. [E7]
4. **Automation:** V84 deliberately reuses native cycles/results and documents older automation worker tables as unused by TypeScript. Name similarity to `automation_sessions`, jobs or reports does not make those dormant tables the correct new executor/report authority. Case-backed latest-attempt-wins reporter semantics cannot become immutable case-free narrative semantics by relabeling. [E9]
5. **Actor identity:** V65's shared MCP actor is useful attribution for the original feature, not a distinct executor installation or authority to claim another instance's work. Preserve historical actor attribution; extend with actual instance/principal lineage. [E2]
6. **Source bindings:** V146 is one mutable binding per project, enabled false, referencing a server-approved checkout and no credentials/path supplied by the client. Preserve that safety boundary. If later multiple repositories/history are accepted, migrate with explicit source identity and historical snapshots rather than silently overwrite past linkage. [E11]
7. **Dormant/preview paths:** No-model proposal publication is guarded by `TESBO_PROPOSAL_REVIEW_PREVIEW_ENABLED`, default off, with effective-skill authority explicitly unready. Graph notification recovery is independently feature-gated; it is not source-provider event reconciliation. Older Zyra save helper definitions must not be called current active paths without their caller sweep; current `zyraSave` uses `zyraSaveAttempt`. [E7,E11]

### QA-B01 — The original delegated QA lifecycle has no implemented end-to-end owner

- **Evidence:** C1 FR001–026 and FR034, C2, C4 proposed task/claim/report/retest tools, C5 T101–106/T201–206/T401/I3-Q; E2 tool registry, E8 generation task UI/service, E9 native case-backed automation. - **Impact:** A user can appear to have “agent testing” while lacking proof of who executed what prompt, which report/attachments were received, whether a stale worker wrote, or which retest changed the conclusion.

- **Alternatives tested:** Reuse internal generation as-is fails external authority and no-key semantics; require automation cases fails zero-case exploration; resurrect legacy worker/report tables lacks active coherent owner; mutable KB report loses original evidence; compose narrow report/attempt records with existing owners fits.

### QA-B02 — Machine authorization still depends on the issuer's active UI workspace

- **Severity / category / status:** Must-Fix / Consistency, Implementation-Grounding / Open.
- **Evidence:** E2 `mcp.service.ts` authorizeRequest calls E3 `LegacyService.requireProjectAccess`; E3 `workspace` resolves `users.active_organization_id`, `requireProjectAccess` compares project organization to it, and `requireProposalAuthority` joins the same active organization. C1 FR015 and C5 T102 require project-bound machine authorization. V65 shared actor is not instance identity.
- **Finding:** Current project consent/client grants are real and valuable, but a valid bound-project machine call can fail because the token owner switches UI workspace. Current read/write token plus shared MCP actor also does not express assigned instance/attempt capabilities.
- **Impact:** Background delegated work is coupled to unrelated interactive navigation; “same runtime” installations cannot be safely distinguished by a brand/actor label.
- **Recommendation:** Extend the canonical authorization service with an explicit trusted bound-project machine principal. Derive workspace from the bound project and check live organization/project membership, token, opt-in, client grants, assignment and capability ceilings where applicable. Preserve interactive UI workspace behavior and revocation; do not bypass membership.
- **Alternatives tested:** Asking the user to keep the right workspace open is not the contract; auto-switching their UI changes unrelated state; globally weakening requireProjectAccess risks existing interactive semantics. A principal-aware canonical seam is the coherent extension.
- **Required verification:** Issuer switches workspace while token remains valid; issuer membership removed; two instances of same runtime; token/client/assignment revoked between calls; global and project MCP plus REST token paths.
- **Gate:** Required for unattended external task/report authority and no-model staging exposure, not permission to replace current consent controls.

### QA-B04 — Associating a Bug still fabricates a failed execution on open/manual runs

- **Severity / category / status:** Must-Fix / Consistency, Implementation-Grounding / Open.
- **Evidence:** E9 `createBug` calls `failLinkedExecutions` after its association transaction; `addBugLink` calls it too. The helper excludes finalized automated runs but updates other linked executions to `Failed`, sets `executed_at=now()` and `executed_by=actor`, then emits result activity/notifications. **C0 revisions 1.4.8–1.4.11 explicitly establish the adopted direct/side policy, distinguish linking from correction, and require removal of automatic status mutation.** C1 FR071–081 carries the occurrence, action/assertion and correction contract. Existing CI smoke source expects Bug reporting to preserve complete execution state, but this member did not attribute a particular CI failure to that assertion. A source comment or commit interpretation does not supersede that canonical human policy; no attributable superseding decision is supplied in this run.
- **Finding:** Correct native access/lineage locking and sealed automation protection do not resolve the semantic error for other executions. Link meaning is currently too coarse to distinguish direct/side/undetermined findings.
- **Impact:** Filing or linking a side defect rewrites a prior pass, an unexecuted result, timestamp and performer; downstream reports falsely show an observation that never occurred. A report-to-native-Bug proposal would inherit this side effect.
- **Recommendation:** Retain native Bugs and links and make association traceability-only. An unfinished attempt may still be explicitly finalized Failed when actual evidence establishes failure of its applicable executed expectation; that belongs to the observed-result writer, not the link writer. A correction of a relied-on/finalized result is separately governed with original outcome, author, evidence, reason and revision retained. Add occurrence-level direct/side/unknown semantics and linked retest history as contracted.
- **Alternatives tested:** Protect only closed automation runs is insufficient; auto-fail only a “direct” link still confuses interpretation with actual result unless explicit correction is selected; a parallel issue store avoids rather than repairs the native owner. Native link/correction separation fits.
- **Required verification:** Create/link Bug against Passed, Untested, Failed, open automation and closed automation; execution actor/time/actual/history unchanged for association; chosen explicit correction separately; cross-project links and retries; all shared dialog/API consumers.
- **Gate:** Before enabling native Bug operations in shared proposal apply or claiming finding/result correctness. Existing baseline behavior, not asserted as a newly introduced PR167 regression.
