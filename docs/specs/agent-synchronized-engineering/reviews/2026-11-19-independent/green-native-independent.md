## 3. Finding GREEN-NATIVE-01 — High, historical occurrence aliasing

**Claim under challenge:** a model dispatch's immutable manifest preserves the model basis of the native execution outcomes attributed to it, despite later native edits and membership changes.

**Observed mechanism:** dispatch captures testcase IDs and model mapping information but omits the native `cycle_items.id` and `executions.id` that were created in its shared transaction. `observedByElementFor` then joins every currently active item/execution in the cycle and attributes outcomes using only `model_run_id + testcase_id`. `governedRunsFor` similarly rolls up all active membership, including later additions. An immutable manifest's bytes do not preserve its consumed meaning when the reader resolves an interchangeable current occurrence.

**Exact producer/consumer evidence:**

- `B/src/behavior-graph/model-studio-repository.ts`, dispatch approximately lines 721–781: native cycle/items/executions and manifest share a transaction, but each manifest case records `testcaseId`, title, path digest, element IDs, sources and mappings; no native occurrence IDs.
- Same file, `governedRunsFor` approximately 808–844: `case_count` and status aggregates read all current nondeleted cycle items/executions.
- Same file, `observedByElementFor` approximately 852–902: mapping key is `${run.id}:${entry.testcaseId}`; the second query selects `model_run_id, ci.testcase_id, e.status` with nondeleted membership and execution filters. Neither identity nor exact reviewed snapshot differentiates original and replacement occurrences.
- `B/src/legacy/legacy.service.ts`, `insertApprovedCycleItems` approximately 7440–7500: a partial unique index only prevents duplicate active membership. The code explicitly documents and implements re-adding a previously soft-removed testcase by inserting a fresh item and execution, with newly captured `snapshot_approval_revision` and `snapshot_reviewed_content`.
- Same file, single/bulk removal approximately 7510–7568: native removal soft-deletes the original item and its execution in a transaction; it does not redispatch or amend the model manifest. The native owner legitimately permits the later add.
- `C/01_PRODUCT_REQUIREMENTS.md` FR-048 requires original tested provenance to survive corrections; its native-run integration allocation explicitly requires occurrence/attempt provenance. `A/implementation-plan.md` bounded native-composition contract preserves ordinary native ownership while requiring model/native integrity. The missing reader grain is within the implemented native composition, not solely an unimplemented external-agent feature.

### Discriminating scenario and oracle

1. Dispatch model revision M1 with approved case A-v1 mapped to element E, creating item I1/execution X1 and manifest D1.
2. Remove A through the legitimate native run membership writer. I1/X1 become soft-deleted.
3. Edit and human-review A-v2, then add the same testcase ID A to the same native cycle. Native run ownership creates I2/X2 with a new reviewed snapshot.
4. Record a result on X2 through the legitimate result writer.

**Required:** X2 is a real native result but has no D1 occurrence/mapping basis. It must not inherit E's attribution merely because its testcase ID matches A. Unrelated cases added later must not inflate the model dispatch's governed outcome counts. The dispatched selection and its provenance remain distinguishable from current cycle membership.

**Forbidden:** attributing X2's result or new snapshot to the immutable D1/M1 mapping; silently substituting I2/X2 for I1/X1; treating legacy missing occurrence pins as evidence for the current membership; presenting an absent or removed occurrence as a successful result.

**Actual source-projection counterexample:** the scratch probe loads and transpiles the unchanged production repository module and invokes its actual `observedByElementFor`. Persistence and Nest imports are stubbed. The original occurrence control returns E with one Passed result, as expected. The replacement occurrence produces the same projected tuple because the production query selects no discriminating occurrence key; it also returns E with one Passed result, violating the required empty-attribution oracle. Two tests executed: one passed, one failed; process exit 1. This proves projection behavior against the declared query tuple. The multi-step SQL producer sequence is source-supported, not executed against a database by this reviewer.

**Contrary evidence examined:** initial dispatch checks current model approval, case eligibility, recorded mapping revisions, locking and shared transaction rollback. Native cycle items capture exact reviewed case snapshots. The model manifest remains byte-stable, and later mapping unlink does not rewrite its recorded element set. Those are valuable controls, but all precede the later native remove/re-add path and cannot recover an occurrence identity that the manifest/consumer never carries. Passing 609-test DB CI does not demonstrate this missing lifecycle scenario.

**Repair boundary:** extend the existing dispatch relation, not a new run or graph store. Capture native item/execution identity within the shared dispatch transaction; consumers join those exact identities with project/cycle/testcase consistency. Retain exact case review/snapshot provenance. A governed amendment is another possible design only if its new basis is explicit and prior basis preserved; the bounded repair need not introduce that larger contract. Do not backfill a legacy manifest by guessing from today's active membership.

Native removal currently excludes deleted items/executions from active counts. The smallest compatible fix can continue that behavior while exposing removed/unavailable provenance and preserving original dispatched identity/count. A separately labeled authorized historical outcome could be useful, but counting a deleted result as an active outcome would change existing semantics. The mandatory distinction is original, removed/missing and later replacement; this review does not invent a new retention or deletion policy.

**Impact and routing:** High because the user can be shown a model-linked result for a different tested occurrence, while the native result itself remains legitimate. Owner: Model Studio dispatch/projection with native run owner. Blue: reconcile owner and intent. Graph/manual trace: exact edge and occurrence identity. QA: real migrated remove/edit/reapprove/re-add regression plus unchanged control, unrelated addition, removal, legacy pins and unlink/history cases. Purple: explicit current versus historical/unknown presentation. White: keep the affected readiness claim blocked. Repair work is underway elsewhere but is not incorporated into this receipt's source identity or verdict.
