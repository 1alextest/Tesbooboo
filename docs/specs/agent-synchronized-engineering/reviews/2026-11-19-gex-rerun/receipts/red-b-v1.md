## Material findings

### GEX-RB01 — Native model selection conflicts with retained activation semantics

**Severity:** Major. **Category:** Spec-Code-Drift / Coupling. **Status:** Open; affected source-fit admission blocked.

MBT-C-12 explicitly makes approved active r1 remain current after authoring or approving r2; activation is a distinct family-owned CAS. The present source does something materially different. `saveRevisionForUser()` appends a new draft. `dispatchRunForUser()` selects the greatest revision number and refuses an older revision with `SUPERSEDED_REVISION`; its own comment says saving a newer revision moves the dispatch basis. The MCP `run_behavior_model` description exposes that same rule, and the frontend uses the latest revision for authoring and mappings. [D3; S4–S6]

**Counterexample, source-derived rather than executed:** a tester relies on approved r1 while a colleague drafts speculative r2. Under the canonical contract r1 should remain usable for CURRENT work until an authorized activation. At the pin, dispatching r1 is refused solely because r2 exists. Approving r2 then makes it eligible without the independently recorded selection required by C-12. This collapses authoring-head and effective applicability, couples a harmless drafting action to another tester's run, and affects historical/current coverage interpretation.

The amendment truthfully calls its extension proposed; therefore this is not an allegation that it claimed implementation complete. It is a concrete migration seam that “reuse immutable model revisions” does not itself resolve. Identify the shared applicability resolver, preservation of already dispatched manifests, initial selection treatment for legacy rows, and REST/MCP/UI compatibility in the existing MBT work before reuse is admitted. A deliberate latest-head-only design is a legitimate simpler alternative **only if the decision owner explicitly amends C-12**; a reviewer cannot silently select it.

**Falsifier/closure:** exact-head source and DB/API evidence showing draft/approval of r2 leaves r1 current, one authorized CAS changes selection, stale competing activation fails, and old attempts retain their original revision. A newer unmerged branch or generic approval test does not close this finding.

### GEX-RB02 — Generated-case retry protection crosses independent transactions

**Severity:** Major. **Category:** Failure / Invariant / Spec-Code-Drift. **Status:** Open; source-supported failure mechanism, runtime reproduction NOT RUN.

`createCasesFromPathsForUser()` holds an outer transaction and per-model advisory lock, calls `legacy.createTestCase()`, then inserts the path-to-case mapping. The legacy helper opens and commits its **own** transaction; `DatabaseService.transaction()` obtains a fresh pooled client. Consequently the case and the mapping do not share the surrounding commit. The unique mapping key cannot protect a case whose mapping never committed. [S4, S7]

**Reasoned interruption:** native Draft C1 commits; subsequent mapping insert or outer commit fails; retry sees no mapping and creates C2. An outer rollback cannot undo C1. This threatens native identity, review burden, duplicate learning labels and reliable resume, precisely the consumers expanded by GEX-05/08. Existing source comments claim repeated generation is idempotent, but the transaction boundary narrows that claim to successful mapped requests.

Reuse the shared native writer through one actual transaction for the selected protected commit and its provenance/receipt, or use an explicitly recoverable staged operation with a durable identity before any independent commit. Preserve a legitimate human Draft workflow where appropriate; do not mistake this native Draft-conversion endpoint for the proposed shared AI candidate-submission operation. The candidate already requires atomic selected publication and separate staging, so the recommendation concretizes its existing invariant rather than inventing a second review system. [D2, D4]

**Falsifier/closure:** inject failure after case insertion but before mapping commitment, then retry/read back through the real API/DB boundary. There must be zero orphan publication or one recoverable stable logical case, never an extra case; verify audit/provenance and concurrent retry as well. A mock which supplies the same client to both calls would conceal the mechanism.
