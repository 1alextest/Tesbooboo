# Native retest backend — independent scenarios, frozen before candidate review

## Scope and evidence boundary

Named increment: bounded native human creation of a new Run from 1–100 explicitly selected executions of an existing Run. This is a static adversarial backend review, not implementation, a runtime certification, a formal architecture quorum, a full immutable execution-attempt/correction journal, or an external task loop.

This checklist was written before reading the candidate migration, native-retest module, nativeRetest service methods, changed tests, or frontend. Inputs were the assigned outcome, repository instructions (`AGENTS.md`, `CLAUDE.md`, `docs/agent-scope-discipline.md`), and the separate baseline checkout at `/workspace/scratch/8e9074abd0d0/tesbo-qa-baseline`.

Baseline evidence inspected: `legacy.service.ts` project authority, ordinary Run creation and item insertion, execution update/bulk/evidence paths, public share projections, Bug link references; `approved-run-cases.policy.ts`; migrations V3, V111, V119, V140, and names/call sites of approval snapshot/dependency machinery in V151/V155/V157. No database, backend, or application E2E was started or queried.

## Baseline ownership and constraints

- Existing `cycles` → `cycle_items` → `executions` is the authoritative Run/result chain. A new Run can reuse canonical current approved testcase content while preserving earlier Run item snapshots and result rows.
- Approved additions already require a current exact native-human approval receipt and lock canonical testcase content; dependency-backed semantic snapshots require a fresh read after a lock wait.
- Existing parent-cycle row locks serialize ordinary result and evidence writes. Deletes and removals are soft deletion; hard-delete foreign keys protect existing history. New lineage must fit those owners without rewriting source records.
- Project access combines actual project membership and active workspace. The baseline has a transaction-bound current authority helper that bypasses request caches. Plan references are project scoped. Plan/billing locks must remain enforced at the new route and final mutation boundary.
- Public Run and execution share responses deliberately use fixed column lists. Internal snapshots, result details, evidence/storage identifiers, actors, and lineage must not become public by adding fields.

## Frozen independent invariants and discriminating scenarios

| ID | Invariant / scenario | Evidence that would distinguish correct behavior |
|---|---|---|
| I01 | Exactly 1–100 selected existing execution identities from one authorized source Run form the request. | Reject 0, 101, absent/null/non-array IDs, malformed IDs, duplicates or ambiguous normalization, foreign/wrong-Run IDs, deleted items/executions. No silent subset, testcase-based substitution, or expansion to all failures. Valid 1 and 100 remain possible. |
| I02 | Native human authority is authentic and current at the consequential commit. | Unauthenticated, agent/API-token/automation principals, wrong tenant, inactive workspace, removed membership, archived project, and lost required permission cannot prepare or commit. Recheck after any serialization wait. Another authorized human can use their own request; request ownership cannot be spoofed by body fields. |
| I03 | Applicable plan entitlement/read-only authority is current. | Allowed state succeeds. Downgraded/locked state refuses writes, including change while waiting on another transaction. Readback of a previous successful creation remains truthful where read access is allowed. |
| I04 | Review binds an exact current approved case definition for every selected source execution. | Draft/demoted/stale-receipt/soft-deleted/moved testcase causes whole-request refusal. Changes to steps, description, custom field values/definitions/tags and any approval-semantic dependency invalidate a pending review. Unrelated metadata that does not change executable semantics must not create unjustified staleness. |
| I05 | Review is bound to actual selected source observations and proposed destination settings. | Review/readback identifies source Run and execution, captured outcome/result/evidence observation, current approved definition, intended destination metadata, and source-to-destination mapping. A caller cannot substitute an ID, name, build, environment, release, plan, or content between approval and creation unnoticed. Temporal meaning is explicit; provenance never silently substitutes a later result for what was reviewed. |
| I06 | Commit is all-or-nothing. | Inject failure after destination Run, items, executions, or receipt insertion: no orphan Run, partial selection, durable success receipt, or consumed success identity. One disallowed member prevents the entire batch. Source rows never receive compensating changes. |
| I07 | Destination is a fresh ordinary manual Run with fresh unexecuted work. | New Run, item, and execution IDs; each selected canonical case exactly once; current reviewed snapshots; manual source semantics; Untested statuses; no copied actual result, executed time/by, errors, step results, history, assignee, evidence, Bug, or external defect fields. Ordinary manual completion remains usable. |
| I08 | Source work is preserved byte-for-byte by retest. | Before/after source Run metadata, item snapshots, executions/results, attachments/evidence, Bug rows and links compare equal. Retest does not reopen/reset a closed source, mutate its status, or reassign Bug/evidence ownership. Covers manual and automated closed source Runs. |
| I09 | Request identity safely supports uncertainty. | Lost successful response followed by exact retry/readback returns the one committed destination and receipt. Concurrent identical requests commit once; changed payload/review under same key conflicts rather than silently returning unrelated output. Failed transactional attempt may be safely retried without hidden partial work. |
| I10 | Serialization and freshness apply to actual writers. | Deterministic interleavings with result edit, evidence add/delete, item removal, source delete, testcase semantic/dependency edit, approval demotion, membership removal/workspace switch/project archive, plan change, and identical creation. Lock order and post-wait statements must rule out stale admission and avoid unnecessary deadlock cycles. |
| I11 | Receipt is durable, exact, and immutable within the existing ownership model. | Receipt records actor, source and destination identities, source observations, reviewed definitions/revisions, selection/configuration, created time and mapping. API and direct ordinary SQL cannot rewrite receipt semantics accidentally; soft deletion does not destroy it. Any allowed hard-delete cleanup is deliberate, scoped, compatible with existing FK behavior, and does not orphan an apparent success. |
| I12 | Readback remains a truthful recovery boundary. | Pending, absent, expired, rejected, committed, and destination-soft-deleted states are distinguishable as the implemented contract requires. A deleted or modified destination must not make a committed request look never-created or permit duplicate creation. A post-commit mutation cannot rewrite creation-time receipt facts. |
| I13 | Canonical hashes represent semantic content deterministically. | Reordered object keys and equivalent normalized selections/settings cannot manufacture mismatches; changed semantically material values do change the digest. PostgreSQL JSON/JSONB output and JavaScript serialization agree for supported shapes, Unicode, numbers, nulls, nested objects, and arrays, or one canonical owner computes all compared hashes. No raw whole-row hash that includes unstable formatting or irrelevant cache fields without purpose. |
| I14 | New reads and creation respect privacy and tenancy independently. | Source/preparation/commit/readback endpoints scope project/tenant/object/actor and handle unknown versus foreign IDs consistently. Share projections and CSV/report consumers expose no new internal receipt, source observations, evidence key/URL, actor, approval token, or private case content. |
| I15 | Existing downstream behavior remains coherent. | New Run appears in list/detail/executions, counts and reports with ordinary schema semantics; subsequent result writes and normal soft delete work; source public shares remain narrow; plan lineage is valid. No special shadow result/evidence store or second approval owner. |
| I16 | Tests prove boundaries rather than implementation agreement. | Real PG tests use independent before/after queries, multiple connections/barriers, actual writer paths, and verified fixture prerequisites. API tests prove native authenticated route admission and readback. Failure tests assert no forbidden side effects; positive controls prove legitimate use. Tests must not rely only on mocked query text, guessed sleeps, or the same hashing/helper implementation as the product. |

## Review method and limits

Next stage may inspect candidate source and tests, trace affected actual writers/readers, and run pure local checks if useful. It must not modify product/tests, run a database/backend/application E2E, deploy, merge, or claim runtime success. Findings will name a concrete reachable mechanism, severity, scope classification, and discriminating validation; speculative concerns will be identified as such and will not be promoted to blockers. The candidate review report will bind conclusions to exact file hashes and leave actual impacted CI with the coordinating agent.
