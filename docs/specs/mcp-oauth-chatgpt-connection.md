# MCP OAuth connection — source-grounded enhancement specification

**Status:** DRAFT / not approved / not implemented. **Source snapshot:** `development@561ae3054fb69665534685f8f3d9481681225073`, 2026-11-23. **Purpose:** enable a user to connect ChatGPT and other conforming remote MCP clients to their chosen Tesbo project via a secure OAuth authorization flow, while preserving existing API-token clients, project permissions, governed publication and immutable QA evidence. This is an extension of the existing API & MCP surface, not a new integrations product or shadow MCP server.

**Authority:** current existing API-token/MCP services and their owner-reviewed policies control deployed behavior; this document proposes changes and does not amend ASER's eight canonical specifications by itself. Any incompatible change to canonical policy requires a separate governed review. No active OAuth provider, actual ChatGPT handshake, connected Tesbo MCP in this session, or native Tesbo QA execution is claimed.

## Protocol-era safety increment (implementation candidate, not OAuth)

**Source scope:** `mcp-protocol-compat.ts`, existing `McpController.respond`, and existing `e2e/api/mcp.spec.ts` MCP-P07 smoke selection. Tesbo currently advertises only legacy `2025-06-18` and `2024-11-05` from `mcp.types.ts`. Before attempting any stateless tool routing, the authenticated HTTP controller now rejects requests declaring unsupported per-request protocol versions and `server/discover` with HTTP 400 and JSON-RPC `UnsupportedProtocolVersionError` (`-32022`) naming the actual supported legacy versions. It runs after project/credential grant authorization and before session validation or tool dispatch. All legacy initialize/session APIs retain their existing responses and HTTP statuses.

This is **a fail-closed compatibility signal, not modern MCP or OAuth support**. The 2026-07-28 stateless request metadata, `Mcp-Method`/`Mcp-Name` header validation, `resultType`, `server/discover` success path, HTTP 200 response semantics, AS discovery, OAuth token issuance and user/client consent are **not** implemented by this increment. A client that requires modern protocol support must still treat Tesbo as incompatible; recognized error details are not proof of automatic successful legacy fallback. Verify actual client behavior separately. The candidate keeps OAuth disabled and does not alter `TESBOPROJECT` records. Unit and disposable real HTTP regressions must pass at their final head before this scope is accepted.

Standards basis: [MCP 2026-07-28 versioning](https://modelcontextprotocol.io/specification/2026-07-28/basic/versioning), [Streamable HTTP transport](https://modelcontextprotocol.io/specification/2026-07-28/basic/transports), and [legacy initialization contract](https://modelcontextprotocol.io/specification/2025-06-18/basic/lifecycle).

### Additional release-blocking lifecycle obligation — OA-20

**Consent review must bind to the displayed authority.** The existing session/interaction CSRF proof alone does not bind the client, resource, account, prompt, effective allowed tools, expiry or owner settings revision that the human saw. If a project owner changes permissions while the consent page is open, the approval must refuse stale review and require a fresh page; cancellation must still work after revocation. The candidate uses a separate keyed review proof over those server-read facts and the session-bound CSRF proof, rederived on affirmative POST before creating a provider Grant. A revision change conservatively requires page refresh even if unrelated. No new permission owner is introduced. Unit and real Nest HTTP negative regressions are committed; CI and live acceptance are pending. This is a page-to-submit consistency control, not an atomic token-family revocation solution: policy changes after the recheck, provider exchange/refresh and same-ID reapproval still require OA-T18 enforcement.

**Revocation must remain effective after a client is reapproved.** The current OAuth read-only verifier correctly checks the current project-owner grant, so removing preapproval immediately denies the access token. However, the owner-grant update path does not yet demonstrably revoke the *existing provider Grant and RefreshToken family*. A previous user consent and refresh token may therefore regain effective read access when the **same client ID is approved again later**. Temporary denial is not the same as permanent disconnection.

Require a verified irreversible invalidation link from the existing revisioned `externalMcpAccess` owner to the relevant OAuth provider Grant/refresh families (or an equivalently enforced, immutable grant approval epoch bound to issued tokens). Never equate an OAuth `grantId` with a Tesbo API `tokenId`, and do not create a parallel client-permission owner. Reapproving the client must not reactivate any prior consent; require a **new explicit human OAuth consent** and fresh token family. Preserve historical proposal/evidence receipts, deny OAuth writes, and make any project membership restoration semantics explicit.

### OA-T18 implementation candidate — 2026-11-24 (NOT RELEASE ACCEPTANCE)

The current PR adds a subordinate `mcp_oauth_grant_approval_bindings` record (V167 migration) keyed by a one-way, domain-separated provider Grant fingerprint. The existing revisioned `externalMcpAccess` project setting remains the **sole permission owner**; the binding only proves which exact approval revision existed when a human consented. A later owner-settings write **permanently tombstones** prior bindings in the same project-row transaction; identity uniqueness prevents a revoked grant from ever being rebound, and reapproval of the identical client ID cannot restore the old family.

The embedded provider's strict adapter mode refuses stale `Grant`, `RefreshToken`, `AuthorizationCode` and `AccessToken` model reads; the MCP verifier and dispatch recheck the exact project, user, resource, client, revision and live owner approval. After positive consent, binding creation re-locks the project and membership; if policy changed in the meantime, it refuses and best-effort destroys the unbound provider artifact. ### OA-T18R — membership authority restoration (research-backed candidate, 2026-11-25)

**Decision boundary (D5):** Separate account identity, current membership/role, owner client approval, user consent, credential family and live connection. The IETF [RFC 7009 §2.1](https://www.rfc-editor.org/rfc/rfc7009#section-2.1) makes revocation terminal for a token and permits family/grant invalidation; [RFC 9700 §4.14.2](https://www.rfc-editor.org/rfc/rfc9700#section-4.14.2) permits event-driven refresh revocation; [RFC 7662](https://www.rfc-editor.org/rfc/rfc7662) distinguishes current activity from expiry. [MCP 2026-07-28 authorization security](https://github.com/modelcontextprotocol/modelcontextprotocol/blob/main/docs/specification/2026-07-28/basic/authorization/security-considerations.mdx) requires resource-bound token validation before serving protected data. None dictates that every organizational rejoin must require interactive consent; this is Tesbo's local decision, not a protocol mandate.

**Industry comparison:** [Slack OAuth](https://docs.slack.dev/authentication/installing-with-oauth/) revokes user-authorized credentials on account deactivation; [Entra](https://learn.microsoft.com/en-us/powershell/module/microsoft.entra.authentication/revoke-entrasignedinuserallrefreshtoken) uses a validity cutoff and [application deprovisioning guidance](https://learn.microsoft.com/en-us/entra/identity/users/users-revoke-access) requires downstream enforcement even for otherwise valid tokens. [GitHub reinstatement](https://docs.github.com/en/organizations/managing-membership-in-your-organization/reinstating-a-former-member-of-your-organization) explicitly allows restoring entitlements, but [credential authorization revocation](https://docs.github.com/en/enterprise-cloud@latest/rest/orgs/orgs) separately requires reauthorization. [Okta](https://help.okta.com/en-us/Content/topics/users-groups-profiles/usgp-deactivate-user-account.htm) distinguishes temporary suspension from deprovisioning; do not claim either product's exact rejoin token behavior without evidence. The [MCP enterprise-managed authorization extension](https://github.com/modelcontextprotocol/modelcontextprotocol/blob/main/docs/extensions/auth/enterprise-managed-authorization.mdx) offers centralized policy-mediated authorization without per-user interactive consent; it is a future alternative, not authorization to silently replace Tesbo's current human-consent model.

**Proposed rule for the default-OFF interactive Tesbo candidate:** actual committed project membership removal invalidates that member's existing consent families for that project; organization membership removal invalidates that member's families across that organization. Reinstatement restores only the approved current membership, not old codes/access/refresh/Grant identity. A fresh positive consent creates a distinct family under current authority. Do not change the existing project-wide owner revision policy, other members' grants, other organizations, legacy API-token semantics, or immutable historical QA records. Ordinary role changes that do not remove eligibility, temporary suspension, archive/restore and global account deactivation need explicit lifecycle dispositions rather than assuming all are identical. Retain existing default-OFF and require owner/White acceptance before activation.

**Mechanism comparison:** a live-membership join alone cannot detect removal followed by re-addition; a timestamp cutoff must be monotonic and race-safe; an application-only cleanup hook risks missing alternate writers; a durable membership-generation binding or transactionally enforced tombstone at every authoritative deletion boundary is a candidate. Inspect schema, actual removal/cascade/reinstatement writers and lock order before selecting; reuse V167 and the existing authority, not a second permission store. Do not asynchronously revoke only after committing the withdrawal. Consent/removal/owner-update/self-revoke lock order and DB-failure behavior require real transactional verification. If selecting a generation mechanism, the consent review proof must also bind that generation (removal/rejoin between page display and affirmative POST cannot authorize a new lifecycle silently). A stale grant must never be made current by reconnecting or rebinding the old identifier. #269 history must derive truth from the same lifecycle authority, not just a policy revision and a UI label.

**Acceptance oracles (proposed, not executed at time of this research):** OA-T18R-P/O preserve old provider artifacts through project/organization deletion and reinsert with the owner policy unchanged; assert denial before and after rejoin, then a new distinct consent succeeds. Direct SQL in the disposable DB isolates persistence semantics; separately exercise real removal and invitation/rejoin APIs, concurrent consent/removal in both orders, rollback, cross-project/org/member isolation, code exchange and refresh over real pinned-provider HTTP, MCP resource denial, stale consent page, history on rejoin, and no secret exposure or duplicate audit. Distinguish already admitted operations from new authorization after the removal commit; define in-flight response semantics explicitly. Actual ChatGPT recovery and owner/White disposition remain release gates. Do not claim the proposed test proves the implementation or deploy while unresolved.

**Conservative lifecycle choice:** ANY project MCP policy revision invalidates every previously consented OAuth Grant for that project, including unrelated client changes; this is intentional fail-closed behavior in this candidate, with potential re-consent burden. Revisit only through an authorized scoped epoch design with equivalent same-ID revocation guarantees; do not relax revision checks silently.

**Consent route ownership.** Tesbo explicitly disables the provider's development interactions at startup. In the pinned version, enabling that feature replaces the application's configured interaction URL. A normal authorization request must direct the browser to Tesbo's session-backed consent flow. Include the observed browser redirect in the OAuth connection regression. [Provider initialization](https://github.com/panva/node-oidc-provider/blob/v9.15.1/lib/actions/interaction.js)

It checks the original access, code, Grant and refresh records after same-client reapproval, including simultaneous refresh-record lookups. ### Mandatory design constraints recovered from source and standards

1. **Transport/HTTP correctness is an explicit prereq (OA-02/03).** Existing `mcp.controller.ts` returns HTTP `201` for ordinary JSON-RPC results and some authorization failures, and middleware can reject before the controller. Audit every HTTP/JSON-RPC response path, authentication middleware, MIME/content negotiation, sessions and both existing MCP routes. A missing/invalid credential must receive an appropriate standards-conformant 401 challenge and no tool dispatch; insufficient authorized scope receives the correct 403 treatment, never a successful 201 with a hidden auth error. A standards-compatible transport test and old-client compatibility must gate OAuth activation. No blind rewrite of currently functioning sessions.
2. **One policy, explicit credential kinds (OA-01/06/07).** Existing `McpClientGrant.tokenId` and the `api_tokens` join cannot be reused for OAuth by forging a token ID. Inventory current DB/middleware first, introduce a discriminated principal and credential-kind-aware grant with a *single shared* project/scope/allowlist/plan/human-only authorization evaluator. Define a reviewed migration and compatibility/rollback strategy for `externalMcpAccess.clients` and its CAS revision; preserve owner-only grant management and no implicit onboarding.
3. **Client trust is distinct from user consent (OA-04/05/12).** Choose the actual authorization-server owner and published issuer before coding. For CIMD require a bounded external metadata fetch with HTTPS, public IP validation, DNS re-resolution, no unsafe redirects, response-size/time limits, exact `client_id` and exact registered redirect check, and localhost warning/attestation policy. Do not treat a client's chosen display name as authentication. Support an actual verified ChatGPT CIMD/DCR flow, not generic hypothetical OAuth.
4. **Resource-bound grant and project selection (OA-08).** The project-scoped MCP URL is the preferred resource. `/api/mcp` may continue to serve API-token clients and OAuth only if an unambiguous single-project grant with canonical resource/audience is proven. No project selection by ambient browser session or most-recent workspace; reject cross-project, wrong issuer, wrong audience and account switching.
5. **Revocation means no new authorized writes (OA-09/10).** Define code/token/refresh-family state and atomic rotation, replay, lost-response, concurrent refresh, expiry, key rotation and family revocation. Revalidate project membership, client grant, scopes and governing Skill basis at the existing transaction-bound write lock. Revoking OAuth consent must not rewrite historical cases/runs or impersonate a human approval.
6. **Human outcome and operability (OA-11/13/14/15/16).** The UI must show project/client and *effective* permitted tool operations (not just requested read/write), pending owner approval, cancelled/expired/revoked states, last action, safe disconnect and accessible errors. Add safe correlated auth diagnostics, outage behavior and false-connected-state checks. Model client→grant→project→tool/operation→requirement/case/run obligations and invalidation consequences without claiming executed coverage.
7. **Protocol era must be explicit (OA-17).** MCP 2026-07-28 is now released. Its stateless core has no `initialize` handshake or `Mcp-Session-Id`; per-request identity/version/capabilities, optional `server/discover`, and MCP method/name headers differ from the 2025 era. DCR is deprecated in favor of CIMD; issuer validation and credential isolation are strengthened. Select a target-client version/era matrix with real ChatGPT proof and either support both eras with explicit routing/tests or defer modern support with a verified compatibility record. Do not silently mix header/body methods, reuse bearer credentials across issuers, or let cached tool lists override current grants. Include OA-T15 for downgrade, mixed versions, stale caches and authorization revocation.
8. **Native staging producer provenance is an enforcement seam (OA-18).** Existing `mcp.tools.ts` staging handlers require `ctx.tokenId` and send `kind: "api_token"` into the authoritative proposal/task owner. Extend only that existing owner with verified OAuth-kind producer receipts and exact retry/hash semantics; never spoof a legacy API-token ID. Preserve human-only apply and ensure forged kind, wrong project, revoked identity and lost-response retries cannot write unauthorized records. Add OA-T16.
9. **Acceptance is multi-layered.** Extend OAUTH-01–14 with OA-T01–14, preserve each native test-case identity within **TESBOPROJECT**, run separate historical build-bound attempts, and verify real ChatGPT/alternative-client interoperability plus production issuer/proxy behavior. CI green, documentation merge and OAuth metadata discovery alone do **not** constitute OAuth acceptance or release authorization.

## 2. Architectural decision and reuse gate

The MCP endpoint acts as an **OAuth protected resource**. An authorization server performs user login/consent, client validation and token issuance. Prefer extending Tesbo's existing login/session and organization/project authorization surface with a narrowly scoped OAuth authorization-server adapter **only after source archaeology has proved that the platform has no reusable standards-compliant inbound AS or deployable existing identity provider**. Otherwise integrate an established AS/IdP and keep Tesbo solely the resource server. Do not copy outbound-integration OAuth handlers into a second credential issuer. Resolve and document ownership of client registration, secret storage, token lifetime, keys, schema and rotation before coding.

No second MCP server, no parallel project client-grant system, no separate human approval authority, no direct test-case writes disguised as user approval, and no automatic cross-project grant. A single policy evaluation must combine OAuth credential/identity validity, selected resource, project-specific named consent, user membership/role, tool allowlist, scope, live project state and existing publication controls.

**Principal resolution:** machine bearer credential resolves to an explicit kind (`api_token` or `oauth_access`), stable credential/grant ID, user ID, project ID, client ID, authorized scopes, expiry, authorization/consent revision, audience/resource, and verified issuer. It must not populate `req.apiToken` with invented `tokenId`; adapt the existing dispatcher to an authenticated machine-principal abstraction. Only the credential authenticator knows the token type; domain handlers cannot privilege one client class.

## 3. Protocol and compatibility contracts

- Publish RFC 9728 OAuth Protected Resource Metadata for each supported MCP resource URL (including path-aware metadata where required) and RFC 8414 authorization-server metadata at the selected authoritative issuer. Resource IDs and issuer must be exact stable HTTPS identifiers; correct proxy-aware external origin, host and forwarded-header trust are mandatory.
- Unauthenticated `POST /api/mcp` and project MCP calls respond with an appropriate HTTP 401 `WWW-Authenticate: Bearer` challenge identifying the resource metadata; insufficient valid scope yields HTTP 403 with a standards-compatible scope challenge. No browser-session authorization substitutes for an MCP bearer token. Avoid redirects that forward bearer credentials.
- Authorization Code with **PKCE S256** for public clients; require CSRF `state`, short-lived single-use code, exact verified redirect URI, issuer binding (RFC 9207), resource binding (RFC 8707), strict client and scope validation, and proof of active Tesbo user login. No implicit grant or password-grant fallback.
- Prefer Client ID Metadata Documents (CIMD) when supported by the deployed client/spec; support client registration via explicit trusted metadata/pre-registration or bounded Dynamic Client Registration fallback only where required by a verified target client. DCR must not accept arbitrary privileged client capabilities or unvalidated redirects. Verify actual ChatGPT client behavior in a live contract test instead of assuming a specific scheme.
- Access tokens must be signed-and-audience-verified or opaque-and-introspected via trusted issuer; short-lived, revocable, and not reusable as Tesbo REST browser/session tokens. Refresh-token rotation/reuse detection, encrypted-at-rest secrets, logout/revoke semantics, issuer/key rotation, skew handling, rate limits, storage retention, and replay prevention require explicit testable policy. Prefer reusing existing credential/secret/storage infrastructure.
- Preserve the already supported API-token MCP path and both endpoints; no forced user migration. The resource-specific endpoint must bind its URL project to the token grant; the dynamic endpoint resolves exactly one authorized project from the credential or fails closed if ambiguous. OAuth token issued for Project A must not call Project B even when the user belongs to both.
- Review current MCP protocol version compatibility **independently** of OAuth: source currently uses `initialize` and `Mcp-Session-Id`; newer MCP revisions changed these. Avoid silently rewriting transport/session behavior in the authorization PR; create a version-negotiated compatibility decision and separate tests for currently deployed clients and ChatGPT.

References for standards validation: MCP Authorization spec and TypeScript SDK authorization guidance, OAuth RFC 9728/8414/7636/8707/9207/6750, and the MCP 2026-07-28 revision notice. Record exact spec date/version and live consumer behavior during implementation, rather than coding only against an undated blog example.

### Self-service OAuth consent history — candidate slice (PR #269)

The existing Tesbo API & MCP page must give a **signed-in project member** a separate, clearly identified view of that member's own OAuth consent records. This is independent of the project owner's named client preapproval list; ordinary members can revoke their own consent without being able to approve clients for the project.

- **Read authority:** query `mcp_oauth_grant_approval_bindings` by both authenticated human `account_id` and route project ID, after the existing membership check. The history SQL statement itself must require both current project and organization membership for the authenticated account at its database snapshot. Loss committed before the statement returns no records even if the preflight succeeded; a read already admitted at its snapshot is not retroactively cancelled. Current membership authorizes reading one's own history; matching historical membership IDs determines consent freshness, so a rejoined member may see old records only as requiring reconsent (or revoked). Never trust an account ID from the request body or disclose another member's records. Return a bounded history with a visible truncation indicator. Provider Grant IDs, bearer secrets, refresh secrets, signing material and raw encrypted payloads must never appear in responses.
- **Human meaning:** classify rows as `consent_current` only when the recorded project approval revision and current owner read scope still agree, `reconsent_required` when a grant is no longer current, and `revoked` after a durable tombstone. **Consent history is not a current-connection probe**; a valid policy binding does not prove the client is online, the token is unexpired or that external-client capabilities have been verified. When currently approved, show the actual read-tool restriction, not an invented unrestricted connection.
- **Self-revoke:** signed-in human only; select a grant by its non-reversible indexed fingerprint (not raw provider ID), under current project and member row locks. Persist `revoked_at` and an attributable audit event in **one database transaction**. A repeated revoke is an idempotent readback, never a second audit or new grant. Owner-managed `externalMcpAccess` stays unchanged. The existing strict issuer adapter and MCP resource authorization continue denying reads and refresh for a tombstoned binding, including after the same client identity is reapproved.
- **Failure/concurrency:** browser cookie and machine bearer never combine identities; revoked membership, foreign user/project, malformed IDs and unavailable audit/storage refuse. After an ambiguous request, clear the UI's local state and require authoritative reload instead of claiming either success or failure. Changing the selected project invalidates pending reads and writes.
- **Tests:** backend privacy and denial tests, actual disposable-PostgreSQL other-user/own-user revocation and audit assertions, and a selected MCP-P18 browser UX regression. CI evidence must be tied to its **exact final head**; synthetic fixtures do not replace authorized live TESBOPROJECT cases, true user identity or actual ChatGPT acceptance.

This is a stacked, default-off-compatible user-control enhancement. No separate OAuth identity service, permission owner, or production activation is created. Later client-session telemetry and per-device disconnection would require separately reviewed evidence and purpose/retention decisions.

## 4. Consent, policy and human outcomes

**Connect:** user sees verified client name, identity, verified redirect origin, exact Tesbo workspace/project, read scope (default), optional write scope (separate explicit opt-in), allowed tool classes, grant expiry, material effects and revocation location. Consent is not inferred from logging in. Owner/manager authorization and existing per-project MCP access controls remain effective; decide whether ordinary project members may request read-only grants subject to owner policy. Consent requests that exceed the user's/project's effective permission must fail, not silently expand privilege.

**Status:** existing API & MCP page shows active/revoked/expired OAuth connections beside (not replacing) named API-token clients, readable owner/actor, last access, scopes/tools, project, creation/expiry, policy revision, and a clear **Disconnect** action. Human outcomes: know what is connected, what it can do, which project it can reach, when it last acted and how to revoke it. Do not expose token values, refresh tokens or full request bodies.

**Write and approvals:** a write-scoped grant may perform only tools that the existing MCP path allows for machine callers and only within assigned scopes/allowlists. Native human-only approval, Skill version assignment/activation, protected selected apply, release approval and published test-run results retain their separate true-human authority. No user-session proxy, OAuth consent, or high scope silently transforms a machine agent into a human approver.

**Disconnect:** revoke grant and related refresh sessions so future MCP requests stop; preserve required immutable audit and previously accepted test cases/runs. If a refresh, scope reduction, project lock, membership removal, consent disablement or Skill assignment change races with an in-flight tool call, check at the same transaction/lock boundary as existing domain writes and leave rejected operations unchanged.

## 5. Proposed bounded schema/owner changes

Extend the **existing** API-token/MCP consent/policy and session persistence owners rather than creating separate auth policy tables for each client. Store OAuth client metadata/registration trust, authorization code hash and one-use state, grant/consent identity and revision, token/refresh family hashes or signing identifiers, project/user/client binding, scope/tool restrictions, revocation/expiry, and auditable provenance. Choose a minimal migration plan only after inventorying current tables and service methods. No production schema shape is approved by this design note. Do not backfill consent or grant OAuth access to preexisting tokens.

Read-only and OAuth metadata can deploy first behind disabled-by-default feature configuration; issuance and credential acceptance activate only after exact CI and owner-authorized staging verification. Fail closed on missing issuer/signing configuration. Feature-off leaves all existing API-token responses, authorization and tooling unchanged.

## 8. Decision register — surface before committing interpretations

- **D1 Authorization server:** in-app narrowly bounded Tesbo AS vs existing suitable external IdP; ownership, audit, credentials, deployment and recovery consequences.
- **D2 Client registration:** CIMD, pre-registered client ID, or bounded DCR based on *actual* ChatGPT/client acceptance; redirect policy and trust verification.

- **D4 Connection selection:** project-scoped URL default vs shared endpoint project picker; one grant per project; cross-project reconnection and account switching.
- **D5 Tokens:** TTL, refresh rotation, revocation SLA, opaque vs JWT, key management, session and evidence retention; reconnect UX.
- **D6 Transport version:** support legacy `initialize`/session alongside the newer MCP revision or upgrade separately; live ChatGPT compatibility proof.
- **D7 Release:** which connected staging/production provider controls issuer HTTPS redirects; actual connected repo/branch, backend authorization-server availability, rollback and key-rotation drill.
- **D8 Client entitlement:** whether a specific ChatGPT account/workspace supports remote custom MCP *writes*; a read-only successful connection is not proof of native writes.
- **D9 Governance:** reuse P-07 human publication and governed Skills/ASER contracts, not agent bypass; specify behavior when Skills or suite/case publication are blocked.

**Owner feedback requested for D1/D3/D4/D5 before implementation** where no existing approved policy settles them; other decisions require evidence, not assumptions. Default design direction for review: single project-scoped OAuth grant, read-only first, machine writes optional with explicit owner-controlled permission, no autonomous human-only decisions, OAuth-off by default, existing API-token clients preserved.

## 8A. Verified ChatGPT product compatibility (not assumed user entitlement)

OpenAI's current [custom MCP connection guidance](https://help.openai.com/en/articles/12584461-connecting-custom-mcp-servers-in-chatgpt) distinguishes **full MCP write actions for eligible Business/Enterprise/Edu workspaces** from **read/fetch-only custom MCP on Pro**. Availability, individual workspace settings, app publishing and approval constraints must be checked in the actual target account; a successful OAuth sign-in does not guarantee native case creation from this conversation.

The same guidance explicitly notes that OAuth connectors need reliable **refresh-token issuance** for durable connectivity; OIDC providers typically advertise and honor `offline_access`. If Tesbo acts as the authorization server, decide whether to advertise `offline_access` and issue rotating refresh tokens for consented clients; if using an established IdP, configure its equivalent. A connected test must survive access-token expiry and must not silently keep working after revocation. Do not invent a ChatGPT callback URL; read the one supplied by the actual setup/registered client, validate it against the authenticated registration model, and pin the outcome in acceptance evidence.

Test both directions: read-only client succeeds with suitable scope, and an account/workspace that cannot use write tools never obtains a false positive official Tesbo write acceptance. Preserve the separate MCP human-only publication barriers regardless of client capabilities.
