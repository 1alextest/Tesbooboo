## 4. Authentication, capabilities and policy

An operation context retains subject kind (human session, agent token, OAuth-linked agent, narrow service identity), subject/actor ID, instance, credential ID/validity, issuer and project/task grants. The issuer is accountability metadata, not the acting human reviewer.

Authorization order:

1. Validate credential/session, expiry/revocation, account/instance status.
2. Resolve the actual resource and owning project, including indirect cycle/execution/attachment joins.
3. Check effective membership/delegated capability and current explicit denials.
4. Check requested operation and task/assignment ownership/valid lease as applicable.
5. Apply protected publication and configured human-review policy for every authored-definition/result effect.
6. Apply project/plan writability, quota and retention rules at the domain operation, without relying only on URL prefixes or HTTP verbs.

Capabilities include read, task create/edit/submit/assign/claim/progress/retest, report/evidence submit/read, analysis create/read, proposal create/read/edit/submit/comment/decision/merge, issue-copy review and agent/credential/grant administration. `04_MCP_API_CONTRACTS.md` maps operations. Human-only policy is a separate invariant; assigning a capability label to an agent does not override it.

New credential scopes omitted/empty/unknown must fail closed. Token issuance cannot exceed delegated administration rights. Migration of broad read/write tokens is explicit; do not silently convert write into all new privileges. Grant changes/revocation apply on the next protected request. Define machine-route cookie/bearer precedence so a human cookie cannot elevate a restricted agent request.

## 5. Exact approval and selected apply transaction

Extend existing zyraSaveAttempt/with-client SQL transaction boundaries:

1. Resolve authenticated human and current publication capability/policy. Reject machine approval under the default protected-project policy.
2. Acquire locks in the §10.2 order: suite-tree first when hierarchy participates, then shared envelope and actual SQL-ordered affected rows, with existing ID-allocation lock as specified. Load immutable revision and explicit stable selected operation IDs under that protocol.
3. Validate human decisions against exact revision/operation payload hashes, profile/policy versions, stable logical-operation commitment and current eligibility. Any approval-relevant change requires a new decision. Normalized duplicate fingerprints are unsuitable.
4. Compare full current authored-base token, including separately stored custom values and intended suite. Reject missing/changed targets, stale bases, invalid dependencies, unavailable suites, ID collisions or required-field failures with zero selected writes.
5. Apply only selected approved, dependency-closed, uncommitted logical operations using existing parameterized SQL validators/writers and the same transaction client. Persisted operation kind/target must match reviewed intent; no late ticket/similarity retargeting. Allocate IDs inside the transaction. Create no unreviewed destination suites before it starts and never silently relocate a case.
6. Persist definition/history/provenance, accepted result snapshots where applicable, operation states, durable idempotent receipt and mandatory audit in the same transaction. An audit failure aborts publication.
7. Commit; then perform cache invalidation, embeddings, counts, notifications and explicitly permitted integrations. Use durable deduplicated jobs/outbox where necessary for reliable retries.
8. Same idempotency key/payload returns the prior result; a different payload with the same key conflicts. Subsequent partial merges select only remaining approved operations. Rejected/pending/issue-copy items are never included implicitly.

The aggregate request remains partially merged only while actionable work exists. Rejected/withdrawn and approved-for-copy issue items are terminal review dispositions; when every item is terminal, derive MERGED only if every item is a publishing operation already applied, REJECTED if all were rejected, WITHDRAWN if all withdrawn, otherwise COMPLETED with the mixed/copy-only summary. Keep legacy generation done separate from shared review state. Retain explicit decisions for every item. Restoring an old definition creates a reviewed compensating operation; it does not erase later history or bypass protection.

## 9. Team-reviewed identity, policy and environment contracts

### 9.1 Deterministic effective authority

Human sessions keep active-workspace isolation. Machine calls resolve organization from their credential-bound project, never the issuer's mutable active_organization_id. Revalidate project/instance status, issuer's current delegated administration eligibility and instance-owner membership separately. MVP removal/demotion/loss of required delegation suspends affected credentials/active attempts on next request. Authorized ownership transfer/reissue is explicit/audited; reports and historical attribution survive. Later issuer promotion does not enlarge an existing credential's issuance ceiling.

Compute effective authority as credential issuance ceiling intersected with current instance/profile allows and resource/task restrictions, with any explicit deny winning. Instance overrides can narrow or add within that ceiling only under delegated administration; unknown/absent capability denies. Scope is exact resource by default; suite-descendant scope is an explicit grant option, reevaluated after moves. No runtime-name or issuing-user-role shortcut.

Use explicit context.profile.read for the approved references in an assigned task. Report/proposal read grants distinguish assigned/referenced work from project-wide analysis/review. List/search applies the same predicates before pagination/counts so task-only clients cannot enumerate unrelated records. Credential/grant/profile changes invalidate authorization caches for the next request.

### 9.2 Protected settings and profile lifecycle

Reuse projects.settings but reserve workflow policy and QA-format namespaces. Generic project/settings saves preserve reserved keys, reject attempted unauthorized replacement and never turn missing/corrupt policy into a permissive default. Protected changes require current policy-admin capability, server-assigned version, expected-version compare-and-set and mandatory audit. Unrelated stale environment/icon/general saves cannot erase/reset policy, profile IDs or versions. Grant tables, if normalized, remain the single grant source rather than duplicated settings copies.

Capability and QA-format profiles have draft/active/retired immutable versions. Create/clone/edit/validate/activate/retire are explicit existing-settings actions. Activation shows affected instances/pending approvals; current grants reevaluate next call while format-bound dispatched work keeps its recorded version. Retired profiles remain historically readable but unavailable for new selection. Require an authorized human reviewer/admin path to remain; an agent cannot weaken protected policy through generic settings. Migrate legacy whole-blob writers and frontend serializers, not only new endpoints.

### 9.3 Existing environment object upgrade

Current TestEnvironmentSetting is only name/url; frontend getTestRunEnvironments and settings normalization drop other keys. Add stable environment ID/context version within the same projects.settings.testRunEnvironments objects, migrate legacy entries deterministically/idempotently and update every parser/writer to preserve them. Array index/name/URL are not durable identity.

Store exact dispatched name/URL/context snapshot in prompt revision alongside identity/version. Rename/reorder/removal cannot change dispatched work or historical run labels. Removal retires selection for new dispatch while old snapshots remain; changed targets need an explicit new task revision/assignment. Validate current naming/URL duplicate rules and backward-compatible existing run labels without another environment store.

## 10. Shared publication semantics that existing save does not supply

### 10.1 Logical operation identity and exact resolved postimage

Separate stable logical operation ID from immutable operation revision ID. A logical publishing operation can commit once across revisions, enforced by durable unique commitment linked to receipt. Previously committed A copied into revision 2 is a historical reference, not a new eligible write, even with a new idempotency key. A new intended correction is an explicit compensating operation against current official base. Do not use content-hash deduplication to collapse intentionally distinct cases.

### 17.2 Architectural synthesis: compose, do not replace

1. **Core domain: Tesbo owns** user/project/session IDs, participant grants, document versions, QA task/attempt, immutable reports, staged proposals, decisions, official cases/results/Bugs, audit and outbox/job receipts. PostgreSQL remains the authoritative system; existing BullMQ/Redis handles event/outbox dispatch. Reuse existing `zyra_chat_*`, `ai_generation_requests`, version/attachment services, rather than proxying all truth into a third-party agent framework.
2. **One web UI:** upgrade existing Zyra/Copilot shell; consider assistant-ui **only** as composable presentation primitives after proving it does not duplicate or replace Tesbo routing, history, auth or design system. AI backend selection is not executor assignment. Streamed external tool events are linked to Tesbo event identities.
3. **LLM layer:** reuse existing model provider catalogue/API integration for native chat; a user-managed coding agent is a separate runtime, and optional hosted agent workers are a later independent deployment choice. The external MCP channel stays usable with no native inference subscription allocation for already-authorized non-LLM task/report operations.
4. **Test execution:** User-managed OpenCode/Hermes/OpenClaw/Claude Code/Codex/Kimi or another compatible agent first claims a scoped task via Tesbo MCP (or verified adapter), executes using its **own** browser/Playwright/API/mobile tools and returns an original report. Agent MCP support or a supported plugin/transport bridge must be verified for each runtime; agent registration alone cannot start it. Hosted workers may use Stagehand/Midscene/Playwright or another supported adapter; report outputs normalize to one Tesbo-owned immutable receipt/evidence contract. **AI interactions alone do not certify assertions**: preserve exact expected/observed comparison, deterministic checks where possible, explicit `UNKNOWN/BLOCKED` and human review.
5. **Workflow protocol boundaries:** MCP = Tesbo tools and executor's target-tool interfaces, AG-UI = optional realtime model/agent UI event projection, A2A = optional peer-agent exchange, ACP = optional agent interface where supported. None replaces authoritative domain lifecycle. No browser-side arbitrary CLI/shell API.
6. **Target access belongs to executor:** If a user-managed agent can already reach an application (including through its own established VPN), Tesbo does **not** need VPN plumbing, tunnels or target-host routing. The user-managed agent retrieves work and uploads reports through internet-accessible, authorized Tesbo MCP. **Only** managed/other remote workers that lack target connectivity need optional target-network planning; never open an unrestricted public tunnel. Capture network-scoped worker trust, credential and egress boundaries, evidence storage locality, cancellation and disconnection recovery. No machine-side Tesbo companion is part of standard user setup.
7. **Cost, security and maintenance:** server-side sandbox isolation, per-project credential/target allowlist, short-lived capability, model budget, network egress, quota/retention, kill/cancel, audit; evaluate upstream cadence, backward compatibility and package impact before dependencies.

### MBT-C-01 — Finite state semantics and supported capability boundary

M1 supports ordinary finite state machines and directed journeys with fixed, explicit actor/fixture bindings. M2 may enable bounded EFSMs only after the interpreter passes the fixtures below. Permission/decision models compile to the same finite semantic representation; no separate decision runtime is promised. Every model and adapter declares a versioned capability set. Unsupported constructs fail validation with `UNSUPPORTED_SEMANTICS`; they cannot silently degrade into an ordinary edge traversal.

An EFSM configuration is `(stateId, sharedValuation, actorValuations, immutableBindings)`. Each variable has a unique stable ID, explicit SHARED or ACTOR scope, type, finite domain and initial value for every bound actor. Integers have inclusive finite bounds; enums/strings have enumerated finite domains. Secret values are credential references, never model variables. Actor IDs and role-policy revision are pinned input, not inferred from the authenticated Tesbo principal. No implicit actor change is allowed within a transition.

One sequential model step has this exact order: evaluate source invariant and precondition against the pre-state; evaluate the guard; calculate all declared assignments from that same pre-state; apply assignments simultaneously to a candidate valuation; validate types/domain, destination invariant and declared postcondition; then admit the symbolic transition. An unassigned variable retains its value. Duplicate assignments to the same scoped variable, undefined symbols, unbounded domains, impure expressions or out-of-domain results are invalid. Guard FALSE means infeasible for that configuration; evaluation error means INVALID, never FALSE or PASS. Postconditions assert the candidate state; they never solve missing assignments. Branches are separate stable transition IDs, not unspecified nondeterministic effects. State equality includes all valuations and actor bindings; a generator cannot merge distinct valuations because their state labels match.

Symbolic effects describe the expected model only. A separately authorized adapter performs target actions, records pre/post observations and evaluates the independently approved oracle; a symbolic assignment does not prove a target change. Actual observations cannot silently mutate the expected valuation to make an assertion pass. Disagreement is a recorded mismatch or UNKNOWN when required observation is unavailable.

Each independent generated path starts from its declared initial valuation and fixture revision. Before target replay, the adapter must establish/verify the fixture baseline through an authorized reset or prove the declared precondition from observations. Reset is a separate recorded operation, cannot delete prior evidence, and failure blocks the path. Sequential multi-actor paths may use explicit actor switches between transitions while sharing SHARED variables; they do not establish concurrent safety.

M1/M2 do not support virtual time, asynchronous event scheduling, eventual-consistency windows, interleaving exploration or race-coverage claims. Such requests return `UNSUPPORTED_SEMANTICS`. A future capability must specify clock/event ordering, bounded observation windows, schedule/reset identity and replay semantics before enabling them. Independent concurrency testing of Tesbo's own authorization/activation/job mechanisms remains required; this scope limit does not waive those tests.

Hand-calculated fixtures: (a) `remaining=1`, reserve guard `remaining>0`, effect `remaining:=remaining-1`: first reserve yields 0, a second reserve is infeasible; (b) two actors share remaining: sequential A reserve prevents B reserve; actor-local counters do not change each other; (c) reset restores remaining=1 for the next independent path; (d) `x=0`, increment then guard `x=1` admits the second step; (e) duplicate assignments, overflow and undefined actor are invalid; (f) a requested concurrent reserve race is UNSUPPORTED, not “covered.” These fixtures discriminate feasible-path correctness from simple edge visitation.


### MBT-C-03 — Validator classes and exact coverage arithmetic

FATAL errors block approval/generation: invalid schema/IDs, dangling endpoints, missing required initial configuration, invalid domains/assignments, unsafe AST, unauthorized cross-project reference, unsupported semantics, missing normative oracle or unresolved authority for a claimed normative assertion. Diagnostics include stable code, element/configuration identity and reason; input/security failures persist no partial imported model.

An unreachable element, guard unsatisfiable in a reachable configuration, disconnected component or dead end is a semantic diagnostic, not automatically a fatal syntax error. It remains unresolved until corrected or explicitly accepted as an intentional exclusion on the exact revision by the authorized reviewer with reason and source. Unresolved diagnostics block approval of a model claiming complete normative scope. A prohibited operation is a negative assertion with an expected refusal/invariant, not a successful traversable edge. Negative assertions have their own denominator and observed refusal oracle.

For a requested finite revision/scope and dimension, partition all elements into disjoint known eligible E, approved excluded X, unresolved eligibility U, and outside-request O. Unknown inventory cardinality is separately flagged. The eligible set is computed from approved semantics/bindings, not from which cases happen to exist or which paths the generator visited. Independently compute mapped M, selected S, observed T and verified V subsets of E; no stage implies another. Report counts and `|M|/|E|`, `|S|/|E|`, `|T|/|E|`, `|V|/|E|` separately. Known subset percentages may appear only as “known eligible subset,” with unknown count prominently visible.

### MBT-C-04 — Deterministic traversal and bounded native jobs

Deterministic inputs are canonical model bytes/digest, semantic schema/interpreter version, generator/version, seed, ordered strategy parameters, actor/role-policy and fixture revisions, initial configuration, objective, scope and logical limits. Canonical serialization defines stable ID ordering (UTF-8 byte order), adjacency/queue tie-breaking, seeded PRNG/version and finite value enumeration. The engine counts each candidate transition guard/effect evaluation as one work unit, including infeasible candidates; stops before exceeding maxWorkUnits, maxPathDepth, maxPaths or maxInputCombinations; and records units consumed and the exact deterministic stop reason. Limits are part of the input digest. Each engine version must specify its strategy ordering; libraries with nondeterministic output cannot claim deterministic support.

Equal deterministic inputs with no emergency interruption produce byte-equivalent ordered path/configuration/valuation output and deterministic stop fields. Operational envelope fields (job IDs, timestamps, host, duration, telemetry) are outside that equivalence and outside the logical manifest digest. Execution observations are never included in this deterministic-output promise. Wall-time, memory, CPU or provider interruption is an emergency protection: return PARTIAL with `EMERGENCY_RESOURCE_CUTOFF`, observed prefix and diagnostics, never a deterministic-completion claim. Delayed evaluation with adequate emergency allowance must produce identical logical output; a forced timeout may differ and must be visibly partial. M2 promises replay from the beginning, not opaque resume; resumability requires a later versioned frontier/counter/PRNG checkpoint contract.

Reuse Tesbo's native task/job, BullMQ, project-limit and audit owners. Before admitting any generation/retry, reserve bounded capacity atomically against BOTH project and platform active-work/rate/spend quotas. Charge actual work/tool/provider consumption cumulatively across attempts, without double charging duplicate command receipts or refunding consumed work after cancellation. Admission failure returns `429 RESOURCE_LIMIT` plus retry guidance and causes no automatic follow-up. Unknown or unset safety caps disable generation with `503 RESOURCE_POLICY_UNCONFIGURED`; there is no uncapped default. Numeric defaults, fairness and p95 objectives must be measured and ratified for the two-domain pilot before M2 activation; no measurements are claimed here.

Native jobs follow QUEUED → RUNNING → COMPLETED/PARTIAL/FAILED/CANCELLED. Cancellation first records CANCEL_REQUESTED (nonterminal), prevents new claims/actions, then reaches CANCELLED after fenced ownership reconciliation. Lease expiry ends the old attempt and fences its writes; retry creates a new attempt under the same logical request with a new generation, subject to cumulative budget and retry cap. Terminal states are immutable. Every heartbeat/result/attachment publication checks project, attempt and lease generation transactionally. A late worker cannot publish, release another worker's reservation or consume fresh credentials. Release unused reservation exactly once at terminal reconciliation; shared active slots are not freed merely because an old process missed a heartbeat while its effects are uncertain. Admission counts unresolved in-flight effects until reconciled. The native job owner is responsible for orphan lease accounting, backlog/age/stop-reason telemetry and bounded operator recovery; no second scheduler/job store is introduced.

### 10. Skills governance architecture and seven-domain lifecycle

#### 10.1 Two separable invariants
1. **Skill identity and immutable revisions:** skills are versioned native content; the agent's only skill mutations are additive candidate creation/proposed successors. Creation, editing existing version payload, approving and publishing are distinct verbs.
2. **Effective assignment authority:** a separate typed binding resolves exact approved skill versions to module/subtype/audience/project operations. Activation/deactivation/assignment, precedence and root protection are *never MCP-writable*. The human-governance endpoint must reject machine principals even when the token owner is a human administrator.

A Skills-authoring meta-skill is itself a governed artifact, but initial bootstrap and successor promotion use an independent human-controlled root trust anchor, not a recursive skill loop. The root can be replaced only by a separately authorized and evidenced governance decision.

#### 10.2 Application and source boundaries
- **Manual:** module/user group/internal-external distribution/ACL and artifact subtype are orthogonal. Internal instructions, developer manuals, external customer instructions, partner manuals and support runbooks are not one indiscriminate template.
- **Policy:** internal application/business/governance policies and external-facing or externally mandated policies are distinct in audience, source of authority, required sign-off, jurisdiction and scope; an externally mandated rule can be handled by an internal enforcement policy while external-public display remains separate.
- **Project-specific adaptations:** portable core and scoped adapter may compose by a human-approved rule. No "last matching skill wins" and no candidate skill can override the root, change the module assignment or supply its own authority.
- **Agent control:** a governed authoring call pins effective assignment IDs, skill version IDs and hashes in the candidate and Change Packet. The native service revalidates binding before submission/promotion; stale means `SKILL_CONTEXT_STALE`, ambiguity means `SKILL_ASSIGNMENT_CONFLICT`, and absent mandatory mapping means `SKILL_UNASSIGNED`.
- **Prompt injection:** a skill candidate is untrusted input until approved and assigned, and external files never inherit instruction authority just by being cited. Effective skills are signed/digest-bound read results; references, assets and examples remain data.

- `artifact_skill_usages`: durable immutable provenance edge per artifact/content version; migration unknown marked UNKNOWN.
- `skill_effective_resolution`: derived read model only, no authored parallel truth.
These are **logical entities**, not a mandate to create six new tables. Use existing KB/history/graph/audit models first, add narrow constrained metadata where proven necessary.

### 11. Hybrid source-change detection and reconciliation — Kiro precedent, Tesbo implementation
**Source-owner reuse:** The existing project source binding, current-cache graph capture/history, `GraphChangeReviewController`, native notification writers and Zyra review feed remain the canonical Tesbo sources. Integration adapters supply observations only; no second repository record system.

**Observation channels and trust:** (a) optional client events such as file save, task completion or agent stop, with exact supported wire event names and security scope discovered for the installed client/version, (b) source provider webhooks for push/PR/merge and repository identity, (c) CI build/check callbacks, (d) deployment/incident provider events when installed, (e) explicit Tesbo MCP capture or human rescan. These channels are complementary, not redundant claims of exhaustive coverage. Not all tools/IDE surfaces support hooks. **Do not require a client hook to prove that a commit exists.**

**Logical normalized receipt** (exact schema delegated to native data/service discovery):
```json
{
  "projectId": "from-authenticated-source-binding",
  "sourceBindingId": "stable-binding-id",
  "configurationRevision": "immutable-configuration-at-original-observation",
  "sourceType": "agent_hook|repository|ci|deployment|manual_reconciliation",
  "sourceEventId": "stable-provider-id",
  "deliveryId": "dedupe-key",
  "sourceRevision": "git-sha-or-provider-version",
  "sourceScope": {"repository": "owner/repo", "ref": "refs/heads/..."},
  "observedAt": "UTC",
  "sourceOccurredAt": "UTC-or-unknown",
  "actor": {"principalId": "verified-or-null", "agentId": "attributed-or-null"},
  "evidenceClass": "tesbo_observed|provider_attested|agent_reported|derived_inference|unobserved",
  "processing": "received|reconciled|incomplete|rejected|superseded",
  "gap": "none|unknown-range|unsupported-source|stale|authorization-failed"
}
```

- Verify source/project binding on each receive and on reconciliation. Reject an unbound remote repository, spoofed source IDs, replaying stale head across environments and cross-project scope.
- Deduplicate by provider/scope/sourceEventId+content identity; record gaps and conflicting branch/head observations; do not order by local arrival time as if it were causality. Repeated file-save events for the same eventual commit may coalesce, but never erase meaningful separate source revisions or reported errors.
- Provider reconciliation detects source commits with no corresponding current successful capture for *known authorized tracked sources*. Where the repository is unreachable or permissions are revoked, result is `UNKNOWN`, not `UNCHANGED`.
- Source-change detection may suggest *review*, never directly mutate approved requirements/testcases/policies or set release readiness to ready. Capture acknowledgments and queue delivery use the existing graph history/notifications and outbox/worker substrate, backed by replay and dead-letter monitoring.
- Multi-repository/dependency scopes are configured explicitly; report `impact_incomplete` for unbound sibling repos. Historical captures are never rewritten by later source events.

### 12. Agent activity, claims and the human Change Workspace — GitLab precedent
**Existing owner:** Zyra's sessions/task/activity, graph review and native change linkage; no separate assistant/agent database. Externally connected coding agents may publish authenticated telemetry or scoped MCP calls without being granted UI-human powers.

**Evidence-level event vocabulary:**
- `tesbo_observed`: authenticated Tesbo MCP/REST operation, authorized native UI action or internally executed job with durable receipt.
- `provider_attested`: signed/authenticated repository/CI/deployment event with verifiable origin and scoped payload.
- `agent_reported`: content submitted by an agent describing work or execution not independently observed by Tesbo.
- `derived_inference`: graph/LLM analysis whose premise and confidence/limitations are inspectable.
- `unobserved`: no trustworthy observation (not a failed test, success or "agent did nothing").

Each timeline entry carries work/change/session/attempt identity, originating authenticated principal (distinct from delegated model/runtime), operation type/target/scope, source revision/build, causality parent, event time/ingestion time, retention/visibility class, redaction policy, outcome, linked evidence and explicit missing observation. Do **not** claim access to hidden chain-of-thought, uninstrumented local tool calls or secret agent prompts. Detailed traces are opt-in/permissioned; project owners can review aggregate progress without seeing restricted evidence.

**Human experience:** Reuse Tesbo project navigation and existing `Zyra` change review. A Change Workspace summarizes one change as:
1. intent/approved expectation vs proposed interpretation;
2. source diff/PR/build/deployment identities with observed/unknown markers;
3. current agent/session and task status; next responsible humans;
4. impacted requirements, cases/models, policies, manuals, files, issues and skills with version/diff status;
5. verification scope and actual results/evidence/known target;
6. blocked/unconfirmed links, risk, decision trail and pending approvals;
7. release-readiness reasons and post-deploy monitoring/incident follow-through.

The same canonical records support role-appropriate developer, solo coder, QA, BA, PM, policy/security, operations and executive views. A high-level release view must **not** reveal private document history or raw tool trace content. `Blocked`, `Awaiting approval`, `Unknown` and `Observed success` remain visibly distinct; users can drill into the proof.

### 14. Cross-artifact consistency and independent truth — Spec Kit precedent
A read-only cross-artifact analyzer operates on typed **approved source obligations and their known revisions** plus code/source/graph observations, case/model links, docs, issue tasks and run evidence. Correct semantic disagreements at the owning artifact, never silently change the authoritative policy to match current code.

**Classification:** `confirmed_conflict`, `unresolved_conflict`, `missing_link`, `stale_reference`, `unknown_source`, `not_applicable`, `no_detected_issue`; the last classification means **only** that this bounded analysis found no supported discrepancy. A source diff can propose a new requirement interpretation, but it cannot itself become a normative oracle. Semantic comparisons require rationale, evidence tier, uncertainty and responsible reviewer, not a blanket LLM pass.

**Completeness boundaries:** first inventory material user goals, actors, states, interfaces, upstream/downstream consumers and negative/recovery paths. Maintain a denominator of assessed vs missing/unverified scope. All change candidates point to canonical records and existing graph; none automatically reclassifies historical executions. Report coverage separately for authored cases, approved cases, execution, deployed target validation and currently reviewed requirement revision. Re-run bounded consistency on relevant source/policy/requirement/skill head changes.

### 15. Release readiness, after-release outcomes and DORA-style metrics
**Reuse:** existing runs/executions/bugs, reports/dashboards, project releases and Graph/Zyra change review as applicable; extend one project-level role-sensitive reporting projection. Do **not** invent a new release-authority database or allow an LLM to determine whether production is "safe."

**Proposed readiness evidence dimensions:**
- source PR/commit and signed/observed target deployment identity;
- applicable current approved requirements and policies; missing or conflicting obligations;
- case candidates vs approved revisions and selected run manifest;
- actually run tests, pass/fail/block status, independent evidence bytes and environment/build;
- active high-severity Bugs, change/regression scope, unresolved impact and known exclusions;
- outstanding role approvals, rollback/forward plan, responsible human and accepted risks;
- post-deployment smoke/monitoring/incident visibility and freshness.

**Readiness vocabulary:** `not_assessed`, `insufficient_evidence`, `blocked`, `ready_for_authorized_decision`. Deployment and human decision are separate axes under ASER-C01. `released_with_known_risks` is a derived observed-release label, not a readiness value. Pre-deployment assessment uses the tested candidate build; post-deployment acceptance requires the observed deployed build. This prevents both fabricated production verification and a circular requirement for production evidence before initial deployment approval. A release authority approves a fixed readiness snapshot, candidate build and risk set. Changed evidence after approval creates a new decision context, never silently replaces the historical approval. Unknown deployment/monitoring is not marked passed.

**Five evidence-backed delivery measures:** change lead time (commit to successful production deployment), deployment frequency (qualifying successful production deployment/activation events per interval under a versioned provider-normalization rule; a later smoke failure or incident does not remove that deployed change), failed-deployment recovery time (duration to restore after a production change failure), change fail rate (qualifying failed production changes / qualifying production changes), deployment rework rate (unplanned remediation deployments / deployments, under an explicitly documented measurement rule). Source IDs, service/production-environment scope, time zone, observation window, denominator, normalization version and missing/censored data are visible. Distinguish pipeline attempts that never reached production from deployed changes that subsequently fail. Deduplicate delivery events, retain rollbacks/remediation as qualifying changes under the declared rule, and leave unresolved recovery intervals censored. Do not exclude a production failure to improve an apparent rate. These two outcome groups—throughput and instability—must not be collapsed into a misleading single score. A configured project without deployment integration gets `NO_DATA` not zero failures. Improvements in those figures do not alone establish a causal effect of Tesbo.

**Human oversight measures:** time to understand/approve a change, review cycles, unverified-agent-assertion corrections, stale-manual/requirement detection, duplicate artifact rate, incident escape and cost per synchronized change. Collect only what the user/organization authorizes, and avoid incentive gaming (e.g., fewer tests to improve apparent lead time).

### 1. User jobs, actual categories and orthogonal axes
A human project/workspace owner assigns governed instructions to the modules and narrower contexts that agents author. Agents consult those instructions when proposing requirements, test cases, manuals, policies, tasks/issues, and files/evidence. Humans govern which instructions are active. Skills themselves are also authored under a *skills-authoring meta-skill*.

**Classification dimensions must not be conflated:**
- `module`: requirements | test_cases | user_manuals | policies | tasks_issues | files_evidence | skills.
- `subtype` within a module: requirements functional/nonfunctional/business/technical/regulatory; tests manual/automated/API/security/performance/accessibility; manuals end-user/staff/admin/support/developer/operations; policies product/business/organizational/security/regulatory/customer-facing; tasks work/bug/investigation/change; files evidence/source/test data/attachments; skills authoring/distillation/evaluation/maintenance.
- `audience`: internal, external, partner, public, mixed (multiple audience bindings allowed).
- `authority_origin`: internal decision, contractual, regulator/statute, standard, external provider; **not** synonymous with whether a policy is externally published.
- `exposure`: private/restricted/shared/public, independently governed by native authorization and information classification.
- `applicability`: workspace/project, system/module/feature, actor, operation, jurisdiction/locale, environment, phase and product domain, as supported/verified.
Examples: an internal operator manual with an external legal source; an external-facing privacy policy that is internally approved; a customer manual for administrators only. A label must not grant public access or normative authority.

### 2. Canonical owner and records
The canonical governed-guide/skill owner is **T-422 / D-14 QA Standards & Playbooks**, extended by FR-076/077/106–113 and T-448–453. One resolver serves native UI, Zyra, REST and MCP. Project-specific authored text reuses current KB document/attachment identity with an explicit immutable submitted/accepted snapshot extension. Ordinary coalesced edit history alone does not meet that invariant. The platform-approved pack and workspace pin retain their distinct scopes; no fake project or copied global core content is permitted. Add typed governance metadata and indexed assignment relations only where necessary. Never duplicate byte stores or let a graph projection become the authority.

Each **skill identity** has stable `skillId`, name, purpose, origin (native/imported), provenance, owning scope, owner, compatibility constraints and zero or more immutable version records. Each **skill version** has `skillVersionId`, parent/head reference, revision number/content digest, normative instructions, references/assets, creation actor and source evidence, supported modules/subtypes, applicability predicate, dependencies, anti-patterns, examples/counterexamples, required input/output contract, validation/evaluation evidence, and status. A newly created skill is a **candidate**, not an active instruction. Version sequence and draft-iteration sequence are distinct; rejected/abandoned candidates never become published versions.

A **skill assignment** is a *separate governed record*: `assignmentId`, exact `skillId+approvedVersionId`, target workspace/project/module/subtype/context predicate, priority or composition rule, active/inactive state, effective interval, assignment policy/approval receipt, actor and immutable history. Disabling one assignment does not delete/inactivate the underlying skill or silently disable its use in other contexts. Global skill availability, version approval, binding activation, and per-project applicability are four different facts.

An artifact revision and Change Packet record the exact **resolved effective skill set**: assignment IDs and versions, skill version IDs, digests, resolution outcome (matched/not applicable/conflict/unavailable) and timestamp/revision. A later skill or assignment change cannot rewrite historical provenance.

### 4. Governing Skills itself: protected bootstrap
A governed **skill-authoring meta-skill** tells agents how to structure a candidate: goal, scope/trigger, reusable principle, context-specific application, required evidence, invariants, prohibited assumptions, input/output examples and counterexamples, admissible exceptions, validation/evaluation and review receipt. **Principle-based generalisation** means distilling the transferable reasoning/failure mechanism, not importing application-specific conclusions or merely accumulating incident instructions.

The root meta-skill plus its promotion rules are **human-governed and server-protected**. Changes use a separately reviewed successor with independent approver(s), version pin, executable negative fixtures and a non-self-referential trust anchor (e.g. reviewed release/security policy). An agent-created meta-skill candidate cannot validate, approve, supersede, enable or assign itself. There is no automatic `skills -> skills -> ...` recursion: resolve the designated approved root once per authoring operation; reject unresolved cycles or self-dependencies.

Projects may extend the portable core with versioned, lower-precedence project adapters. Adapters cannot relax root security, provenance, required evaluation or approval constraints. An external agent instruction (`AGENTS.md`/`CLAUDE.md`) is only a trigger; it never supersedes the server-enforced effective assignment.

### 5. Resolution, composition and changes mid-flight

#### 12.1 Candidate repair without mutable history

### 13. Skills within the connected delivery assurance workflow

#### 13.1 Role of skill versus role of tool/event
- A **skill** prescribes a reviewed authoring/evaluation method for an applicable module, versioned and assigned only through human governance.
- An **agent hook** is an optional client-side event producer (e.g. Kiro-style task/file events), never a module-skill assignment tool, evidence of full external agent behavior or official write approval.
- A **source/CI provider event** is a scoped, separately authenticated observation of code/build/deployment state, not a request to invent requirements from observed code.
- A **composite MCP tool** invokes several native Tesbo domain actions under the same effective skills and role/approval checks; it has no elevated governance authority simply because it is one call.
- A **consistency analyzer** compares observed/inferred behavior against independently authorized requirements/policies; its output is a review candidate, not a newly approved normative source.
- A **release-readiness calculation** combines independently sourced status/evidence and human decisions, never an AI certification or automatic proof of defect-free software.

#### 13.2 Governing skill resolution in a multi-step composite workflow
Before authoring, the agent retrieves approved effective skill IDs, immutable version IDs and digests per **applicable** module and subtype. A partial transaction preserves skill provenance for items that committed and leaves all other items explicitly failed, uncertain or not-attempted. An exact duplicate reads the existing logical receipt; explicit resume follows ASER-C04 and never replays committed operations. On resume, changed effective skill heads require conflict/reassessment; restoring client cache alone cannot authorize stale publication. A raw provider/agent event does not become a newly skill-authored artifact solely because it was observed.

#### 13.3 Source-package interoperability and safety boundary

Library records must preserve a versioned package digest, attachment hashes, supported agent/engine capabilities and dependency/version constraints. **Executable skill resources are disabled by default** until independently authorized sandbox execution and scan/policy controls are implemented. A human approving skill text does not grant executable scripts/network/MCP tool privileges.

An imported skill is an inert candidate. It does not become active because an external agent includes it in its local context or uploads it to KB. Only explicitly approved Tesbo assignment records govern the module.

### Effective stopping, monitoring and recovery

Resolve the stop's accountable actor/policy and exact task/project/descendant scope. Persist its control event and fence current authority before acknowledging that future protected effects are denied. Reject new claims, delegated starts, protected writes and relevant credential renewal/use; recheck queued work at its actual effect boundary. Record in-flight effects that may have committed before the fence, delayed responses and unreachable external clients as uncertain until reconciled. Do not promise reversal or instantaneous termination of arbitrary external services.

Stop controls must survive a failed or compromised worker and remain separate from its credentials. A task-scoped stop cannot terminate a shared host/process or another tenant's work without the separately required service authority. Deny new protected work, preserve an independent control receipt where possible, disclose any audit gap and reconcile it after recovery. Preserve affected evidence, secrets rotation where indicated and cleanup verification. Unaffected authorized work remains available according to policy.

A model may advise on suspected drift but cannot silently widen authority or become the sole judge of malicious intent. ### Unit, expectation and dependency basis

Multiple contribution profiles may share lifecycle obligations without sharing an execution mechanism. Stay within the existing modular application and domain services. First-party compiled extensions, inert content packages, remote adapters and isolated third-party execution are alternatives to evaluate, not four mechanisms selected for implementation.

### Registration, identity and composition

Use stable namespaced plugin and contribution identities, exact artifact version/digest and provenance, compatible host/protocol ranges, declared extension points and required/optional package dependencies.
