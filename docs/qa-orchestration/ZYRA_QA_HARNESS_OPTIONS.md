# Zyra QA harness options

**Status — proposed for product review.** Each option has its own adoption decision. The recommended first experiment is a read-only assertion comparison. This document authorizes no implementation, customer trial, active Skill change or mandatory approval gate.

For an end-to-end example, see [One stale save, from task to human review](examples/zyra-stale-save.md). It includes a runnable Node.js harness, five observed outcomes, the proposed reviewer view, and the existing Save behavior.

| Option | Decision the tester can make | Smallest useful proof |
| --- | --- | --- |
| Assertion adequacy | Would this case detect the particular defect I care about? | Compare one assertion against approved correct and faulty observations. |
| Evidence-aware run analysis | What happened on this attempt, and what check would change my decision? | Reconstruct one failed-then-passed case with a deliberately unbound attachment. |
| Skill and client regression | Does a candidate Skill preserve the required output and behavior across our team’s clients? | Compare active and candidate versions on the same tasks in two independently capable clients. |
| Customer-agent evaluation | Did our agent achieve the authorized outcome and stop where it should? | Observe one repeatable task in a customer-authorized disposable environment. |

## What to reuse before building

The [builder comparison and exercised Playwright controls](reviews/zyra-harness-prior-art.md) establish the starting point for each option.

- **Assertion adequacy** starts with the existing versioned proposal reader and two independently graded controls. Stryker is already configured for a different code path. A fault-specific fixture must earn its own evidence.
- **Run analysis** starts with a stock Playwright JSON report. It already preserves individual retries, errors and attachments. A two-project control demonstrated that case ID plus retry number collides. Map the CI run, reporter project, test, attempt and native case revision before attributing a result. Treat a healer’s proposed skip or assertion change as a draft edit requiring review.
- **Skill regression** can use Promptfoo as an external trial driver once representative clients and comparable tasks are available. Compare against the native fixture and evaluate an existing Langfuse destination only where its incremental value and data handling justify it. A direct model call is insufficient evidence of client conformance.
- **Customer-agent evaluation** can reuse independent state and action grading, as demonstrated in Sierra’s τ²-bench. Customer-approved rules or reference actions establish the expected state. An independently authorized reader observes what the agent actually changed. Actions requiring review receive their own checks even when a refused action leaves the same final state.

A full agent runtime is a later adapter decision. Keep the existing Zyra task as the durable record. If a pilot needs a worker to wait for new evidence, resume on a matching event, recheck the member and revision, and consume the pending action once.

For a QA evaluation, try **Promptfoo** as the test runner. Start with recorded observations and a trusted deterministic grader. Keep unavailable evidence and deliberate fault detection distinct from an ordinary failing assertion. The existing Zyra service remains the baseline. It can be hosted inside a team-controlled process. Bind its permitted tools to Zyra’s existing readers and proposal services. ## How a tester reaches review

The harness is a bounded extension of Zyra’s existing decision loop. An evaluation uses controlled tasks to measure Zyra, a Skill/client combination, or a customer’s agent. A team can adopt an individual option without deploying a general agent platform.

1. **Open the work.** From **Agents → Tasks → Create task**, use the existing project and task purpose. Today this route starts case generation using the project model allocation. In the proposed flow, open the resulting task detail and select a draft item to assess. An authorized MCP member may resume the same shared batch by ID. Checking an existing item must never silently start another generation or create another batch. If generation lacks a model allocation, show that limitation. A reviewer can still inspect an existing authorized batch through its native review surface. When no batch exists, offer a supported manual task route only if it is available.
2. **Establish what should happen.** Through permission-scoped readers, resolve the task, stable item and target IDs, the expected draft revision and any existing target case revision, effective Skill assignment/version/digest, and approved criterion or policy for that scope. Record source versions and effective dates. Use the shared draft for the assertion under examination. Build the independent expected outcome from pre-existing approved sources. If those are missing, contradictory or outside the member’s access, qualify the result and identify who can decide. Withhold private chat, candidate-authored expectations and hidden scoring labels from the independent first pass.
3. **Choose one useful check.** Zyra identifies the uncertainty, a permitted observation, and which outcomes would change its recommendation. The backend determines permitted tools and data destinations, checks the current grant at each action, and enforces step, time and cost limits. The default pilot reads recorded evidence. Executing a test needs an authorized, capable external runner and the existing dispatch flow. A specialist, if selected, receives one bounded question and a scoped evidence view. Persist its attributed observations, disagreement or timeout. Compare its added value against one ordinary Zyra pass before adding another specialist.
4. **Return a finding to its owner.** The task or Run presents the question, observed outcome, evidence limits, affected item/revision, and the next action a human can take. Link to accessible evidence. Distinguish what was observed from what Zyra inferred. Use existing Tasks, Runs, Skills and review surfaces. The optional graph view may prioritize another check using existing gap records. A nominated path establishes planned work only. An inaccessible source must not leak through summaries, counts or links.
5. **Propose and decide.** A read-only check has no draft effect. A requested repair stages an attributed edit in the existing Zyra draft. The human sees a field-level diff, the evidence supporting it, their permitted action and the effect of selected Save. Revalidate the current member, expected revisions, effective method and dependencies for the selected items. A concurrent material change expires the affected check. Preserve earlier evidence as history, recompute dependent assertions, then invite a new decision. A newly saved case enters the native repository as Draft. Formal case approval, Run admission, execution, Bug classification, Skill activation and release decisions each belong to their existing owners.

The native technical writer, authenticated member or service principal, originating client and grant, model/specialist, runner and deciding human have distinct provenance. Two people sharing one MCP client retain distinct member IDs. One member using two clients retains one member ID and two origins. A shared service credential supports service attribution until an independently verified human delegation exists. Client-provided display names cannot supply missing authorship. The collaboration owner defines legacy drafts, selection, streaming and closure behavior. [Shared-draft contract](../specs/agent-synchronized-engineering/mcp-change-workflow.md) · [MCP team attribution](../specs/agent-synchronized-engineering/mcp-team-attribution.md)

## Assertion adequacy

**User outcome.** A reviewer can see exactly what assertion would overlook a particular fault and can inspect a proposed repair. Scope the conclusion to the named obligation, assertion, fault and observation method.

Use an approved requirement, an independently adjudicated correct/faulty pair and the exact proposed assertion. Keep the decision on the expected outcome independent of the assertion author. Record how the pair was produced. A reviewer reading a pair of records can assess a case design. A claim that an executable assertion detected a real defect requires matching execution evidence for both variants. During design review, identify an unsaved case by its stable draft item and revision and record that it has no native target yet. For execution, capture the assertion ID or step, actual values, build, fixture and attempt. To claim native case coverage, match the exercised assertion content to the exact saved case revision. An isolated execution of unpublished content can support only a claim about that draft revision. An unrelated failure or a timeout earns no credit for the target assertion.

| Correct control | Faulty control | Finding |
| --- | --- | --- |
| Accepted | Rejected by the intended assertion | Detects this fault under the stated conditions. |
| Accepted | Accepted | Misses the fault. Show the unchecked observation. |
| Rejected | Rejected | Rejects valid behavior. Investigate setup and assertion before taking credit. |
| Rejected | Accepted | The assertion favors the wrong outcome. Revisit the rule or implementation. |

If **either control** is absent, invalid, mislabeled or unobservable to the independent verifier, or the target assertion never runs, the pair cannot be graded. Record the reason and exclude it from the graded denominator while showing its count. Once the verifier establishes that the pair really differs, an assertion that accepts both is a counted miss.

**First fixture.** Bob opens draft items A, B and C and selects B. Alice removes A before Bob saves. Use an explicitly approved stale-write rule for this fixture. In the correct outcome, Bob’s stale save is refused and the state of B and C is preserved. In the faulty outcome, C receives the edit intended for B. An assertion that merely observes a completion notification common to both outcomes misses the fault. The repair reads back B and C by stable ID. On a fresh, deliberate edit it verifies the intended change to B and preservation of C. Assert the official case revision separately while work remains unpublished. Claim preservation only for the observed records unless a complete authorized change set supports more. Include a conforming fresh save, an unknown expected behavior and a case where a different assertion fails first. [Source journey and historical service fixture](reviews/PR264-application-journey-review.md#git-style-collaboration-follow-up)

**Selection decision.** Start offline with the weak and repaired assertions on recorded pairs. Advance to one isolated executable Playwright case only if reviewers make better decisions within the agreed cost and false-block bounds. A manual comparison establishes design evidence. Live product coverage requires the exact observed run. Use the existing T-458/T-459/T-461 and QA-473/474/481 proof paths; equivalent variants, unreachable faults and runner faults remain visible in their own counts. [Canonical proof owners](05_IMPLEMENTATION_BACKLOG_AND_TEST_PLAN.md)

## Evidence-aware run analysis

**User outcome.** From the native Run result, a tester can see which attempts support a finding and select the cheapest next check that can distinguish the remaining explanations. Return one recommendation with its rationale, evidence references and a stop condition. Valid dispositions include no further action, investigate the environment, request a particular missing observation, or stage a defect candidate for triage.

The Playwright reporter resolves the case ID and sends result status and retry count. Its case summary keeps the last outcome. Its upload identifies Run and case. With only that information, a final pass after retry and a screenshot cannot establish which attempt produced the screenshot, the cause of the first failure or whether the feature under test was reached. An attempt-bound CI record can supply the missing link. Preserve the original result when a retry passes. A retest after a fix creates a linked attempt/run with its own build and evidence. [Reporter result handling](../../sdk/playwright-reporter/src/index.ts) · [Evidence upload](../../sdk/playwright-reporter/src/client.ts) · [Existing integration limits](../playwright-integration.md)

**Acceptance.** Present the same failure with and without an immutable attempt binding. With it, assign the attachment to its attempt. Identify the failing step only when the content or a trusted step record establishes it. Include an attempt-bound teardown screenshot that reveals nothing about the failing step. Without it, show “Passed after retry. The screenshot’s attempt is unknown.” A second fixture fails before the target assertion, then passes on retry. Identify the unreached step and distinguish the observed failure from a hypothesis about its cause. Missing, conflicting, quota-dropped, late or duplicate artifacts preserve a limited conclusion. A repeat request with an uncertain dispatch acknowledgment must reconcile the existing operation before any new external work. Revocation or cancellation stops further dispatch and retains lawful historical observations. Compare next-action quality against a tester using today’s native case and Run views. A historical candidate for an authorized replay is the [PR #228 review](https://github.com/1alextest/Tesbooboo/pull/228#pullrequestreview-6029017176), where the first attempt failed before editor assertions and the retry passed. Preserve which observations came from the trace and which came from the retry log.

**Dependencies and expansion.** Reuse T-459 per-attempt receipts and the existing connector, claim and retest contracts. A manually supplied, authorized CI attempt manifest suffices for a read-only pilot. For later mobile support, an external Appium/UiAutomator2 adapter must demonstrate real assertion, session/attempt, app build, device/OS and evidence correlation through the same contract. A named integration or prepared Run alone cannot satisfy this acceptance. [Execution and retest contracts](04_MCP_API_CONTRACTS.md)

## Skill and client regression

**User outcome.** Before adopting a Skill revision, its owner can see which clients, roles, governed fields or important behaviors changed, and reproduce a failing example. Resolve the active method normally. Exercise the proposed version as a pinned candidate in isolated trials. Keep the active project mapping under its existing human-controlled workflow. [Skill delivery and output contract](../specs/agent-synchronized-engineering/skills-governance.md#mandatory-skill-delivery-and-cross-member-authoring-conformance)

Compare active and candidate **within each client** before attributing a difference to the Skill. Freeze the task, criterion, fixture, suite overrides, effective role, available tools, budgets and grader. Pin the client/model versions and behavior-affecting settings where observable. Record unknown settings as limits on attribution. Compare across clients only on matched, supported capabilities and equivalent effective authority. Include two members using one client and one member using two independently capable clients. A viewer and an author can legitimately have different expected outcomes.

Score three independent dimensions. The governed projection must match exactly where the Skill prescribes a field, value, order or rendering. Check observable business meaning against an independent rubric where prose may vary. Grade the process evidence separately, including server-observed delivery of the exact Skill before accepted submission, any client attestation about consulting it before writing, and validation at intake. For instrumented authoring, verify that the Skill was loaded before the first generation or edit. Label the ordering inside an uninstrumented external client as self-reported or unknown. A correct external case cannot independently prove how the external model reasoned. Missing required Skill preflight or a changed effective mapping follows the existing refusal/review policy.

**Acceptance.** Seed an intentional governed-field regression, a paraphrase with equivalent obligations, a legitimate suite override, a stale candidate, and a client with read-only access. Repeat each supported cell with fresh state. Report attempts, consistency across all trials, false accepts, false blocks, and untested or unsupported combinations by version/client/role. Keep an unchanged-version control to estimate ordinary variation. A candidate may improve average prose while regressing a required field or approval boundary. Surface that regression on the version review and preserve the active mapping. Adopt, revise, defer or retire through the native Skill owner only.

## Customer-agent evaluation

**User outcome.** A customer can test whether its own agent completes a bounded QA task with the right authority. The customer selects the question, approved expected outcome, permitted tools and targets, disposable scope, and independent verifier. The subject is the named customer agent in its actual client/model/tool configuration. Reuse native scoped Tasks, grants, evidence, review and history. The first trial can use a Tesbo-native draft task. Extending a claim to a customer application requires that application’s independently authorized source of truth.

**First scenario.** Ask the agent to propose a change to B and request review. An independent read must find the intended attributed draft revision, preserved C, an official case at its original revision and the native review handoff. Record each relevant effect and attempted tool action. An agent that intentionally stops at review and an agent that tries to publish but is refused can leave identical final records. Score the requested task, the attempted action, the backend’s enforcement and any resulting effect separately. A subsequent reversal cannot erase a transient unauthorized write from the evaluation. Where the verifier cannot observe the relevant action history, qualify this dimension as unknown.

**Acceptance.** Include legitimate alternate action sequences, a denied grant, a grant revoked between read and proposed write, an unavailable verifier and a subject claiming completion after a failed write. The verifier reads trusted state with its own scoped credentials. Keep hidden expectations and grading records outside the subject’s write/read capabilities as applicable. Reset state between trials and verify cleanup. If cleanup fails, quarantine the fixture before reuse. Budget time, steps and cost, define cancellation and authorized destinations, redact credentials and apply tenant retention/deletion policy to transcripts and artifacts. Limit any report to the observed environment, version, permissions and tasks. A passing trial supplies evidence for the customer’s decision. Certification and general claims of competence require their own authority and scope.

## Pilot decisions and measurement

A project owner may select, defer or decline any option independently. Before running a comparison, the QA lead records the baseline, primary decision, reviewers, held-out cases and trial count, target improvement, tolerated false blockers, time and cost ceilings, and conditions for stopping. Use the same authorized inputs and comparable model, time and tool budgets in both arms. Blind the adjudicator to the method when feasible. Hold back expected answers from the subject in every arm. Include conforming behavior, real faults, underdetermined expectations, missing evidence and valid alternate paths. A second domain case is required for a cross-domain claim.

| Option | Comparison | Evidence that would justify advancing |
| --- | --- | --- |
| Assertion adequacy | Ordinary Zyra plus current review vs paired assertion assessment | More correct reviewer decisions about faults and valid cases within the predeclared limits. Report critical misses, false approvals, false blockers, unknowns and cost per correct decision. |
| Run analysis | Existing Run evidence review vs attempt-aware recommendation | More correct next actions or less time to the same correct action, within the agreed quality floor. Count needless reruns and unsupported causal claims separately. |
| Skill/client regression | Active vs candidate and active vs itself, per supported cell | Detect the seeded regression and preserve valid alternatives, role differences and governed output expectations. Report denominators, repeatability, reviewer effort and cost. |
| Customer-agent evaluation | Independent verifier vs pre-adjudicated expected outcomes and attempted actions | Reliably distinguish lawful completion, refusal, attempted violation, harmful effect and insufficient evidence. Record reset failures and operational cost. |

A missed or misclassified critical violation, a critical false approval, or any effect outside the authorized fixture stops promotion of the affected harness option pending adjudication. A deliberately seeded violation inside the fixture that the evaluator correctly detects counts against the subject agent and in favor of the evaluator’s detection result. Insufficient trials or inconclusive differences justify another experiment or deferral. Reviewers can choose a simpler deterministic check when it yields the same decision. Publish trial counts and limits with any comparison. A favorable result for one option does not authorize any other.

### Comparison accounting and acceptance guard (proposed)

A pilot's graded accuracy is conditional on the cases it managed to grade; it is not the proportion of assigned decisions it resolved correctly. Before either comparison arm runs, freeze the authorized trial inventory and its stable case/fixture, role, version, repetition and independent expected disposition. Define the primary measure, missing-evidence tolerance, paired comparison rule and stop thresholds before opening the results. Reuse the existing trial and review owners; this is an evaluation contract, not a new native schema, automated gate or mandatory product policy.

- Reconcile each arm against the same frozen inventory. Preserve assigned, attempted, graded-correct, graded-incorrect and ungraded counts; distinguish not attempted, missing/untrusted evidence, failed grader, unavailable runner and cancellation. Duplicate delivery cannot increase a denominator; a retry is a separately linked attempt, not a replacement for a failed or unknown assigned outcome. A post-assignment exclusion requires an independently recorded reason and symmetric treatment of both arms, not a result-dependent change to eligibility. Report unsupported combinations outside the eligible inventory explicitly.
- Report conditional accuracy (correct / graded), grade availability (graded / assigned) and correct-decision yield (correct / assigned) together, with numerators and denominators. A zero denominator is undefined, not a perfect score. Keep paired both-graded outcomes and ungraded asymmetry visible; a high conditional score alone cannot justify advancing an arm that silently drops difficult cases. Apply the predeclared primary measure and missing-evidence tolerance, alongside the critical-violation stop rule above. Do not retroactively select a favorable metric.
- Distinguish a *correctly identified underdetermined requirement* (the independent approved rubric expects abstention or escalation; grade that decision if its evidence is sufficient) from an *ungradable trial* (the independent verifier cannot establish the outcome). An expected refusal can be a correct decision, and a detected deliberately seeded fault is not an evaluator failure. Missing evidence does not earn a correct decision or automatically become a false approval. Retain unknowns in assigned accounting without treating them as graded fault-detection cases.

**Synthetic accounting challenge, 25 November 2026 (executed outside Tesbo).** A deterministic Python counterexample used the same ten assigned controls in both arms. The baseline resolved eight correctly and two incorrectly; the candidate resolved six correctly and left four ungraded. Graded-only accuracy rose from 8/10 (80%) to 6/6 (100%), while grade availability fell from 10/10 to 6/10 and correct-decision yield fell from 8/10 to 6/10 (60%). Assertions confirmed both directions. This demonstrates a measurement trap, not a product defect, live model result, independent reviewer outcome or native Test Case/Run. The pilot must not treat the higher conditional score as proof of improvement. Include this counterexample, reversed missingness, a zero-graded arm, duplicate deliveries and a legitimately underdetermined expected disposition in the eventual comparison acceptance fixture.
