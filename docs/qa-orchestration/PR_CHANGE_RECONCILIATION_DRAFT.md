**Status:** Proposed, not implemented or approved. **Original source baseline:** `development@93ca0d6` (24 November 2026); **source-grounded review comparison:** `development@97ce6b18143a62bc377f9dd7dd671fe92456d546` (25 November 2026 UTC). It creates no second requirement, case, task, approval, graph, run or bug owner. The canonical package remains NOT FROZEN.

## Outcome and boundary

A coding agent creates a PR and submits its account of the change to Tesbo: the task/change identity, applicable existing records, proposed requirement and case changes, links, claimed coverage and evidence. Zyra independently inspects the exact PR revision and the authorized *pre-existing* Tesbo expectations before reconciling that account. Tesbo presents agreements, omissions, contradictions and uncertain product decisions as reviewable findings and stages justified candidates through existing native proposal owners. Human decisions and real executions remain separate. A successful analysis can report unresolved QA findings; operational success is not change readiness.

The PR provider owns code, PR identity and commits. FR-115/T-455 owns the changeset identity; the Change Packet is its assembled view. Existing Zyra tasks own generation and typed proposal review. General assigned project work has its own completion criteria under Work Package C. A change can have zero or more linked tasks. The graph is a versioned observation and relationship aid, not an expectation or coverage authority. Native Requirements, Test Cases, Knowledge Base, Runs, Bugs, Skills and FR-119 impacts retain their current owners.

## Scope, authority and review evidence

This is an **optional provider-PR assessment slice** of the existing FR-115–124 and ASER Change Packet/agent workflow, not a prerequisite for source-free, human-started, planned, unplanned or pre-PR change work. Work remains usable when a coding agent has no Tesbo MCP access, no hook fired, a repository integration is OFF, or a PR has not yet been created; record the applicable source/observation gap without inventing a PR or blocking unrelated manual QA. One change may involve multiple repositories, bases, builds and releases; a release retains its own independent decision and evidence scope.

### Bounded native implementation increment — changed requirement nomination review

The existing read-only consequence preview can project a per-requirement triage lead from a committed current-cache graph receipt. This increment distinguishes added, modified and removed cached requirement nodes that have **no case nomination in that receipt**, even if another changed requirement has an explicit case nomination. It uses the existing authorized history reader and source contract, not a new requirement, finding, approval, execution or scorecard store. A removed requirement requires investigation of downstream behavior, not automatic creation of a replacement case. A nomination can include an old reference; it is not evidence of a current link or an approved expectation. An absent nomination is not a confirmed coverage gap. The inventory counts changed nodes only, not link-only changes.

Open Zyra → Change impact review → Explain possible impact (read-only). The reviewer can inspect the affected requirement references and continue in the existing requirement and testcase workflow. Unsupported graph contracts, missing compatibility fields or invalid/cross-project identity inventory are shown as unavailable, not as zero gaps. Reopen the explanation to read the exact receipt again; a mismatched project/receipt response is not displayed. Older observations are not rewritten.

This is a deterministic, receipt-derived investigation aid, not the independent provider-PR first pass described below. Its input can be a cached observation rather than a live provider or approved pre-existing native requirement. No actual model reasoning, semantic recall, policy decision, current-build verification, native case publication or deployment is established by this projection. Qualification remains with the existing backend graph unit/receipt tests, the authorized native endpoint and disposable Zyra Playwright tests; full independent and human acceptance are separate.

Ordinary chat deliberately includes conversation history, previous sources and pending drafts. The allocated provider is project-scoped. The Skill resolver supplies versioned methods for applicable operations. Verify enforcement at each writer: the standalone case staging insert does not persist the same Skill context as a requirement bundle. External MCP clients already have separate authenticated routes.

For the independent first pass, extend Zyra with a read-only assessment operation. The [generic AI retrieval filter](https://github.com/1alextest/Tesbooboo/blob/97ce6b18143a62bc377f9dd7dd671fe92456d546/Tesbo-Backend-Nest/src/legacy/knowledge-document-revision.ts#L14-L40) excludes typed manuals and policies. Load effective governed versions through their authorized native readers, preserve the retrieval boundary and record unavailable authority explicitly. Exclude conversation history, pending proposals, mirrored copies of the agent account and the account itself. The exact diff can itself contain tests, comments and expected values written by the PR author. Pin the pre-change approval cutoff and inventory those spans. If the first pass reads those spans, mark the relevant material as exposed. This limits independence even if the provider request used a new chat. Seed distinct synthetic markers in a changed test, an authored note and an independently approved earlier requirement. Inspect actual prompts, context, tool results and retry inputs, including telemetry destinations where applicable. Only the approved baseline should inform the independent oracle. Inspect the actual provider request in the acceptance fixture. If the separation fails, expose the limitation. Reuse provider transport, budgets and validation. Reusing ordinary chat context would cause the reviewer to see the author's proposed answer. Authorize each data class and endpoint at the point of transfer.

A specialist receives a bounded question, allowed evidence, an applicable method and a budget. The Agents screen already labels Run Analyst and Bug Triage as planned roles. One specialist on the existing model allocation is sufficient to test the design. Multiple independent provider allocations, generic worker delegation and protected write authority require separate implementation evidence. Persist the evidence used for a decision at the native change/task/evidence owner. Langfuse and bounded chat traces provide best-effort operational telemetry. A missing or truncated trace cannot certify which governed inputs a specialist saw or which native records it changed.

For case work, the existing Zyra task or chat review batch is the working copy. Continue an explicitly shared draft by its existing ID across permitted clients. Distinguish its draft revision from the official case revision used as its base. The current selected-save writer remains the publication owner. A member can fetch, draft, compare, reconcile and submit through supported MCP capabilities. Opening a change or completing a task does not move the official artifact revision. ## Required sequence

1. **Bind submission.** A provider event or a permitted human can open an assessment with no agent submission. When a coding agent reports after creating the PR, it submits the canonical project/change/task identity and stable provider repository ID, PR number, base/head SHA, declared intent and exact native record/proposal references through an authorized MCP path. A pre-PR change may exist under FR-115 and is bound later. Validate repository-to-project entitlement and fetch provider identity server-side; never trust an arbitrary URL or client-authored diff as proof. Duplicate deliveries with the same key return the same receipt; a later head is a new assessment generation under the same change.
2. **Independent first pass.** Before exposing the agent's proposed cases or interpretations to Zyra's analysis context, retrieve the exact diff and authorized approved requirements/policies, existing cases, manuals, graph relationships and relevant historical evidence. Record the bounded dependency frontier, retrieval gaps, source revision, effective Skill versions and separate observations versus inferred consequences. A model-only or semantic match cannot establish a normative requirement. If practical blinding is unavailable, record the contamination and weaken the independence claim.
3. **Reconcile.** Seal the first-pass inventory before any report enters comparison. Keep independent observations visible when no report exists. Compare against the latest attributable, applicable report revision only within its declared scope. For each meaningful behavior/obligation classify `agreement`, `missing_from_agent`, `unsupported_agent_claim`, `contradiction`, `unknown_intent`, or `not_applicable`, with evidence and uncertainty. Search existing native identities before proposing new ones. A code behavior absent from an approved requirement is a candidate or a decision question, not automatically the intended requirement. Do not demand a new document in every domain: record evidence-backed unchanged/not-applicable/undetermined outcomes.
4. **Route work.** The one change/task view links FR-119 impacts and existing proposal tasks. Use their native writer and review gates for requirement/case/link and manual/policy candidates. A suspected bug is a triage finding in the existing task/Bug path; a failed execution retains its raw result and evidence, then becomes a confirmed Bug only after classification against expected behavior and environment/test reliability. Preserve rejected, duplicate and no-change dispositions. No agent can apply, approve or publish merely because it authored or reviewed a candidate.
5. **Execute and revisit.** Authorized manual/automated Runs link case version, target build/environment, source/head where supported, evidence and result to the change. Designed, linked, selected, attempted and passed coverage are distinct. A push or relevant approved-record revision supersedes the current assessment; older receipts stay historical. Reassess current head, retain proposal continuity only if its exact base/Skill/target remains valid, and never silently replay a mutating proposal.

## Independence, source precedence and an honest review claim

A **source-separated first pass** means the coding agent's narrative and proposed tests are withheld until Zyra has recorded a version-bound analysis of the independently retrieved changed-source inventory and *approved pre-existing* Tesbo records. This is not necessarily an **independent agent invocation**, a different model family, an independent oracle, or an empirical demonstration of correctness. Preserve those as distinct, checkable dimensions. A source comment, malicious PR description, provisional graph edge, historical unapproved case, or KB document authored by the coding agent is not converted into normative expected behavior simply because a different request retrieved it. Establish approved source/version and actual applicability before interpretation; explicitly distinguish missing prior expectations from a valid documented decision.

Record an immutable pre-reconciliation observation manifest (within the existing change/task/evidence owners where supported): provider repository and base/head identity; exact diff/capture digest and coverage frontier; approved source/Skill/permission versions and effective intervals; seen and unexamined documents; actor/model and tool roles; analysis instructions/version; whether agent narrative was excluded; semantic hypotheses, alternative outcomes and counterexamples; and independent ground-truth authority or lack thereof. The later comparison must never rewrite this earlier manifest. If a supposedly blinded pass consumed the coding agent's proposed cases or a trusted-looking but agent-written requirement, lower the independence claim and mark affected conclusions uncertain.

A finding needs a **discriminating oracle**, not merely a plausible consequence. Use external authoritative rules, approved requirements/policies and recorded target behavior where appropriate; present mismatches as candidates when no approved expected outcome exists. A reported absence of issues is only a *bounded negative result* if the covered source/relationship frontier has a reviewable completeness witness and unexamined/hidden consumers have been counted as unknown. Compare with at least one conforming no-impact and one misleading lexical/link counterexample; see canonical FR-116/118/119, GA-AC-04 and DISC-02–04.

## Decision discovery and human review contract

The agent must **discover** underdetermined product decisions, not merely relay questions supplied by a coding agent. Generate possible decision points from observed changes to state transitions, authorization, ownership, data lifecycle, concurrency, money, trust boundaries, failure/retry behaviour and human-facing meaning. For each changed behaviour, compare current approved intent with alternative interpretations and their observable consequences. A missing decision is not necessarily a requirement defect: classify it as an evidence gap if an authoritative source cannot be retrieved, and as a genuine `decision_required` only when at least two materially different interpretations remain plausible after source review.

Decision detection is a separate pre-reconciliation pass. Its inputs are the exact bound diff, approved expectation versions and authorized historical evidence, **not** the coding agent's explanation or proposed tests. Invalidate or label independence when tool/context contamination occurs. Record false-negative probes, not only the questions the model happened to generate. Required triggers include a newly reachable transition, altered negative path, changed default, changed permission/consent, altered retention or revocation, changed version/approval owner, incompatible client behaviour, and a new user-visible status or label with uncertain meaning. A changed file alone is not proof that any trigger applies.

Each reviewable finding has a durable native task/reference and an evidence-backed record containing: specific affected journey and actor; observed behaviour; approved rule and its exact version (or explicit absence); competing interpretations with expected observable outcomes; impact/severity and reversibility; ownership of the pending decision; proposed verification probes; confidence/unknowns; and the exact source/head/Skill context. Keep detection evidence distinct from the agent's submitted claim and from the human decision. If no authorized decision-maker is identifiable, escalate through existing project governance instead of electing an AI team as owner.

**Information hierarchy for the reviewer:** show the human goal and changed outcome first, then the concrete conflict or decision and what happens if each option is chosen, then existing approved intent and actual evidence, then recommended next action. Put commit hashes, scanner references, graph paths, source excerpts, raw token usage and internal task mechanics in expandable provenance. Do not present opaque statuses like “Version 3 awaiting review” without the artifact purpose, changed fields, impact and action available to that reviewer. Do not make an unanswered question look like a defective feature or a pre-approved requirement. Use existing native proposal diff/version/approval UI where available; this is a specification for its contextual presentation, not a second UI system.

A reviewer may select an interpretation only with the native authorization appropriate to that decision. Record `accepted`, `rejected`, `deferred`, `superseded`, `duplicate` or `needs_evidence` with actor, target version, rationale and linked native proposal. Approval of a decision does not approve code, a Test Case, a Skill version or a release automatically. Any subsequent code or normative revision requires new exact-version validation. If there is an unresolved high-consequence interpretation, readiness cannot become `ready_for_authorized_decision` merely because analysis ran successfully.

Use progressive disclosure for commit/Skill digests, scanner IDs, graph edges and raw logs; links must return to the same task and current project after review. A version number without purpose, affected artifact and actual field changes is insufficient context.

## Authoritative findings and freshness

Reconcile **three separate** evidence layers: native PR review threads (including outdated unresolved threads), authoritative scanner/code-scanning alerts, and Tesbo's own independent findings. Do not treat a resolved GitHub thread as proof that the corresponding alert is closed, that its disposition was authorized, or that the scanner covered the exact source. Link them by provider alert identity and source revision, preserving many-to-one or unmatched relationships. Missing scanner credentials, API pagination, skipped analyzers, stale SARIF or ambiguous alert identities produce `insufficient_evidence` or `blocked`, never a clean finding count. The security reviewer can record a verified false positive or intentional fixture with its exact rule, finding, source and evidence. A separate risk authority can accept a real residual risk only where policy allows, for an explicit release/build, interval and conditions. Preserve the provider’s open state, finding history and decision independently. Undisposed material risk blocks. A valid scoped disposition can allow the human decision to proceed if other obligations are settled. An exception in release A cannot clear release B.

For every approval/readiness evaluation, read back the provider's current PR head and relevant approved-record/Skill revisions; fence decisions against the captured generation. Findings arriving after status publication or resolution changes without a new commit require fresh reconciliation. A GitHub branch rule requiring thread resolution and a trusted exact-head check are complementary controls, not substitutes. Preserve existing assurance gate ownership; do not create another self-publishing green check or let a bot change repository protections.

## Canonical state vocabulary — no local enum override

ASER-C01 in canonical 04_MCP_API_CONTRACTS.md is the sole owner for the **proposed** persisted consistency, domain-assessment and readiness vocabularies. PRR comparison labels such as agreement, missing_from_agent, unsupported_agent_claim, contradiction and unknown_intent are *review-local analytic classifications*, not new native consistency enum values, approval states, or independently persisted statuses. At the actual owner boundary, map only with evidence and review: a proven contradictory authority may support confirmed_conflict, a contested meaning unresolved_conflict, an actual missing required trace missing_link, a stale relied-on revision stale_reference, unavailable/unverified material unknown_source, an evidenced exclusion not_applicable, and a bounded no-supported-issue result no_detected_issue. None may be inferred from model agreement alone.

The existing **proposed** ASER readiness vocabulary is **not_assessed, insufficient_evidence, blocked, ready_for_authorized_decision**. Unresolved material findings remain separate native finding/impact/task records and may produce blocked with attributed reasons; incomplete required evidence yields insufficient_evidence. Do **not** add findings_open as a fifth stored readiness value. A successful operational assessment with unresolved findings is compatible with blocked readiness. Job progress and presentation labels must not be silently serialized as authoritative native state enums. Unknown future values receive explicit compatibility failure or a safe bounded degradation, never success.

## Result contract

Present two orthogonal *projections* on the exact assessed basis: **operational assessment health** (e.g. completed/partial/failed for transport, authorization, bounded analysis and durable receipt; proposed presentation/check vocabulary, not a new approved ASER persisted enum) and **canonical proposed ASER-C01 readiness** (not_assessed/insufficient_evidence/blocked/ready_for_authorized_decision). A completed operational assessment can coexist with blocked readiness and unresolved findings in their native records. Partial or failed execution cannot be shown as zero findings. A pass on the operational check means the bounded assessment was durably saved, **not** that the PR is safe or all tests passed. The entitled Tesbo detail shows scope, unexamined areas, permitted counts, links and freshness. Publish only fields independently allowed for the provider destination and its audience. Inspect the full serialized check including names, title, conclusion, annotations, summary, URL, external IDs and error text. A repository-only reader must receive equivalent output for assessments that differ only in restricted data. Use a generic allowed projection or suppress publication where even existence is restricted. Re-evaluate grants and destination visibility on retries and updates. An earlier external disclosure may persist at the destination, so enforce this before the first transfer.

A GitHub check is attached to a repository and commit. Track the native decision by stable base and head repository IDs, PR number, exact base/head revisions and applicable project/change/release basis. Two PRs can share a head and legitimately reach opposite decisions. Keep the check advisory until the project demonstrates actual merge eligibility for both PRs in both publication orders, on retarget, and on the synthetic merge commit when a merge queue is used. Inspect skipped, neutral, stale and missing results under the configured rule. ## External-reviewer boundary and differentiation check

A provider's PR-review bot, custom check, repository instruction file or Copilot agent is an **external evidence producer**, not the authoritative Tesbo decision maker. GitHub documents that Copilot reviews may consume instructions/skills from the **PR head branch** and that Copilot approvals can be configured to count toward GitHub merge requirements. Therefore a contributor-editable AGENTS.md / review instruction / skill on the proposed PR cannot supersede the pinned human-authorized Tesbo policy or method, and a provider bot's approval cannot satisfy Tesbo's independently authorized human decision merely because the provider accepted it. Resolve actual verified principal kind, reviewer authority, source of instructions, tool/Skill provenance and effective protection policy for every protected action. Preserve the bot's review as attributed evidence and allow relevant source text to be inspected as untrusted data; do not discard it or grant it authority. Reconcile with the existing trusted assurance publisher rather than creating another security state owner. See [GitHub Copilot code-review documentation](https://docs.github.com/en/copilot/how-tos/use-copilot-agents/use-code-review) and [OWASP prompt-injection guidance](https://cheatsheetseries.owasp.org/cheatsheets/LLM_Prompt_Injection_Prevention_Cheat_Sheet.html).

Existing PR-review tools already offer context-aware change review, security feedback, regression-test generation and CI assistance. For example, [CodeRabbit](https://www.coderabbit.ai/FAQ) and [Qodo](https://www.qodo.ai/solutions/testing/) describe such capabilities, but these vendor descriptions do not prove they complete Tesbo's native governed QA lifecycle or measure comparative effectiveness. The proposed value of #264 is **defensible cross-owner requirements/policy/case/run/evidence reconciliation and independent human decisions**, not merely generating another review summary. The FR-124 pilot must compare against capable contemporary PR review plus existing Tesbo QA on equivalent seeded cases, including conforming code incorrectly flagged by an LLM. [Jin and Chen (2026)](https://link.springer.com/article/10.1007/s10515-026-00638-5) report a systematic overcorrection risk in LLM requirements-conformance judgments, motivating counterfactual executable verification and false-positive adjudication instead of explanation volume.

### 3. One contract, three separate evidence layers

**Intended** = approved native requirement/criterion and case/condition revision, including authorized changes. **Asserted** = what an exact technical test definition actually checks within a known scope. **Observed** = what happened on an identified execution attempt/build with evidence. A source-derived candidate is never an approved expectation, an assertion is not proof of execution, and a passing run does not validate an unasserted requirement. A historical unknown remains unknown.

The native case remains the authoritative human-authored definition. A source observation and its explanatory projection attach to that case or remain an unlinked discovery in the existing task/change receipt. It must not create a second native case by default. Reuse existing case identity/automation metadata, source references, requirement links and revision owners. Add only missing structured fields/subrecords after proving the storage and API fit; do not hide semantic identities in title strings, test names, arbitrary Notes or external ticket keys.

Conceptual field contract (names are proposal semantics, not a shipped schema):

- Definition: native case/definition revision or unlinked discovery identity, scope/project, primary objective, test level, subject/actor, capability, conditions, source authority, applicable roles/events, parameterized inputs and their types/units, fixture setup and cleanup.
- Ordered actions: stable step IDs; actor or component, operation/target, bound inputs, applicability/branch/iteration, explicit before-state capture and observed checkpoints.
- Expected conditions: stable assertion IDs tied to one or more relevant steps, semantic subject, operator/predicate, typed expected value or reproducible formula/reference, comparison tolerance/units, quantifier/domain, temporal bound where relevant, polarity and required/optional/applicability, expected forbidden effects. Preserve one-to-many and multi-checkpoint mappings. Preserve explicit alternatives, failure semantics and cleanup obligations. An intentional smoke/no-throw test is an explicit minimal oracle and cannot be credited as stronger verification.
- Source assertion observation: stable test identity where a native tag or qualified symbol exists, framework and version, repository ID + exact commit/blob/path + source spans; discovered test/fixture/helper/mock/assertion spans, extraction adapter version and scope, normalized predicate and operands if supported, conditions/parameter rows and reachability qualifications, comparison coverage and unsupported constructs. A heuristic match remains proposed. A renamed/moved test may preserve an established identity only with verified mapping or human disposition; ambiguity stays unresolved.
- Mapping: approved requirement version + criterion key(s) + case revision + condition ID ↔ source test identity/revision and assertion observation ID(s); relation type, provenance, applicability, independent review status. Test-to-case and condition-to-assertion mappings may be many-to-many. No equality-by-title. Existing FR-081/118 typed lineage is the owner. Observed execution links separately bind test occurrence, environment/build/commit, actual condition verdict and evidence through Runs. No inferred execution.
- Projection: render the same structured representation in user terminology and/or necessary component vocabulary; Given describes conditions/setup, When denotes tested action, Then/And describes actual asserted predicates. Preserve step association, units, bounds and negative constraints. Shared-first coverage with explicit actor-specific variations for user-facing tests; use component/contract scopes for technical tests. One coherent primary objective can have multiple assertions; don't split integrated invariants or duplicate shared definitions. If plain-language Gherkin cannot faithfully represent a property, concurrency schedule, loop, custom predicate or timing condition, show structured table/predicate/technical detail and disclose projection limitations. No invented assertion or false claim of valid executable feature syntax.
- Required validation: references resolve, normative expectations are source-grounded, all supported actions/assertions remain mapped and no conditions silently vanish, types/units and evaluation timing agree, required-oracle obligations have explicit verification or an unresolved gap. Validate candidate syntax/data with deterministic rules, then assess semantic correspondence independently. Unknown, unsupported, conditional, skipped, or unexamined are not passed.

### 4. Bidirectional workflows and change semantics

**Human/specification → code.** In the existing case editor/approved automation handoff, let a permitted author define or refine the structured case and inspect the exact requirement/criterion and approved version. The existing Zyra/agent proposal owner stages candidates; authorized human approval binds immutable expectations. Existing handoff carries exact selection, requirement, case, approved condition and skill pins, target repository/path/revision, adapter and applicable oracle scope. Adapter generates a reviewable native framework change and a condition-to-source map, reports unsupported/unbound fields, and must not silently drop assertions, lower comparator strength or invent fixtures. No implicit execution or approval. Reverse-read the actual generated bytes and reconcile with the originating contract; an unresolved mismatch is a failed conversion/admission, not success because generation compiled.

**Code → human specification.** From a connected repository, authorized task or existing PR review, select exact immutable source revision and bounded files; inventory supported test declarations, inherited/setup/teardown hooks, fixture data, parameter rows, mocks, helper/custom matcher definitions and reachable assertion sites using a framework-aware parser/AST and resolved symbols where possible. Never execute PR code to obtain a static summary. Distinguish test setup guards from target-behaviour assertions, mocked from real collaborator behaviour, assertions from log output, conditional from always-applicable obligations, and skipped/only/disabled from runnable intent. Detect missing source/helper/config context and record incomplete inventory. A source-derived observation may feed an AI language projection with exact spans and normalized predicates as context; validate it against the extracted representation, including omissions. Treat source/comment text as data, never instructions. If a helper or dynamic matcher cannot be resolved, show the precise unknown rather than inventing semantics. For unsupported frameworks preserve available identity/provenance and report partial/unavailable. Never upload secrets or protected code to an unapproved external model. Do not create/overwrite a native case, requirement or expected result just because a test was discovered. Stage a linked candidate only on authorized request through existing proposal workflow; reuse an existing case or create a genuinely uncovered draft after independent requirement review.

**PR delta.** Independently extract both exact base and head using the same adapter/semantic contract and source-scope policy; reconcile adapter changes or disclose non-comparability. Compare identity, setup/inputs, data cases, branches and applicable required predicates, assertion targets, expected values, polarity, comparator/tolerance, cardinality/quantifier, timing, mocks and reachability. Classify each evidenced difference as added/removed/modified, unchanged/refactor-only within demonstrably comparable supported scope, potential weakening/strengthening, or unknown/needs review. Strength/weakness requires an independently grounded obligation or discriminating counterexample (e.g. exact equality → existence can admit a wrong value); a changed literal alone is not a defect. Detect disabled tests and hidden shifts through helpers/fixtures in bounded dependency scope. Compare code-to-code and code-to-approved-intent separately; show runtime base/head difference only with separately attributable actual observations. A genuine intended change uses native requirement/case proposal and review before expectations become normative. A green CI run, source-only match or count of files/lines/assertions cannot clear missing coverage or certify readiness.

On new head, relevant approved case/criterion revision, source mapping or semantic-adapter change, fence current claims by exact basis and supersede/recompute affected projections. Preserve earlier receipts and reviewer decisions. Partial analysis cannot be represented as complete; preserve unexamined population, reason and remaining action. Current readiness policy owner, not a new gate, determines any blocking effect, after separately approved policy/rollout. No mandatory repository source access for ordinary source-free manual authoring.
