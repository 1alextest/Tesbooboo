# PR change reconciliation — scoped specification draft

**Status:** Proposed, not implemented or approved. **Original source baseline:** `development@93ca0d6` (24 November 2026); **source-grounded review comparison:** `development@97ce6b18143a62bc377f9dd7dd671fe92456d546` (25 November 2026 UTC). This is not a full current-runtime audit. This extension refines FR-115–119, FR-124, R-ASE-06 and the existing Change Packet contract in canonical 01/03/04/05. It creates no second requirement, case, task, approval, graph, run or bug owner. The canonical package remains NOT FROZEN.

## Outcome and boundary

A coding agent creates a PR and submits its account of the change to Tesbo: the task/change identity, applicable existing records, proposed requirement and case changes, links, claimed coverage and evidence. Zyra independently inspects the exact PR revision and the authorized *pre-existing* Tesbo expectations before reconciling that account. Tesbo presents agreements, omissions, contradictions and uncertain product decisions as reviewable findings and stages justified candidates through existing native proposal owners. Human decisions and real executions remain separate. A successful analysis can report unresolved QA findings; operational success is not change readiness.

The PR provider owns code, PR identity and commits. FR-115/T-455 owns the changeset identity; the Change Packet is its assembled view. Existing Zyra/project tasks own work and review candidates. The graph is a versioned observation and relationship aid, not an expectation or coverage authority. Native Requirements, Test Cases, Knowledge Base, Runs, Bugs, Skills and FR-119 impacts retain their current owners.

## Scope, authority and review evidence

This is an **optional provider-PR assessment slice** of the existing FR-115–124 and ASER Change Packet/agent workflow, not a prerequisite for source-free, human-started, planned, unplanned or pre-PR change work. Work remains usable when a coding agent has no Tesbo MCP access, no hook fired, a repository integration is OFF, or a PR has not yet been created; record the applicable source/observation gap without inventing a PR or blocking unrelated manual QA. One change may involve multiple repositories, bases, builds and releases; a release retains its own independent decision and evidence scope.

Merged PR #266 already adds *prompt-level* question-discovery instructions to the real MCP initialize and staging tool descriptions; merged PR #267 already proposes a *conceptual* decision-candidate receipt through existing R-ASE-09/12/15/16/40 task/Change Packet owners. The latter does **not** prove that current native task storage accepts those fields, that a model reliably discovers omissions, or that a hard authorization gate exists. Reuse these owners and the existing evidence-grounded-decisions skill instead of reintroducing a decision registry, self-certifying detector or extra MCP payload. Merged #261 supplies a separate existing security-assurance provenance contract; #191's trusted default-branch bootstrap requires its own verified admission and is not presumed active.

This draft's [source-grounded full-roster challenge](reviews/PR264-20261125-coordinator-charter-challenge.md) is a **coordinator review against eleven risk lenses**, not eleven independently dispatched team agents, an eligible cold Elephant-Gold invocation, a Graph harness execution or a White freeze. All implementation acceptance scenarios below are **NOT RUN**. ## Required sequence

1. **Bind submission.** After creating the PR, the coding agent submits the canonical project/change/task identity and stable provider repository ID, PR number, base/head SHA, declared intent and exact native record/proposal references through an authorized MCP path. A pre-PR change may exist under FR-115 and is bound later. Validate repository-to-project entitlement and fetch provider identity server-side; never trust an arbitrary URL or client-authored diff as proof. Duplicate deliveries with the same key return the same receipt; a later head is a new assessment generation under the same change.
2. **Independent first pass.** Before exposing the agent's proposed cases or interpretations to Zyra's analysis context, retrieve the exact diff and authorized approved requirements/policies, existing cases, manuals, graph relationships and relevant historical evidence. Record the bounded dependency frontier, retrieval gaps, source revision, effective Skill versions and separate observations versus inferred consequences. A model-only or semantic match cannot establish a normative requirement. If practical blinding is unavailable, record the contamination and weaken the independence claim.
3. **Reconcile.** Compare Zyra's first-pass inventory with the coding agent's submitted account. For each meaningful behavior/obligation classify `agreement`, `missing_from_agent`, `unsupported_agent_claim`, `contradiction`, `unknown_intent`, or `not_applicable`, with evidence and uncertainty. Search existing native identities before proposing new ones. A code behavior absent from an approved requirement is a candidate or a decision question, not automatically the intended requirement. Do not demand a new document in every domain: record evidence-backed unchanged/not-applicable/undetermined outcomes.
4. **Route work.** The one change/task view links FR-119 impacts and existing proposal tasks. Use their native writer and review gates for requirement/case/link and manual/policy candidates. A suspected bug is a triage finding in the existing task/Bug path; a failed execution retains its raw result and evidence, then becomes a confirmed Bug only after classification against expected behavior and environment/test reliability. Preserve rejected, duplicate and no-change dispositions. No agent can apply, approve or publish merely because it authored or reviewed a candidate.
5. **Execute and revisit.** Authorized manual/automated Runs link case version, target build/environment, source/head where supported, evidence and result to the change. Designed, linked, selected, attempted and passed coverage are distinct. A push or relevant approved-record revision supersedes the current assessment; older receipts stay historical. Reassess current head, retain proposal continuity only if its exact base/Skill/target remains valid, and never silently replay a mutating proposal.

## Independence, source precedence and an honest review claim

A **source-separated first pass** means the coding agent's narrative and proposed tests are withheld until Zyra has recorded a version-bound analysis of the independently retrieved changed-source inventory and *approved pre-existing* Tesbo records. This is not necessarily an **independent agent invocation**, a different model family, an independent oracle, or an empirical demonstration of correctness. Preserve those as distinct, checkable dimensions. A source comment, malicious PR description, provisional graph edge, historical unapproved case, or KB document authored by the coding agent is not converted into normative expected behavior simply because a different request retrieved it. Establish approved source/version and actual applicability before interpretation; explicitly distinguish missing prior expectations from a valid documented decision.

Record an immutable pre-reconciliation observation manifest (within the existing change/task/evidence owners where supported): provider repository and base/head identity; exact diff/capture digest and coverage frontier; approved source/Skill/permission versions and effective intervals; seen and unexamined documents; actor/model and tool roles; analysis instructions/version; whether agent narrative was excluded; semantic hypotheses, alternative outcomes and counterexamples; and independent ground-truth authority or lack thereof. The later comparison must never rewrite this earlier manifest. If a supposedly blinded pass consumed the coding agent's proposed cases or a trusted-looking but agent-written requirement, lower the independence claim and mark affected conclusions uncertain.

A finding needs a **discriminating oracle**, not merely a plausible consequence. Use external authoritative rules, approved requirements/policies and recorded target behavior where appropriate; present mismatches as candidates when no approved expected outcome exists. A reported absence of issues is only a *bounded negative result* if the covered source/relationship frontier has a reviewable completeness witness and unexamined/hidden consumers have been counted as unknown. Compare with at least one conforming no-impact and one misleading lexical/link counterexample; see canonical FR-116/118/119, GA-AC-04 and DISC-02–04.

## Decision discovery and human review contract

The agent must **discover** underdetermined product decisions, not merely relay questions supplied by a coding agent. Generate possible decision points from observed changes to state transitions, authorization, ownership, data lifecycle, concurrency, money, trust boundaries, failure/retry behaviour and human-facing meaning. For each changed behaviour, compare current approved intent with alternative interpretations and their observable consequences. A missing decision is not necessarily a requirement defect: classify it as an evidence gap if an authoritative source cannot be retrieved, and as a genuine `decision_required` only when at least two materially different interpretations remain plausible after source review.

Decision detection is a separate pre-reconciliation pass. Its inputs are the exact bound diff, approved expectation versions and authorized historical evidence, **not** the coding agent's explanation or proposed tests. Invalidate or label independence when tool/context contamination occurs. Record false-negative probes, not only the questions the model happened to generate. Required triggers include a newly reachable transition, altered negative path, changed default, changed permission/consent, altered retention or revocation, changed version/approval owner, incompatible client behaviour, and a new user-visible status or label with uncertain meaning. A changed file alone is not proof that any trigger applies.

Each reviewable finding has a durable native task/reference and an evidence-backed record containing: specific affected journey and actor; observed behaviour; approved rule and its exact version (or explicit absence); competing interpretations with expected observable outcomes; impact/severity and reversibility; ownership of the pending decision; proposed verification probes; confidence/unknowns; and the exact source/head/Skill context. Keep detection evidence distinct from the agent's submitted claim and from the human decision. If no authorized decision-maker is identifiable, escalate through existing project governance instead of electing an AI team as owner.

**Information hierarchy for the reviewer:** show the human goal and changed outcome first, then the concrete conflict or decision and what happens if each option is chosen, then existing approved intent and actual evidence, then recommended next action. Put commit hashes, scanner references, graph paths, source excerpts, raw token usage and internal task mechanics in expandable provenance. Do not present opaque statuses like “Version 3 awaiting review” without the artifact purpose, changed fields, impact and action available to that reviewer. Do not make an unanswered question look like a defective feature or a pre-approved requirement. Use existing native proposal diff/version/approval UI where available; this is a specification for its contextual presentation, not a second UI system.

A reviewer may select an interpretation only with the native authorization appropriate to that decision. Record `accepted`, `rejected`, `deferred`, `superseded`, `duplicate` or `needs_evidence` with actor, target version, rationale and linked native proposal. Approval of a decision does not approve code, a Test Case, a Skill version or a release automatically. Any subsequent code or normative revision requires new exact-version validation. If there is an unresolved high-consequence interpretation, readiness cannot become `ready_for_authorized_decision` merely because analysis ran successfully.

## Human journey and interface contract

Use the existing change/task detail, native proposal review/diff and domain destinations; no new standalone Review Board is authorized. At the first screen level show **what the person is trying to decide**, the changed outcome and affected user/journey, current versus prior authoritative requirement, what is known/unknown, the practical alternatives and consequences, current responsible owner and the one permitted next action. Show separate assessment health, readiness, provenance and stale/partial scope without implying that an analytical completion approves code or a release. Use progressive disclosure for commit/Skill digests, scanner IDs, graph edges and raw logs; links must return to the same task and current project after review. A version number without purpose, affected artifact and actual field changes is insufficient context.

The planned interaction matrix must cover loading/queued, no findings with proven bounded scope, partial or missing evidence, scanner unavailable, outdated status, project switch, access denied/revoked, expired decision, conflicting proposal version, valid not-applicable/unchanged, interrupted apply, rejected/deferred/selected-only review, recovery/resume, and empty review permissions. Preserve draft comments and keyboard focus where safe, never re-enable a revoked action through stale UI state, never expose hidden project counts, and never represent declined normative changes as independently approved tests. Verify authentic interface comprehension with BA/QA/PM/solo reviewer and an unfamiliar low-knowledge person; browser, accessibility (keyboard/AT/zoom) and action/return-path checks require real UI evidence, not a textual mockup.

## Authoritative findings and freshness

Reconcile **three separate** evidence layers: native PR review threads (including outdated unresolved threads), authoritative scanner/code-scanning alerts, and Tesbo's own independent findings. Do not treat a resolved GitHub thread as proof that the corresponding alert is closed, that its disposition was authorized, or that the scanner covered the exact source. Link them by provider alert identity and source revision, preserving many-to-one or unmatched relationships. Missing scanner credentials, API pagination, skipped analyzers, stale SARIF or ambiguous alert identities produce `insufficient_evidence` or `blocked`, never a clean finding count. Scanners may report deliberate rejection fixtures; contextual explanation is evidence for independent triage, not blanket suppression.

For every approval/readiness evaluation, read back the provider's current PR head and relevant approved-record/Skill revisions; fence decisions against the captured generation. Findings arriving after status publication or resolution changes without a new commit require fresh reconciliation. A GitHub branch rule requiring thread resolution and a trusted exact-head check are complementary controls, not substitutes. Preserve existing assurance gate ownership; do not create another self-publishing green check or let a bot change repository protections.

## Status freshness, bounded work and operations

Reconcile PR lifecycle events (opened, synchronized/force-pushed, base changed, closed, reopened, merged), human starts with no PR, external changes without agent hooks, policy/Skill/repository-binding revisions, scanner-alert updates and retrospective reviewer dispositions. A source head remaining unchanged **does not** guarantee the assessment remains applicable: its generation basis must include relevant approved obligation/Skill versions and applicability windows, source/binding generation, provider event revision, scanner coverage/status, and decision/review context. Preserve an append-only prior result; a late worker, retry or callback cannot overwrite the current generation or publish a green current-head verdict after relevant authority/evidence has changed. For unknown original write outcome, read back the existing native idempotent receipt before a new attempt.

Use the native impact/task/notification owners for progress and recovery. Distinguish accepted, queued, running, completed, partial, failed, superseded, cancelled, blocked and dead-letter states where applicable; distinguish the **assessment job state** from the **product/readiness conclusion**. Preserve durable retry limits, worker lease/epoch, elapsed time, source/graph/frontier caps, AI spend and human review burden, failed pages/analyzers, last known valid source, next retry/owner and permission-safe correlation IDs. A skipped scanner, absent provider grant or stale release check cannot become an empty finding set. Operators need a scoped replay/reconcile path and alert when a material impact is stranded; no invented kill of an external executor or promise that a webhook was delivered.

Define privacy/retention/redaction for submitted agent text, source code excerpts, sensitive policies, original evidence, traces and token/cost logs at existing file/audit owners. An observer's visibility into a status cannot imply access to restricted finding details. Report measured critical-miss recall, false-positive adjudication, review time, latency and total incremental cost against a predeclared baseline under FR-124. Do not optimize the number of generated cases or findings.

## Canonical state vocabulary — no local enum override

ASER-C01 in canonical 04_MCP_API_CONTRACTS.md is the sole owner for the **proposed** persisted consistency, domain-assessment and readiness vocabularies. PRR comparison labels such as agreement, missing_from_agent, unsupported_agent_claim, contradiction and unknown_intent are *review-local analytic classifications*, not new native consistency enum values, approval states, or independently persisted statuses. At the actual owner boundary, map only with evidence and review: a proven contradictory authority may support confirmed_conflict, a contested meaning unresolved_conflict, an actual missing required trace missing_link, a stale relied-on revision stale_reference, unavailable/unverified material unknown_source, an evidenced exclusion not_applicable, and a bounded no-supported-issue result no_detected_issue. None may be inferred from model agreement alone.

The existing **proposed** ASER readiness vocabulary is **not_assessed, insufficient_evidence, blocked, ready_for_authorized_decision**. Unresolved material findings remain separate native finding/impact/task records and may produce blocked with attributed reasons; incomplete required evidence yields insufficient_evidence. Do **not** add findings_open as a fifth stored readiness value. A successful operational assessment with unresolved findings is compatible with blocked readiness. Job progress and presentation labels must not be silently serialized as authoritative native state enums. Unknown future values receive explicit compatibility failure or a safe bounded degradation, never success.

## Result contract

Present two orthogonal *projections* on the exact assessed basis: **operational assessment health** (e.g. completed/partial/failed for transport, authorization, bounded analysis and durable receipt; proposed presentation/check vocabulary, not a new approved ASER persisted enum) and **canonical proposed ASER-C01 readiness** (not_assessed/insufficient_evidence/blocked/ready_for_authorized_decision). A completed operational assessment can coexist with blocked readiness and unresolved findings in their native records. Partial or failed execution cannot be shown as zero findings. A pass on the operational check means the bounded assessment was durably saved, **not** that the PR is safe or all tests passed. A separately configured readiness check may block merge under explicit project policy; it cannot be inferred from a green operational check. Include scope/frontier, unexamined areas, counts by actual lifecycle state, proposal/task links, and evidence freshness. The provider status is bound to the actual current head SHA and becomes non-current when the head changes.

## Trust, concurrency and cost

- Verify webhook signatures/provider installation, stable repository ID, base repository versus fork contributor head, tenant/project/source entitlement, current member/token grants and least-privilege read/check permissions before capture and again before deferred reads/publication/notifications. PR text, code, comments, agent task content, scanner output and retrieved KB are untrusted data (including prompt-injection attempts): never promote instructions embedded in these artifacts into agent authority. Use restricted read-only evaluator credentials and redacted, permission-scoped retrieval; prohibit privileged checkout, arbitrary tool escalation, arbitrary outgoing URL fetch and secret exposure. Do not execute PR code in a privileged webhook/check publisher; use an isolated separately authorized executor for testing.
- Use one bounded assessment basis per scoped change with authenticated project/source binding, PR/head/base where present, approved requirement/policy/manual/Skill revisions and effectivity, graph frontier and authorized scanner/reviewer evidence status. The logical change remains FR-115/T-455; proposed generations are revisioned receipts/projections under that owner, **not** an independently approved new schema. Dedupe event replay by stable identity/digest, fence late workers and prevent older evidence publishing current readiness. Reconcile same-head status/authority changes and preserve original uncertain writes before retries.
- Bound changed-file analysis, graph traversal, model calls, test selection and execution budgets. Report truncation and unsupported language/source semantics as partial scope, not no impact.
- Pin actor, model/skill/version/digest, approved expectation versions, graph capture, proposal revision, source and execution provenance. Specialist agents may later receive bounded task scopes; Zyra reconciles their distinct evidence and disagreements under the same task owner. Agent count or consensus is not proof.
