## Reconstructed problem and independent trace questions

The immediate outcome is to preserve the option of general contributions while keeping existing users' work understandable and attributable. A source manager connects a remote namespace; a project member consumes retained knowledge; a method reviewer approves/assigns an exact Skill revision; an executor performs admitted work; a reader interprets evidence/report output. Package publisher, installer, project enabler, acting principal and human decision owner can differ. Existing native records must remain usable when an optional contribution fails or disappears.

My questions were: does the package noun hide several different authorities; can current integration machinery support its claimed continuity; what historical relationship survives reconnect/removal; can a declarative contribution use the same semantic principles without inheriting an executor's runtime; which current UI patterns can truthfully be reused; and what remains unknown until an actual profile is selected?

## Findings, counterevidence and gates

### GB-C2-01 — Medium: current integration overview substitutes a disconnected state for an unreadable state

**Class:** existing-source reuse/convergence limitation; not introduced by the documentation amendment. **Owner:** existing frontend integration/status surface, with QA/Purple functional and comprehension proof. **Disposition:** track under the selected native integration/UI work before using this component as proof of 1.4.49's truthful state contract. Non-blocking for keeping this amendment Proposed/Backlog.

At current source `d440c48…`, `Tesbo-Frontend/components/settings/IntegrationsTab.tsx:77–87` catches each Jira/Linear/Notion status rejection and substitutes `{ connected: false }`, then stores these values and clears the top-level error. Lines 177–205 suppress connected/source/project information when the substituted value is false. Lines 208–241 choose Manage/Disconnect versus Configure, or the plan-based upgrade route, from that same value. Thus an unavailable status response follows the same source branch as an actual unconnected provider. A failed read does not establish disconnection or lack of configured usage.

**Source-level trace:** a project/workspace user opens the integration overview; a previously valid provider's status request rejects; the catch supplies false; no provider read error survives; the overview omits its connected context and offers the alternate configuration/plan action. The expected alternative is an unknown/unavailable observation with safe refresh/return and no invented current connection conclusion. A successful connected response and an actually disconnected response remain legitimate contrasting controls. All three providers use the same mechanism; this is not three independent findings.

**Counterevidence and limits:** `WorkspaceIntegrationConfig.tsx:66–79` exposes a status-load error instead of substituting a false status. Its existing treatment is a reuse lead, not a fully validated solution. `getIntegrationStatus` in `lib/api.ts:4071–4072` calls the actual workspace status route; the backend's native management permission remains authoritative. This observation does not demonstrate unauthorized effects, a falsely completed disconnect, or a deployed incident. No UI was rendered and no network failure was injected. The proposed 02/04/07 contracts already require truthfulness; they do not claim this current UI satisfies it. Recommended proof is a boundary test with connected, disconnected, failed and recovered provider reads, with an unaffected provider preserved, followed by actual accessibility/comprehension checks when UI work is authorized.

1. **Sequential source replacement remains an implementation gate.** V47's organization/provider uniqueness and V97's retained row coexist with OAuth callback upserts replacing `external_id`/site/credentials. The processor's mirror key remains project/provider/external-ID/role. No source/schema change is authorized by this report.
2. **Disconnect is not a proven final effect fence.** Service `markRunning:194–200` has only run ID in its update predicate; the processor can load provider inputs, await comments/analysis, and reach mirror write `569–600` without a run/connection-generation check in that transaction. Those controls do not establish the missing late-effect fence. C2 correctly leaves safe reproduction, legitimate completion controls and any owner fix open.
3. **Retained read authority is distinct from provider connection.** Current disconnect deliberately retains KB content; `getKnowledgeDocument`, history and exact-version reads require project access. C2's narrower wording matches this observed owner split. Full project/client/derivative access enforcement is not certified by this selected trace.

These retained gates are consequential before a selected implementation relies on the stronger proposed guarantees. Recording them is compatible with a proposed documentation amendment; it is not closure, accepted residual risk or runtime signoff.
