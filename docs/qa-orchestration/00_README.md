## External architecture reconnaissance and disposition — revision 1.4.3

There are already mature solutions for individual layers. **No complete replacement of Tesbo has been approved.** `03_TECHNICAL_DESIGN.md` §17 records public repository sources and targeted reuse options; `05_IMPLEMENTATION_BACKLOG_AND_TEST_PLAN.md` contains the evaluation gate. Immediate candidate spikes: **existing Zyra UI vs assistant-ui primitives**, and **an optional Midscene or Stagehand execution adapter**. The **first execution proof uses the user’s already installed, self-managed agent communicating with Tesbo MCP** (OpenCode initially), followed by Hermes/OpenClaw or another independently operated executor. OpenCode SDK/headless server and OpenHands are optional hosted-runtime candidates, not the core integration strategy; LibreChat is a candidate for **selective source/module incorporation into Tesbo**, not a substitute application or separate chat backend. Qase MCP is a reference for task-oriented assistant tools, not a reason for a second MCP server. Competitor examples such as Momentic/Qase AI indicate feature overlap; product differentiation must be demonstrated through durable project sessions, evidence-backed human governance, interoperability, provider portability and reuse of Tesbo official QA records.

**Decision standard:** record functional fit, existing-code overlap, integration cost, security/tenant isolation, maintenance, data migration/reversibility and one working proof before selecting external infrastructure. Incorporation decisions remain with the project owner; the engineering team assesses technical fit and integration safety. User authorization is still needed for real customer environments. This research did not install or execute any candidate.

## Revision 1.4.4 — confirmed dual AI entry paths, MCP exposure, summaries and module audit

**Two routes, same services:** (A) a user operating the ChatGPT or Claude app links Tesbo MCP, discovers only opted-in authorized projects, opens their QA sessions, reads KB/official records, creates an external execution assignment, retrieves returned evidence, requests a retest and stages proposals; (B) a user operates **one Tesbo web Copilot**, selects an authorized project/session and a configured analyst model or hosted/remote CLI-agent-backed conversational engine, then uses those same services. Copilot backend selection is NOT the same as assigning a task executor. A user-managed OpenCode/Hermes/OpenClaw/etc. can separately claim a task through Tesbo MCP and use its own network/target testing tools. Hosted agent execution is optional.

**MCP exposure:** project policy is *deny/off by default*, with an explicit project setting, named external clients, narrow credential/grant and session/task/data-class scopes. Existing broad tokens cannot imply access to a newly opted-in project; disabling exposure invalidates access at the next operation regardless of stale client discovery. Default role/account membership alone cannot override the external-access switch. Human approval cannot be delegated to a model or executor.

**Summaries:** External client tools explicitly submit attributed summaries for a selected Tesbo session (user-requested per-chat or periodic); native Copilot may checkpoint a summary; executors submit report/attempt-linked summaries. Each stores original-vs-derived distinction, source visibility, completeness window/gaps, revision, reference IDs, human corrections and injection restrictions. Tesbo cannot automatically read provider-private messages never sent through its service. Summary is not an authoritative report, requirement, approval or pass/fail result.

**Existing-module dispositions:** requirements/ticket links, test-case suite/custom-field/history, plans, runs/results, bugs/links/evidence, insights/reports, Agents/Zyra task/review surfaces, Knowledge Base/folders/versions/search, Activity Stream/audit and Project Settings/token management all remain the official surfaces. Extend them with deep links and shared service operations. Add only justified **Copilot session navigation, session summary controls and Project Settings → External AI & MCP Access**. The complete per-module source map and adaptation decisions are in Technical Design §18; functional/UX/MCP tests are mapped in the original seven companion specs. **This is a source review and planned design, not a deployed or executed change.**

## Product boundary: platform-wide vs pilot-specific (revision 1.3.4)

**Tesbo is a reusable, multi-project QA platform, not a DMIS/ODPEM testing application.** It manages project-independent QA task orchestration, agent integration, evidence, test definitions, results, human governance and audit. Projects independently configure target kind (initial web browser flow; extensible API/mobile/other executor integrations when supported), environments, target authorization, test-case templates/fields/hierarchy, identity/role vocabulary, import sources, issue trackers, approval controls and evidence/retention policy. **No DMIS term, field, role, tenant, screen, workbook or governmental retention rule is a Tesbo-wide invariant.** The DMIS website is the first reference **pilot fixture** for the end-to-end ChatGPT ↔ Tesbo ↔ OpenCode/Chrome MCP workflow. Other projects must run without a DMIS profile, Excel import, government policy or GitLab account. Optional unsupported adapters must state `NOT_SUPPORTED`, never claim test coverage.

## User workflow and system boundary

1. The user discusses a feature with ChatGPT and agrees testing scope.
2. ChatGPT submits the exact natural-language testing prompt as a Tesbo task.
3. A registered execution agent retrieves its assigned prompt through Tesbo MCP and tests using its supported external tool/runner (OpenCode + Chrome MCP in the DMIS website pilot).
4. OpenCode submits the complete original report and evidence to Tesbo.
5. An authorized analysis client (ChatGPT initially) reads the complete report/evidence from Tesbo and stages individually traceable case, execution-result and native-defect/issue-draft proposals.
6. If evidence is missing, contradictory or insufficient, ChatGPT or the human requests clarification/verification/retest via a *linked new Tesbo task*. An assigned executor claims the revised instructions and produces a separate report; ChatGPT re-analyses and supersedes affected draft revisions. No original report is overwritten.
7. The authenticated human reviews diffs, may edit, approve, reject or request further testing, and separately authorizes merge/publication. Only exact approved selected operations enter existing Tesbo Test cases, Runs/Executions or Bugs. Project-configured external tracker filing remains a separately authorized optional action (manual copy initially).

OpenCode may be replaced by Claude Code, Codex, Kimi Code, Hermes or another capable runtime. Capabilities are assigned to registered instances, not permanently to runtime names. Tesbo does not launch/control any external executor's browser, API or device tool. No new built-in Playwright/Appium runner is required for the first pilot; optional existing Tesbo regression and reporter integrations remain valid. An executable adapter is required for each newly claimed target type.

## Revision 1.4.1 — single web Copilot, project sessions and hosted agent adapters

**Architectural commitment:** Tesbo is a web-only, project-neutral QA platform. It exposes **one native Copilot chatbox/interface**, shared across the user’s authorized projects and capable of creating, switching, searching, and resuming **many project-scoped sessions**; each session retains its own attributed conversation/events, linked tasks/retests, agent participation, evidence, decisions, and proposals. This does **not** mean one all-seeing cross-project AI context: opening a session loads only knowledge and records permitted for that project/session. Provider-native conversation IDs are changeable bindings, never authoritative Tesbo history. External ChatGPT, Claude, and execution agents are optional session participants, not separate Copilot instances or owners of the session. Use existing Zyra chat/session foundations. DMIS is a pilot only.

**UI decision based on user-supplied Open Design screenshots (reference only):** borrow the compact agent/model selector near the chat composer, not the desktop architecture, `Local CLI`, device `PATH` discovery, or `Rescan PATH`. Tesbo’s **single web Copilot** exposes a project/session picker and an available **AI backend** selector (configured hosted API/BYOK or supported server-hosted agent), with separate execution-agent selection on tasks. Model lists, readiness, permissions, and cost are shown only for actual configured server-side capabilities. Preserve Tesbo’s violet light/dark theme, navigation, responsive chat, knowledge references, execution/evidence/review panels, and existing history. No user-installed software is required to use the Copilot.

**Execution-plane integration routes to evaluate (not shipped):** user-managed agent → Tesbo MCP (manual task pickup initially; optional agent-owned poller/plugin), independently hosted agent/gateway → Tesbo MCP, and optional Tesbo-managed hosted worker. **Copilot analysis backends are separate.** Candidate agent runtimes include OpenCode, Hermes, OpenClaw, Claude Code, Codex and Kimi; Grok-box is an optional sandbox substrate, not an agent brain. **Optional hosted-only routes:** Claude Agent SDK or supported server-hosted Claude Code runtime, Codex SDK/app-server in isolated hosted workers, compatible Kimi structured CLI/ACP in hosted workers, and Hermes gateway/agent endpoints. A hosted CLI is a **server-side agent implementation**, not a process on the end user’s laptop. Provider API authentication, SDK use, commercial eligibility, model support, and agent runtime support must be verified independently. Externally operated OpenCode/Hermes agents may also connect through scoped Tesbo MCP from their own environments without Tesbo providing local installation or control. MCP (Tesbo QA tools), execution MCP (browser/Playwright), and potential ACP (agent integration) remain separate protocols; never invent equivalent capabilities.

**End-to-end session flow:** human in the **single Tesbo Copilot**, or authorized external analyst → select/create a project-scoped session → retrieve canonical KB/versioned requirements/context → Tesbo orchestration/MCP task → **authorized hosted executor or externally connected MCP agent** → browser/Playwright/other allowed target tool → immutable Tesbo report/evidence → Copilot or external analyst review → (optional scoped retest through a linked task/attempt/independent report) → staged case/result/native-Bug proposals → exact human per-revision approval → shared protected apply into existing Tesbo suites/results/Bugs. The same Copilot UI can switch sessions without copying project knowledge; no AI backend, CLI tool approval or session owner impersonates a human reviewer.

**Canonical knowledge rule:** Each project document has one authoritative KB identity and immutable revisions; sessions reference versions rather than copying originals. Existing Test cases/Runs/Bugs and original reports retain their established authoritative stores, with unified search and links rather than duplicate KB files. Session summaries are derived, source-linked and rebuildable; an assistant's unreviewed inference cannot silently revise a canonical requirement.

**Source-to-code reuse:** extend existing `zyra_chat_sessions`, `zyra_chat_messages`, `ai_generation_requests`, `agents`/`actors`, `api_tokens`, Knowledge Base, `testcase_versions`, queues/storage/audit, Zyra chat/review and project UI shells. Keep durable event sequencing, provider session bindings, hosted-adapter isolation, capability checks, and per-project knowledge-version access as focused extensions where genuinely missing. No desktop companion, separate chat app, alternate case store, second defect tracker, generic remote shell service, or second UI framework.

**Validation:** FR-054–FR-063, AC-020–AC-024 and QA-141–QA-158 retain their IDs and now cover one web Copilot with multiple sessions, user-managed/remote MCP agents, optional managed execution and project-isolated evidence. T-407–T-410 remain the same tasks with revised boundaries. All are planned, not executed. The original Project Library eight files remain revision 1.2 pending supported canonical replacement; this working package is revision 1.4.1.

A newly created case has **no assumed execution PASS/FAIL** until its preconditions/steps/expected behavior have actually been evidenced and accepted for a stated target/build; an independently linked retest is required after a fix. The same Bug may be direct for one attempt and incidental for another.

**Historical integrity:** a Bug link does not silently rewrite a finalized Passed/Untested attempt; if evidence proves its *own* original expectation was violated, propose a separately governed correction with original result, author, evidence, reason and revision retained. An unfinished attempt may be finalized Failed on direct step evidence. Historical test-case definition versions, executed exact definition/version, and ongoing test-case evolution are distinct from evolving test results and defects. Keep one authoritative Test Cases/Runs/Bugs model and extend existing V63 snapshots and V48 Bug links.

**One cross-client standard:** project-agnostic **QA Standards & Playbooks** are reusable, versioned policy/decision guides and authoring templates, with scoped inheritance (platform/organization mandatory constraints, project defaults, module/artifact-specific standards and permitted task overrides). This is NOT an untrusted natural-language prompt replacing enforcement: Tesbo exposes effective guides to native Copilot, external MCP analysts and authorized executors with version hashes and enforces protected domain rules server-side. Modules show contextual guide entry points to the one canonical standard; they do not each create separate instruction databases. Optional tracker-specific templates (e.g., an organization's GitLab issue style) are configured data, not platform requirements.

**New design proof:** require direct/side/unknown finding classification and step/condition evidence; existing coverage search and disposition; reviewed case create/update; validated execution status; new retest after fix; source-preserving test-case version diff; same output structure from external ChatGPT/Claude and native Copilot when bound to one guide revision; strong read/write permissions and deny-on-untrusted guide text. See FR-071–078, AC-029–033, T-420–423, QA-228–248 and D-14/D-15. This is a **proposed implementation**, not a claim that Tesbo currently supports it.
