## Goal and actual user workflow

The user discusses a feature with ChatGPT. ChatGPT writes an exact natural-language testing prompt through Tesbo MCP. OpenCode claims it through Tesbo MCP, then controls its own actually connected **Chrome MCP or Playwright MCP** to test a supported target, without Tesbo proxying the browser. It submits its complete original report/evidence to Tesbo MCP. ChatGPT reads full sources, proposes cases/results/**native Tesbo defect records and optional tracker text**, and can send a *linked verification/retest task* through Tesbo MCP to OpenCode; the retest creates a separate report, new analysis and revised proposal. The user often corrects the drafts, asks for retesting or rejects findings. Only the exact selected approved revisions become official.

Tesbo becomes the approved project QA repository and coordinates agent handoffs; migrating Excel is optional and specific to the DMIS pilot. OpenCode can be replaced by Claude Code, Codex, Kimi Code, Hermes or another capable runtime; permissions are configurable per instance. A Tesbo-managed Playwright/Appium runner is not required for the initial Chrome MCP pilot; other projects may use their own supported external browser, API or mobile tools. Preserve Tesbo's existing Jest/e2e/Playwright checks and optional automation reporter without introducing a new execution framework as a dependency.

#### Test-case authoring guidance

1. **Name the actor and outcome.** Use a concise primary-actor-and-expected-behaviour title under the active project convention. 2. **Keep one coherent behaviour.** Supporting steps and actor changes may belong together when they establish one outcome. Split unrelated goals or materially different conditions needing independent verdicts. Compare actor/access scope, starting state, trigger/input class, requirement and expected effects before adding a case. Different permission, tier, state or file-format conditions may legitimately require separate cases. Classifications and related-area references do not create duplicate definitions.
3. **Separate setup, inputs, actions and expectations.** Preconditions describe the starting state, permissions and independently preparable fixtures. Test Data contains inputs, secure credential references and precise run-specific selection/generation criteria. Numbered Steps describe actions, navigation, actor changes and observations. 4. **Make the setup reproducible.** Name every necessary input and include units, currency, precision, file type and size where relevant. Preserve deliberate invalid data. Resolve variable inputs before the relevant action; distinguish an unavailable fixture from an unknown business rule. An unresolved design/input dependency is not a prepared fixture or a Passed/Failed result.
5. **Observe the right effect.** Capture a baseline before a change; compare the same record, scope and state afterward. A notification does not prove a saved record or downstream effect. 6. **Keep the case concise and complete.** Use the fewest understandable steps needed for independent execution, without a fixed global step cap. Keep authoring prompts, internal reasoning and revision narration outside case content while retaining meaningful source references and tester actions. Simplifying wording must preserve negative inputs, limits and assertions.

### Portable method for discovery and principle distillation

Apply this method when assessing whether an existing or proposed capability achieves its intended outcome, including routine status, conformance and completeness reviews. Trace a bounded, consequential outcome from initiating actor or event through the decision, needed evidence, action and consequence. Include one relevant exception or handoff where evidence permits. A feature request, known defect or suggested mechanism is unnecessary to trigger this step.

Choose discovery lenses from the context. Human roles, machine actors, scheduled jobs, events, contracts and handoffs may each be useful. User type, module and context are optional lenses. For a material correction, missed opportunity, false alarm or repeated friction, preserve **observation → consequence → failure class → invariant → agnostic principle → reusable question → context-specific example**. Label the observed evidence and causal hypothesis separately. **Shared distillation quality gate (UX/UI, Security and every other domain):** Start with the intended human or operational outcome, its actors and accepted constraints; research successful and failed examples and, when pertinent, contrasting designs from other disciplines. Compare observations and supporting evidence with *at least one plausible alternative causal explanation* before attributing success or failure to a mechanism. Classify the discovery by complementary, non-exclusive axes—human-outcome-driven, mechanism/causal, outcome-backward, anti-pattern/negative-space, comparative/counterfactual, lifecycle/relationship, and evidence/provenance. A category describes how the insight was found, not its truth, authority, or an obligation to apply every lens. Search existing principles first: extend an existing invariant when the meaning overlaps, rather than creating a differently named duplicate.

**Transfer and evaluation gate:** Express a *positive, application-independent causal principle* that explains why the outcome matters; distinguish it from a contextual implementation rule and a falsifiable test. Challenge it with materially different applications, a valid counterexample, an allowed exception, a no-change case and an insufficient-evidence case proportional to risk. Record its applicability and failure boundaries, provenance, competing explanations, predictive check and residual unknowns. Then instantiate it in the actual target's policies and permissions. Track **proposed → implemented → independently demonstrated effective** as separate statuses. Solicit authorized user feedback on the *resulting application* where meaningful; propose a reasoned, provisional grade for usefulness, fit and false-positive cost without treating satisfaction as security or causal proof. Canonical 03 governs evaluation receipts and grading/version approval; canonical 06 governs this authoring method. Preserve feedback, negative findings, rejected candidates and historical grades in the existing records; no candidate becomes active merely because its text or grade improves.
